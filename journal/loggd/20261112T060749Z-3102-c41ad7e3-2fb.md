## The finding worth the iteration: the keep-list trap again, one ticket after #3099

The obvious predicate is `inArray(notification.media_type, viewerMediaTypes(browsableTargets))`.
It is wrong, and for the same structural reason the keep-list was wrong on #3099 — except there
the orphan value was `track` in `LIST_TYPES_BY_MODE`, and here it is **seven** values in
`MEDIA_TYPES_BY_MODE`. `watchxd_media_type` (`src/server/db/schema.ts:23-36`) has twelve values;
`MEDIA_TYPES_BY_MODE` (`src/lib/media-types.ts:272-277`) covers five. A keep list hides any row
typed `track`, `person`, `author`, `actor`, `director`, `movie_actor` or `movie_director` from
every account, which is exactly what AC7 ("including every existing notification type") forbids.
The comment specifies the complement instead — a `hiddenMediaTypes(browsable)` built by walking
the modes `browsableMediaModeTargets` did **not** return — plus `isNull`.

**Generalisation for this role:** on loggd, any `*_BY_MODE` map is a partial cover of its DB
enum, so a viewer-scoping predicate written as a keep list silently hides whatever the map
forgot. Two tickets in a row. Expect it in #3104, #3069 and every other "reaches only accounts
that may browse X" ticket in trees #3062/#3063.

## What the two review rounds caught (nothing blocking in round 2)

Round 1, five findings, all real, all acted on:

1. **The AC2/AC3 test setup I recommended cannot see a preview at all.** I pointed the coder at
   `notification-write.integration.test.ts`'s preamble and said to seed an `account_authority`
   row. Its `requireMemberForRequest` is `requestMemberMock(authenticateRequest,
   checkUserNotSuspendedOrBanned)` — two arguments — and a two-argument mock *deliberately*
   returns a resolution with no `access` (`src/test/request-member-mock.ts:6-9,28`), so
   `withAuth` answers the enabled modes and the authority table is never read on the v1 path.
   The fix is the optional third `previews` argument; seeding the table is right only for the
   creation test, where `notify` reads it itself.
2. **I named the wrong criterion for the NULL exemption.** AC2 does *not* catch a missing
   `isNull`: for a preview account the hide set is `["album","artist"]`, so a `'book'` row
   survives `NOT IN` either way. Only an AC7 test that seeds a **row with no media type** and
   asserts it is still listed and counted can fail on it. Absence assertions over rows that
   were never seeded — the same shape as the `assert-effect-not-mechanism` lesson.
3. **I over-claimed on AC6.** "None of the three test files can prove a removed guard" is true
   of the two *read* guards (SQL), false of the creation guard, which is a JS filter at
   `notify.ts:184-194`: `notify.test.ts`'s FIFO select queue can feed an authority result with
   and without `books`, and its already-mocked `insert` and `dispatchPushNotifications` show
   both halves of AC1 — the only easy place to assert "pushes nothing".
4. `import_failed` is a **notification type**, not a media type (`schema.ts:1262`), and the enum
   runs to `:36`, not `:34` — my range cut off `movie_director`.
5. "Its only reader is the link builder" was false (`NotificationDropdown.tsx:299` reads it too).
   The defensible claim is the one that matters: no *query* filters on the column.
