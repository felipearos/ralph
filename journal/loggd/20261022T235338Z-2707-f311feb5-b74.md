## What landed

The #2694 guard (`src/server/movie-page/require-visible-movie.ts`) now covers
the member movie family, in two layers.

**Pages.** The shared request
(`[username]/movie/[slug]/_components/movie-user-page-request.ts`) calls
`requireVisibleMovie` above the profile read, which covers the layout header,
the layout poster and the four tab bodies. All six `generateMetadata` exports
call `movieVisibleToViewer`. `(review)` and `r/[reviewNumber]` call the guard
directly in their bodies, because they join `accountAuthority` and the shared
request would cost them a second profile query.

**Hydrators — the real finding of this ticket.** Three of the page's
"load more" paths are public server actions that take `profileUserId`,
`tmdbId`/scope and `mediaType` from the client, so the page gate was never the
only way in:

- `getShowDiaryPaginated` / `loadShowDiaryPage`
- `getShowUserListsPaginated` / `loadShowListsPage`
- `loadActivityPage` — gated in `readMemberActivityPage`
  (`src/server/queries/activity.ts`), the chokepoint its own docstring calls
  "where the arguments stop coming from the caller". That one placement covers
  the action, the page leaf `MediaActivityContent.tsx`, the profile feed and
  `src/app/api/v1/activity/route.ts` at once, ahead of the block check and the
  viewer-exclusion read.

Each returns an empty page before any read rather than throwing. Series are
never gated: TMDB carries no adult flag for them.

## Key decisions

- **Gate at the query chokepoint, not at each caller.** The diary/lists gate
  came from the local standards review; the identical activity-feed hole came
  from a **Codex P1** on `movie-user-page-request.ts:68` and was correct. Both
  are the same class of bug: a page gate in front of a server action the client
  can call directly.
- **Keyed on `scope?.mediaType === "movie"` only** in the activity gate. The
  separate `mediaType` parameter is a whole Media Mode's feed over many titles,
  not one title.
- **Fail closed:** the shared helper's unknown case is `"withheld"`.
- Every gate was **mutation-checked by the orchestrator, not the coder**
  (the coder cannot commit, so it can only report): reverting the reader to
  `movieVisibleToViewer(scope.tmdbId)` fails 4 cases, ignoring `viewerId` fails
  4, flipping `"withheld"` to `"visible"` fails 3.

## For the next iteration

- **The unscoped profile activity feed still has no adult filtering** — a
  flagged movie's activity can appear in a member's general feed. The spec axis
  confirmed that surface is not one #2707 enumerates, and #2685 already has a
  `member-activity-gate` child for it. It was deliberately left out; do not
  read this PR as having covered it.
- **This iteration was almost entirely wait.** Ten supervisor waits across nine
  sessions — six CI rounds, two merge rounds, plus two that resumed mid-build —
  and not one of the timeouts was anything red: Buildkite builds 4048–4100 ran
  back to back on this agent host, load average 39.6 on 16 cores at 22:40Z. The
  published learning is `ci-wait-times-out-behind-host-build-queue`; a timeout
  with the build plainly running and nothing failed is not a red and not a
  reason to re-run or block.
- One genuine red (build 4061) was the `supabase-go` bootstrap failing in the
  e2e job's `test:security` step **before any test ran** — not the diff. The
  single §5.4 re-run allowance went to it; builds 4058–4060 on the same host
  had passed the same nine jobs, so it is intermittent.
- One rebase, in session 6, over a real textual conflict with #2783's landing.
  §5.6's cap ended at round 1 of 2.
- `bun lint` and `bun run build` were never run locally on this branch: the §4
  host fence refused them every time the host was checked. Both are inside the
  required `buildkite/loggd`, which is green on the merged head.
- Model routing was right for the work: the coder found neither hydrator hole,
  and both reviewers (local standards, and Codex on the PR) did.
