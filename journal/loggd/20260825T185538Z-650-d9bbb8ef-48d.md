## What the reviews caught, which is the case for keeping the gate

The standards axis and the spec axis were run independently and **both
independently found the same critical bug**, which is the strongest signal
either of them produced:

- **The onboarding gate as I first wrote it was bypassable.** I gated on the
  submission's *fields* — `skipRemaining === true`, or `step === "profile" &&
  skip`. But neither transport constrains `step` to the step the account is on,
  and `answerOnboardingStep` honours a later step by recording every step it
  jumps as skipped. So `POST /api/v1/onboarding {"step":"import","skip":true}`
  walked a username-less Google account straight past `profile` and out of
  onboarding permanently, in one request, naming neither guarded field. The fix
  gates on the state the submission would **produce**
  (`isOnboardingComplete(next) || isOnboardingStepAnswered(next, "profile")`),
  which closes that door and every other one at once. Two new tests pin it.
  **The lesson is general: a guard written against the shape of a request is
  only as good as the request shapes you thought of.**
- `redirectTo` was trusted from an unauthenticated body and forwarded into the
  emailed link — an open redirect whose payload is somebody else's tokens. Now
  the origin is the server's and only a `getSafeRedirect`-validated *path* is
  the caller's.
- The web Resend button posted to the versioned route, which mints a
  **native-flow** link whose tokens arrive in a URL fragment `/auth/callback`
  cannot read. Web members would have got a Resend link that always failed while
  their original one worked. Web now has its own `/api/auth/resend-confirmation`.
- Resend was a **membership oracle**: GoTrue errors for an already-confirmed
  account, so `400` vs `200` sorted a wordlist into members. Every non-429
  provider answer is `sent` now. Both of my original tests for this property
  were vacuous — one only exercised the happy mock, the other mocked the core
  and asserted the mock. A test named for a security property it never reaches
  is worse than no test.
- Both endpoints keyed their own rate-limit bucket rather than
  `rateLimitIdentifier`, handing one IP a budget on top of every other `auth`
  route's — the exact drift `src/lib/rate-limit-identifier.ts` was written for.
- Two throw paths sat outside the core's `try`, and an unexpected fault
  rendered as 400, so a sign-up outage would not trip 5xx alerting.

## Decisions worth not re-litigating

- **Password minimum is 8.** Web asked 6, mobile asked 8, the server asked
  nothing. Unified up; sign-in applies no length check, so existing
  six-character passwords still work. `e2e/auth.spec.ts` and
  `src/app/sign-up/loading.tsx` updated with it.
- **Mobile confirmation still lands in a browser, not the app.** No deep link
  handler exists. That is **#651**, explicitly, and it does not belong here.
- **The onboarding e2e fixture cannot express a username-less account** —
  `e2e/db-cleanup.ts` keys the fixture on its username (`getUserId(sql,
  username)`). The gate is pinned by 15 unit cases in
  `onboarding.username-gate.test.ts` instead. Changing that fixture is a
  bigger change than this ticket.
- **A stranded-account rescue** is in `submitOnboardingStep`: an account that
  skipped `profile` before this gate existed can still supply a username, and
  it advances no state. Not asked for, but the gate creates the stranding.
