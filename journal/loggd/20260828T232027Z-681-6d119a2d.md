## The thing that cost the most, and that #737 also has

**A migration in `drizzle/` takes down every PGlite-backed suite, and one of
them fails as "no tests".** Drizzle hands a migration file to PGlite as a single
statement, so any multi-statement RLS migration dies on `42601 cannot insert
multiple commands into a prepared statement` before a single test runs.

`bun run test` was green on `origin/main` and red on the first commit of this
branch. Three suites broke loudly; `src/server/queries/lists.hidden-visibility.test.ts`
broke as `Tests: no tests` with a **non-zero exit**, because its migrate call is
at module scope and the throw took the file out before vitest collected
anything. A "no tests" line is a failure, not an empty file — read the exit code.

Four call sites replay `drizzle/`: `src/test/database.ts` and three suites that
each hand-rolled their own exclusion list, which is precisely what that module's
header says it exists to prevent. The fix is one exported predicate,
`isAuthorizationBoundaryMigration`, matched case- and quoting-insensitively on
`create policy`, `auth.uid()`, or a grant/revoke naming `anon`/`authenticated` —
the third clause because a migration can narrow a write surface without writing
a policy at all. It excludes the WHOLE file, so schema and policy must not share
a migration; that is now written down where the predicate lives.

**#737 (#680) has the identical break and has not fixed it.** Whoever picks that
draft up after its apply should expect a red `bun run test` and should take this
commit's approach rather than rediscovering it: `747cff88`.

## The clone probe is the whole method — reuse it

The #680 journal's recipe worked unchanged and is still the reason this shipped
with measurements instead of reasoning. `docker exec supabase_db_loggd`,
`CREATE DATABASE list_probe`, `pg_dump --schema-only -n public -n auth` from the
running stack, restore into the probe, `GRANT anon, authenticated TO postgres`,
then `SET ROLE` + `SET request.jwt.claim.sub` per actor. Drop it afterwards.

Two notes on top of what #680 recorded: the restore prints ~55 errors, all of
them `must be able to SET ROLE "supabase_auth_admin"` and `permission denied to
change default privileges` — auth-schema ownership, irrelevant to RLS, and NOT a
sign the clone is bad. And a single `pg_temp` function that returns one row per
actor turns "what can each of five actors read across four tables" into one
readable table, which is what made the before/after diff obvious enough to put
in the PR body.

**Do not run `bun run test:security` locally.** It resets the shared stack twice
and CI, Felipe and the E2E runs all share it. It does not matter anyway: the
migration is not applied to that stack, so the assertions could not pass. CI is
where they run for real — and importantly, **the security suite lives in the
E2E job, not `quality`**, so a migration draft that is red at
`db:check-production-migrations` still gets its security suite executed. That is
the job to read on a draft like this one.

## What the two review axes were worth: an existence oracle

Both found the same thing independently, and neither of them was wrong.
`list_like_insert_own` was left ungated: `WITH CHECK (auth.uid() = user_id)` and
nothing about the parent. `list.id` is a serial, so POSTing a like for id N
answered 201 for a List that exists and a foreign-key violation for one that
does not — **a working existence oracle over exactly the owner-only and hidden
Lists the migration had just made secret**, plus a like landing in the owner's
List Popularity from outside the audience. Before this change the oracle
disclosed nothing new, because the table was world-readable; the read rule is
what turned it into a leak. The migration already made this argument for the
discussion INSERT and simply had not carried it to the sibling table.

The generalisable lesson: **when you close a read, re-audit every write on the
same object.** A write that answers "does this exist" is a read.

The other finding worth carrying forward: **two of the three write assertions
could not fail.** The `is_hidden` denial aimed at the moderated List, which the
new read rule already hides from its owner — delete the entire grant change and
the test stays green. It now aims at the List the owner *can* read and *can*
otherwise update, where only the column grant can refuse, and the permitted
counterpart (owner renames their own List) was added, because an allowlist that
over-revoked looked exactly like enforcement from the denial alone. Same shape
as the standing "assert effect, not mechanism" rule: pick the target where only
the mechanism under test can produce the outcome.

Also caught: nothing asserted that a **follower cannot read the owner's
owner-only List**. A predicate that asked for the follow without first asking
whether the audience is the Followers Audience — the single most likely way to
get this function wrong — would have passed the whole suite.

## The review stages both failed, and the fallback is what saved it

`ralph/inspect.sh review.standards` and `review.spec` each **exited 0 and
produced no report** ("exited cleanly but never produced a report"). Exit 0 is
not in the documented failure set (2 = harness unavailable, 4 = errored), so
nothing forced a fallback — the stage just silently returns nothing, and a
careless iteration would have shipped unreviewed on a green exit code. The
`.jsonl` had 16 and 10 text events and no final assistant message, so there was
nothing to salvage by re-rendering.

Falling back to two in-session `Agent` calls on `model: "opus"` — the alias the
lineup names for the exit-2 case — worked, took ~5 minutes each in parallel, and
produced the two best findings of the iteration. **Treat "exit 0 with no report"
as exit 2.** Both stages failing identically suggests a renderer/harness
mismatch rather than bad luck, so expect it again until `inspect.sh` learns this
harness's event shape.

## Decisions worth knowing

- **Staff get nothing at this boundary**, same as #680, same reasoning
  (moderation reads through Drizzle, which is RLS-exempt as table owner). The
  suite asserts a moderator cannot read a hidden or owner-only List.
- **No collaborator clause.** The two application read paths genuinely disagree:
  `viewerIsInListAudience` does not admit collaborators, `list-summary/index.ts`
  admits an accepted collaborator on a collaborative List. The migration follows
  the canonical helper, the stricter of the two, and says so.
- **The hidden-comment policy is one notch stricter than the app.**
  `listCommentIsRenderable` keeps a moderator-hidden top-level comment that
  still hosts live replies; the policy drops it. The alternative would return
  hidden CONTENT to get a tree shape right, and nothing renders a thread over
  PostgREST. Written into the migration header so it reads as a decision.
- **`list_collaborator`, `list_draft`, `list_thumbnail_pins`,
  `profile_pinned_list`, `user_list_directory`**: RLS on, zero SELECT policies,
  verified by inserting rows and reading 0 as `anon`. Untouched on purpose.
