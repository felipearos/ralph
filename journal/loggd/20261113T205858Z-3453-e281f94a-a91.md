**Decision.** `ready-for-human`. #3453 is the `learning-fix` for
`prod-migration-ledger-unapplied`: unapplied prod migrations turn every web PR's
`buildkite/loggd` red. The learning's own Suggested fix is "A person applies the
pending migrations to prod by hand", which is a withheld production credential
(readiness rule 5). The body is the generic learning-fix template — `What to
build` says "Triage this recurring problem into a concrete, bounded code change"
and the first acceptance criterion asks someone to specify the criterion — so
there is no spec to promote either.

**Mapper evidence (route 1, ralph-mapper, clean).** The gate is in this repo and
is deliberate: `.buildkite/pipeline.yml` `key: production-migrations` runs
`bun run db:check-production-migrations`;
`scripts/check-production-migrations.ts` `compareMigrationLedgers` reports both
directions (`missing <tag>`, `applied ahead of main: <hash> at position N`) and
throws `LEDGER_MISMATCH_MESSAGE` on any finding. Escape hatches that already
exist: the docs-only `ci-scope-verdict.sh` skip, the availability-only advisory
for positively identified non-main branches, and the pending-safe-apply verdict
behind the `/etc/loggd-migration-apply-switch/enabled` file switch (which covers
only the committed-not-applied direction, so "applied ahead" always stays red).
No env-var skip, no allowlist, no PR-vs-main softening. `docs/adr/` says nothing
about the gate; `docs/development-workflow.md` states the policy twice —
"ledger mismatches and failures on `main` or unknown CI remain red" and "If a
queue build applied and the PR then did not merge, the ledger check reports
production as applied ahead of `main`; that one case needs the operator."

**Why not needs-info, and why not ready-for-agent.** Loosening the gate is a
reversal of a documented policy, not a bug fix, so it is a decision no rule
settles — and the rule that exists says the opposite. There is no question a
sentence of clarification would answer; there is a choice to make. The comment
lays out four options for the person: (1) operations only, keep the gate; (2) a
bounded diagnosis-only change that names the PR owning each unexpected hash and
says "operator, not rebase" — the only agent-sized one, and it unparks nobody;
(3) make "applied ahead of main" advisory on non-main branches, which needs an
ADR first; (4) the harness-side `classify.ts` fix, which is `felipearos/ralph`
and cannot be a ticket here.
