## You cannot read a Buildkite log from inside this loop

`BUILDKITE_API_TOKEN` is on the withheld list, `doppler` is forbidden by the
same rail, and the build page 403s anonymously. The `ci-debugging` skill's whole
procedure begins with `doppler secrets get BUILDKITE_API_TOKEN`, so that skill is
**not usable by this loop** — worth knowing before you route to it.

What you *can* read, and what I got out of each:

- `gh api repos/.../commits/<sha>/status` — per-context state and description.
  Better than `gh pr checks` here, because it gives you `Build #N failed
  (7 minutes, 52 seconds)` versus `is failing`, which is how you tell a finished
  build from a running one. `gh pr checks` reported `fail` on a build that was
  still going, and my §5.4 wait loop exited immediately on it because there was
  no `pending` row. **A Buildkite `fail` is not necessarily a finished build.**
  Loop on the description until it says `passed` or `failed`.
- `docker logs buildkite-agent` — job start/finish, PIDs and exit statuses. No
  commands and no output, but the *timings* are real evidence: #1130 had one job
  die at **40 seconds** and another at **6.5 minutes**. A 40-second death is an
  early step, which is what pointed at `db:check-production-migrations` rather
  than at tests.
- `docker exec buildkite-agent env` — 20 variables, no `RALPH_*`. That kills the
  agent-wide env-leak hypothesis (the `PLAYWRIGHT_TEST_BASE_URL` incident) in one
  command; do it early, it is free.
- `/buildkite/builds` inside the agent container is **empty** — workspaces are
  cleaned, so there is no local log to salvage. Do not go looking twice.

## Both review axes found the same real bug, and delegation did not

`ralph/delegate.sh` (deepseek-v4-flash) produced the conformance test in one
round: AST walk, virtual-repo fixtures, anti-vacuity pins, and it ran its own six
mutation probes and reported all six. Good work from a long, concrete brief.

It also **documented a hole instead of closing it**: the header listed
"the CTE name in `db.$with(\"name\")`" under *what it deliberately does not
check*. That is an identifier built from a name, and the advisory's own scope
note names CTE names as a risk. It wrote the exclusion because my brief listed
three APIs and `$with` was not one of them. **A brief that enumerates the cases
gets exactly those cases**; the executor treated my list as the boundary of the
problem rather than as examples of it. I closed it myself.

Then both review axes independently found a *fifth* API that neither of us saw:
**`alias(table, name)` from `drizzle-orm/pg-core`**. It reaches the same
`escapeName()` — the aliased-table proxy answers `Table.Symbol.Name` with that
string — and it evades every detector twice over: it is a bare call rather than a
property access, and it names its identifier in argument **one**, not zero. Five
call sites use it today. Nothing was live, but the file's claim to cover the
surface was simply false.

**The lesson is the one from #682's `updated_at`, in a new costume: I wrote the
brief from a grep, and the grep only finds the API you already thought of.**
Before enumerating a "complete set" of call paths into a library function, read
the library's exports, not your own repository's current usage.

The spec axis also caught an overconfident **"no"** in the advisories doc:
`sanitize-html` is a *runtime* dependency that `require`s `postcss`, which
depends on `nanoid`, so both are in the deployed graph. Chasing it down gave a
better answer than either the original claim or the correction: sanitize-html
only runs `postcssParse` over a `style` attribute the policy allows, and neither
policy in `src/lib/sanitize.ts` allows one — so it is latent, not live, and
**adding `style` to `allowedAttributes` would activate it.** That trigger is now
written down. A wrong "no" in a security table is worse than no table.
