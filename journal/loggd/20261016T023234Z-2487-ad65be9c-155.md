## Key decision: a true-positive split, with the migration isolated into one human child

Four checkboxes, so it was the surfaces arm again — but unlike #2480 this one genuinely builds on
web, mobile, server **and** db. One `ralph-mapper` pass put it at ~22 files.

The load-bearing finding is that **nothing on `profiles` can hold the dismissal today**: the
onboarding account-state block (`src/server/db/schema.ts:187-199`) is enum/timestamp-typed,
`feed_preference` (`:1814`) is four feed booleans, every `jsonb` column belongs to something else,
and mobile's only completion record is the device-local AsyncStorage key in
`mobile/lib/onboarding-completion.ts` — which is precisely what #2487 forbids. So the ticket needs a
new column plus a migration, which no loop may write or apply.

That could have made the whole of #2487 `ready-for-human`. Instead the split isolates it:

- **#2495 — db + server, `ready-for-human`** (`onboarding-core`). The column
  `profiles.welcome_card_dismissed_at` + a backfilling migration, `readWelcomeCardState ->
  { pending, titleCount }`, a `welcomeCard` field on `OwnProfileHeaderWire`
  (`src/app/api/v1/users/me/route.ts:95`), `dismissWelcomeCardAction`, and
  `POST /api/v1/users/me/welcome-card/dismiss`. Blocked by #2479 (migration number + the count helper).
- **#2496 — web, `ready-for-agent`** (`web-landing`). `WelcomeCard` mounted in
  `src/app/_components/authenticatedHome.tsx`, the `/feed` greeting at
  `src/components/home/HomeEmptyState.tsx:159`, the dead `WelcomeGreeting.tsx:46`, a story, and the
  landing Playwright assertion. Blocked by #2479.
- **#2497 — mobile, `ready-for-agent`** (`mobile-landing`). Card + greeting on
  `mobile/app/(tabs)/index.tsx` off the `/users/me` read `useMyProfile` already makes
  (`mobile/hooks/useProfile.ts:147`), plus RNTL. Blocked by #2479, #2480.

Staffing: I did **not** put the client children in `onboarding-core`. Both were deliberately
specified to avoid the snapshot (`src/server/queries/onboarding.ts`, `useOnboarding.ts`) and ride
`/users/me` instead, which makes their file sets genuinely disjoint from the in-flight seen-step
work — and the known "staffing groups serialise whole specs" learning says sharing the group here
would buy nothing but a queue.

The count is the parent spec's definition, quoted from #2478 ("watch status is Watched or
Watching … Want-to-watch and watchlist-only rows do not count"), reusing whatever helper #2479
lands rather than defining a second count. `getProfileStats` (`src/server/queries/userStats.ts:24`)
is not it: it counts every non-null `watch_status` row. No `decisions` entry: this is the parent
spec's own text, not a product question I settled from a repo doc.

## review.spec — two rounds, and what they changed

Round 1 (14 findings) and round 2 (4) were both run against a fetched `.ralph/logs/spec-2487.md`
with the full child bodies pasted into the brief as the change under review. What they caught, all
fixed in the text that was written:

- A new nullable column is null on every row, so **every pre-existing completed account** would have
  read as "card pending" → #2495 now requires an explicit backfill `UPDATE`.
- No child named the wire shape the other two are written against → #2495 now names the read, the
  field, the action and the route; #2496/#2497 are written against those names.
- #2497 was inventing a "Welcome back" the mobile home **does not have today** (the only one in
  `mobile/` is `app/auth/sign-in.tsx:55`) → the greeting now renders exactly when the card does, and
  the screen is unchanged for everyone else.
- The Discover **Members** category has no deep link (`mobile/app/(tabs)/discover.tsx:877` keeps it
  in local state) → navigating to it is explicitly out of scope.
- `resetOnboardingFixture` (`e2e/db-cleanup.ts:1510-1518`) does not clear the new column, so the
  landing spec would pass once and fail on every rerun and retry → now a criterion on #2496.
- Unfailable criteria removed: the "dismissed/absent" story, and the backfill assertion that only
  re-tested the read (now an honest review-and-apply check). `caught_up` is explicitly deferred to
  #2479's helper with the test asserting its answer, rather than left silently ambiguous.

## The limitation I hit again, and the follow-up it needs

`add-blocker` accepts a plan-local `ref` only for `blockedBy`, never for its target, so **the
#2496 → #2495 and #2497 → #2495 edges could not be written by this plan** (same wall the #2483 split
hit). Mitigation: both client children carry a stop rule in `## What to build` — "if
`welcome_card_dismissed_at` is not in `src/server/db/schema.ts` at `origin/main`, this ticket is not
startable, leave it blocked rather than adding the column yourself" — and both are blocked by
#2479/#2480 anyway, so neither is takeable today.

**Next triager iteration: add `add-blocker` on #2496 and #2497 with `blockedBy: 2495`.** All three
now have real numbers, so it is one tiny plan. Doing it before #2479 merges removes the only
remaining way a coder could pick up a client half before the column exists.
