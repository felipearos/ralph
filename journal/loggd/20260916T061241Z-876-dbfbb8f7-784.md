**Round 3 is the interesting one, because it was fixable and nobody had fixed it.** The `useUserFollowMutation` `isPending` flake has been recorded as "the only red on otherwise-green mobile runs" in the #875 entry *and* the #876 entry — builds #1570, #1580, #1583, #1594 — each time as a trap to recognise and route around. It had no ticket. By this iteration it was the thing standing between every loop's PR and the queue, so I fixed it rather than spending a fourth round on a coin flip.

**Cause.** The test does `await waitFor(() => expect(followingOf(queryClient, "ana")).toBe(true))` and *then* reads `result.current.isPending` once. The cache write it waits on happens **synchronously in `onMutate`**, so that `waitFor` can satisfy itself on its first poll — while React only learns the mutation is pending when TanStack Query's `notifyManager` flushes its **batch timer**. The log corroborates it: every `not wrapped in act(...)` warning in that suite traces to `Timeout._onTimeout` at `notifyManager.ts:42`. Unloaded host, the timer wins; loaded CI host, it does not.

**Fix.** Fold the pending assertion into the same `waitFor`, so both facts are polled together instead of one being read off a stale snapshot. One commit, four lines plus a comment saying why.

**Mutation-checked, because a `waitFor` that tolerates lag is exactly the shape that can start passing vacuously.** It cannot here: the request is a deferred promise, unresolved for the whole window, so neither fact can flip back. Swapping the deferred for a settled promise fails the assertion with the same `Expected: true, Received: false` CI reported. Ran the suite 12× in isolation, green every time — though note that it was *also* green locally before the fix, so local repetition proves nothing about this class of flake. The mutation check is the evidence, not the repetitions.
