## What the split turned on: the parent's premise is wrong

The body says `media=books` "replaces, for that request only, the refusal #3068 keeps".
There is no refusal for a viewer who **may** browse Books, on either read:

- **Popular reviews.** The route declares `{ media: "filter" }`
  (`src/app/api/v1/reviews/popular/route.ts:16`), the wrapper resolves the scope before the
  handler, and `books` is let through for a preview holder
  (`src/lib/api/media-mode-scope.ts:284-298`). `getGlobalPopularReviews(…, "book", …)`
  already returns book rows from the cached ranking (`community-rankings.ts:48-52`, `:123`;
  pinned at `community-rankings.media-guard.pglite.test.ts:142`). What drops them is
  `hydrateReviews`, which sends every non-movie row to `getTVShowBasic(review.tmdb_id)`
  (`review-hydration.ts:110-124`) — a book row's `tmdb_id` is not a TMDB id — and
  `catch { return null; }`s the failure. The answer today is `200 { reviews: [] }`.
- **Friends section.** `readBookFeedSection` returns a hard-coded `emptyPage` for every
  non-titles Books section (`books-sections.ts:142-143`), pinned in the wire type at
  `packages/shared/src/feed-sections.ts:306-311`.

So the work is hydration plus the Books section's own envelope rules; the gate and the
cache boundary the body asks for already hold, and each child **pins** them rather than
building them. Both children are written against the code and say so.

## The three judgement calls

1. **The Books Feed path does not go through the registry.** `readBookFeedSection` is
   reached straight from the route, so `readFeedSection`'s fallback and feed-control-category
   rules (`read-feed-section.ts:227-253`) are re-implemented in `books-sections.ts` rather
   than inherited. #3549 is the first Books section answering to a category at all.
2. **An unresolved book is kept in #3548 and dropped in #3549.** #3548 follows #3104's
   `ProfileReviewBook` contract (reference plus placeholder title, never absent); #3549
   follows the Feed's own behaviour, where the shows section drops a review whose title has
   no poster (`popular-reviews-with-friends.ts:87-93`). One unresolvable book can therefore
   appear in the popular reviews read and be missing from the Feed section. Written onto
   #3549 as deliberate — **the call most worth revisiting** if it reads wrong in use.
3. **"Nothing viewer-derived" in the cache key means no viewer Media Modes.**
   `excludedUserIds` *is* viewer-derived (`reviews/global.ts:135`: blocks plus feed mutes,
   normalised so viewers excluding the same set share an entry). Both children say "no viewer
   Media Modes or browsable set", so the criterion is testable against unchanged code. The
   reviewer caught the original wording, which would have failed on `main`.

## The spec review, which earned its round

Nine findings, all acted on:

- **#3549 AC5 was unpassable.** A signed-out request to the Feed sections route is a **401**
  (`withAuth` refuses before the scope resolves, `api-utils.ts:414-420`), not the 400
  `VALIDATION_ERROR` a signed-in viewer without the preview gets. Both are now named
  separately, and only the 400 half carries the mutation check.
- **#3549's "a continued page never falls back" is unreachable over HTTP.** The registry entry
  declares no `pages`, so the route answers any cursor on this section with 400
  `does not support paging` (`feed/sections/route.ts:119-124`). The AC now pins the 400 at the
  route and the never-falls-back branch through a direct `readBookFeedSection` call.
- A wrong line citation (`media-mode-scope.ts:284-290` is the *pass* branch, not the refusal),
  a missing AC for the row's own fields and `showId`, a Hardcover-outage case, and a note that
  `hydrateBooks` answers no review ids so it must be restructured into a by-id map rather than
  zipped.
