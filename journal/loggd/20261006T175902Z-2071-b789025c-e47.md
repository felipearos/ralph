**What shipped.** `settleProfileLists` in `mobile/hooks/list-write.ts` — the settle
shared by the `profile-list-pin`, `profile-list-reorder` and `list-directory-save`
List Write kinds — kept a narrower contract than every other List Write. It now

**Key decisions.**
- `{ listDetails: false }` verified against `ListDetailMeta` and `ListSummaryWire`:
  neither carries a pin, pin-order or List Directory field. Flagged in the PR body
  as a narrowing the owner may widen.
- The settle now also stales every title's Lists directory (`mediaListsPredicate`),
  wider than the pre-#2093 code. Comes with the shared helper by design; spec review
  judged it defensible, and it is flagged too.
- AC3 deliberately not duplicated — a second raw-key scanner in
  `list-surfaces.test.ts` would be a weaker copy of
  `hooks/__tests__/list-write-key-owner.test.ts`. A pointer comment instead.
- Declined: unifying `profileKeys.me()` vs `listSurfaceKeys.profileRoot()` in one
  module (pre-existing, other kinds' blast radius); dropping the `stale` loop as
  duplicated (`PINNED_KEY` and `DIRECTORY_KEY` are not in `EVERY_SURFACE`).

**Dead ends worth remembering.**
- **A vacuous staleness test.** Asserting invalidation via `fetchStatus` on *seeded*
  keys passes even with `refetchType: "all"` — a seeded key with no observer never
  refetches whatever invalidates it. Replaced with live observers counting each
  read's `queryFn`. This is the general trap for any React Query invalidation test.
- **A `const` referenced from inside a `describe` body, declared below it, yields
  `undefined`** under the jest/babel transform — not a TDZ `ReferenceError`. It
  seeded a query with an undefined key and crashed `isProfileListSurfaceKey` inside
  `invalidateQueries`. Fixed by moving the describe below the shared apparatus.
- A pre-existing suite encoded the defect: `list-write.test.ts` asserted "the owner
  read and the profile Lists reads, and nothing else", with `BROWSE_KEY` among the
  untouched. Three tests failed on the fix and were rewritten.
