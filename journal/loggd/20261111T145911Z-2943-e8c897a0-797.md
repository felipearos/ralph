# 2026-11-11 — #2943 The Hardcover client retries a rate-limited request

**Outcome: merged.** PR #2996, merged through the Mergify queue at 14:57:21Z (merge commit `fe830579`), batched with #2992 and #2994; issue auto-closed and labelled `testo-done`.

**What shipped.** `fetchHardcover` (`src/lib/hardcover.ts`) now treats HTTP 429 as the one retryable failure: it throws a module-private `HardcoverRateLimitError` carrying the `Retry-After` seconds and hands the policy to the repo's shared `withRetry` (`src/lib/retry.ts`) — 3 attempts, a 10s cap on any single wait, and the helper's jittered backoff when Hardcover states no delay. Exhaustion throws `Hardcover API: rate limited, 3 attempts exhausted` with the rate-limit error as `cause`. Every other failure still fails on the first attempt with its old message. 17 tests in `src/lib/hardcover.test.ts`, each mutation-checked.

**Key decisions, and what was ruled out.**
- **Not a hand-rolled retry loop.** The first commit copied `fetchSpotify`, as the issue literally said. The standards review pointed out that would be the third copy of `Retry-After` handling in a repo that already owns that policy in `withRetry`. Switched to the shared helper; the observable behaviour is still exactly what the issue asked for.
- **Dropped twice, deliberately:** the correctness reviewer's P2 that a `Retry-After` above the cap should fail fast rather than retry at the cap. It contradicts the acceptance criterion ("waiting the provider's stated delay *up to a cap*") and the Spotify precedent the issue names. The rebuttal was written out in advance in case Codex raised it; it never did.
- **Also dropped:** adding jitter on top of a server-stated delay. `retry.ts` deliberately lets a server delay beat its computed backoff, and changing that is a change to the shared helper — outside this ticket.
- Three review rounds of small flagged-line fixes were done by hand; `delegate.sh` ran once, exit 0, for the whole first implementation slice.
