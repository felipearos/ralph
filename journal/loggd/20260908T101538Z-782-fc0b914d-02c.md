## Read this before writing another source-scan test

- **Name lists are not a fence.** The first cut matched write-helper
  basenames (`watchStatus*`, `review*`, `log*`). Both review axes found the
  same two holes in minutes: `db.query.review` needs no schema import at all,
  and `~/server/queries/reviews/social` or `~/server/actions/activity` reach
  the tables with names that say nothing. Following imports and judging each
  module by what IT touches closed both, and the real tree was clean under
  it on the first run — except one hit that decided the fence.
- **Fence the tables the module owns, not the family.** With `reviewLike`
  and `reviewComment` fenced, the List CSV import route reached
  `queries/comment-visibility.ts` through `actions/list`. That is List
  comment visibility, nothing the merge writes. The fence is now exactly the
  merge's four tables, with the reason in a comment. Baseline-growing was the
  alternative and #770's journal already says why not.
- **`import\s+\{([\s\S]*?)\}\s*from "…/schema"` is wrong** in any file with
  more than one import: the lazy match starts at the FIRST `import {` and
  swallows every import before the schema one, so `library-merge.ts`'s own
  names came back short. `[^}]*` is the specifier list. The self-test that
  asserts the merge's direct touches is what caught it; keep one such
  positive assertion in every scan test.
- Mutation-tested three ways (a `db.query.review` in imdb, an
  `actions/activity` import in generic-csv, a multi-line `review as
  reviewTable` in letterboxd); each fails naming the module. The failure
  lists the reached module once per in-scope root that reaches it (routes →
  jobs → run), which is noisy but names the culprit on every line.
