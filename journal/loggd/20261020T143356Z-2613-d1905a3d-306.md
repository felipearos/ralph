**What changed.** The recovery email link now points at {{ .SiteURL }}/auth/confirm?token_hash&type=recovery. The web and mobile confirm surfaces verify only when the user taps "Set a new password". On web the tap goes to /auth/callback, which sets password_reset_pending, then to /reset-password. On mobile the tap runs verifyRecoveryLink and then goes to reset-password?verified=1, and only when store.recovering is set. The shared parser returns an un-redeemed `recovery`.

**Key decisions.**
- Built the link on SiteURL, not RedirectTo: callers shape their redirects differently, SiteURL is safe whatever the deploy order, and #976 did the same.
- Mobile only honours `verified=1` when `recovering` is set, so a crafted link cannot skip reauth.
- A network failure or a rate-limited tap keeps the tap retryable. The rate-limit case came from a valid Codex P2 and was fixed in a897aeffe with a mutation-checked jest test.
