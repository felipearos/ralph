## Key decisions

- **A REVOKE on a sequence is deliberately NOT safe.** The first cut matched
  `<table>_<column>_seq` by name; the correctness review broke it twice. That
  name is only PostgreSQL's first choice and is silently changed when taken, so
  `CREATE TABLE episode_watch (status_id bigserial)` guessed the live
  `episode_watch_status_id_seq` — unfixable by reading SQL. Removed, with the
  reason in the code, and every guessed-name case pinned unsafe.
- **Residual limitation (stated in the PR body):** a new table with a `serial`
  id still needs its sequence REVOKE in a reviewed lock migration. AC1 is about
  the table and is met.
- `AT_ForceRowSecurity` dropped — it narrows nothing for a client, only puts the
  server under RLS. A dotted `relname` is refused as `unrecognised`.
- `drizzle/0084_progress_updates.sql`'s stale comment left alone on purpose:
  production's ledger stores each applied file's SHA-256, so editing it would
  red `production-migrations`.
- Three mutation survivors kept as fail-closed layering, documented in the code
  as redundant given the object check.
