**What the ticket actually was.** It reads like a verification ticket — "ensure
writes converge, close a11y gaps, verify the journeys" — and the trap is
treating it as one. AC4 and AC5 were already met by pre-existing e2e and mobile
journey suites; nothing needed writing there. The real work was AC1/AC2, and the
answer to "does mobile invalidate everything a List write stales?" turned out to
be no, in three concrete ways. Do not read a hardening ticket as a no-op: go map
the thing it claims is already true.

**The three convergence bugs, all found by mapping rather than by reading the
ticket.**

- `useRespondToCollaborationInvite` invalidated **nothing at all** — no
  `useQueryClient` call, no `onSuccess`, while its three sibling mutations in
  the same file all refresh the roster. Accept flips the row and the List's
  collaborative flag; the owner's roster kept saying "pending".
- `useCreateList` never invalidated the Lists tab of a title it was seeded with,
  so the contextual "Create new list" path left the new List missing from the
  screen it was created from.
- `useSetListItemMembership` (Manage List) and `useSetListMembership` (the
  picker) wrap the *same* `PUT /lists/{id}/items` for the same act, with two
  different blast radii. Only the picker refreshed the media surfaces.

Plus a server one: accepting flips `is_collaborative`, which every List Summary
projects as `collaboration.enabled`, and the collaborator write core never
called `invalidateListSummaries()`. Signed-out discovery advertised a List as
non-collaborative for the full 300s `cacheLife`.

**The key decision, and it was the review's, not mine.** My first contract took
`{ media: MediaReference[] }` and asked each call site to enumerate the titles
it touched. Both review axes independently found the same hole: three of the six
Manage List writes (`useSaveListContent`, `useSetListVisibility`,
`useDeleteList`) can't enumerate — a save reorders and drops in one go, a delete
takes every title with it, a visibility flip changes listability under all of
them. They passed no media and left `["show"|"movie", id, "lists"]` stale, which
is the one List Surface no prefix reaches (the tmdbId sits in the middle). A
CSV-seeded create meanwhile fanned out to ~1000 invalidations.

`invalidateListSurfaces` now takes **no argument** and matches that family by
shape with a predicate. Correct for every writer, cheaper than the largest of
them, and it deletes the tv→show mapping the module had no business re-deriving
(the read hook owns it; a future `book` type would have silently mismatched).
The compatible-picker scope needed no handling either — it is a prefix-child of
`["lists"]` and always was, so the explicit per-media call was a provable no-op.

**If you write a cache-invalidation test, seed the real read hook's key.**
Asserting `listSurfaceKeys.detail(7)` equals `["list", 7]` proves only that the
same literal was typed twice, and asserting `invalidateQueries` was called with
a key proves only that the function calls what it calls. Neither could catch a
surface the contract *forgot*, which is the entire failure mode. The tests now
seed the surfaces at the keys the read hooks use and assert
`getQueryState(key).isInvalidated` — that form would have caught the miss above
on the first run. Gotcha when seeding: `useSetListMembership`'s optimistic
`onMutate` reads `previous.lists.map(...)`, so a picker page seeded as
`{ seeded: true }` throws inside `onMutate` and the mutation never succeeds —
seed picker pages as `{ lists: [...] }`.

**There is a conformance ledger for exactly this and I missed it first time.**
`src/server/list-summary/invalidation-conformance.test.ts` pins which write
functions must call `invalidateListSummaries`. Adding the call without adding
the entry means deleting the call later breaks nothing. Its third case asserts
`actions/listCollaborator.ts` must *not* invalidate — still true, because the
action is a transport over the core, but the rationale comment needed
qualifying. Check that file whenever you touch a List write.

**Accessibility (AC3).** A Sonnet audit against the house style (counted, not
guessed: `hitSlop={8}` on small icon buttons, `{6}` on compact rows, role+label
on every icon-only control) produced 10 findings; 9 applied. The two that were
real bugs rather than conformance: a failed comment post was **completely
silent** — no `onError` anywhere in `addComment.mutate` — and the per-comment
delete button never became `disabled` while its own delete was in flight. The
delete fix uses a per-row pending **set**, not a screen-wide `isPending`; the
screen-wide form is the #534 shared-observer trap and would disable every
comment's delete while one is deleting. Left alone deliberately: no confirmation
on Decline, since declining is reversible (the owner can re-invite).
