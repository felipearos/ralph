## What shipped

- **Server:** `GET /api/v1/users/upcoming` (`withAuth("read")`, member id from the session only), backed by the shared query `src/server/queries/upcomingEpisodes.ts#getUpcomingEpisodesFromFollowedShows`.
  - Reads followed TV shows only, capped at 100 (newest follows first).
  - TMDB revalidate is 1800 s; `fetchInBatches` runs 5 shows at a time.
  - Window is UTC today−1 … today+14, compared as `YYYY-MM-DD` strings.
  - Sorted by air date, show name, season, episode.
  - Partial success at two levels: a failed show drops only that show, a failed season only that season.
  - Season fetches are skipped when `next_episode_to_air` is null and the last episode aired before the window.
  - Tests: route test plus a PGlite integration test, 12 cases.

## Key decisions

- **Home link row kept.** #842 calls Catch Up's View All the *primary* entry point, but `CatchUpRow` renders null for a caught-up member, which would leave Upcoming unreachable from Home. The spec reviewer called the row P3 scope creep; I declined and explained why in the PR.
- **Grouping happens on the client.** The server doesn't know the device time zone, so it sends a padded UTC window and the client draws the boundaries. Only non-empty groups render.
- **Web `/upcoming` untouched.** It still runs its serial loop with a 30-day horizon and doesn't filter `media_type`, so movie follow IDs reach `getTVShowDetails` there (found by the standards reviewer; pre-existing). Moving it onto the shared query is a worthwhile follow-up ticket, and nobody has filed it yet.
- **Duplication refactors declined.** The standards review (P2) flagged the header, card and skeleton copied between Catch Up and Upcoming, and `catchUpCard` now styles Upcoming cards. The copying mirrors Catch Up on purpose; a shared schedule-screen header or card would be a cross-cutting refactor.
