## The finding worth keeping — AC1 is unsatisfiable as written

The spec review caught it and I verified it by reading
`packages/shared/src/app-links.ts` directly. AC1 wants a test proving neither
Apple's components **nor** Android's intent filter claim any path under `book`,
`books`, `author` or `series`. Apple is fine (`{ "/": "/*/*", exclude: true }`
at `:358` plus `UNCLAIMED_SITE_ROOTS` at `:50-92`). **Android already claims
them:** it has no exclusions, so `ANDROID_APP_LINK_PATHS` (`:385-398`) is
written positively with `/[^/]+/<profile-tab>` and `/[^/]+/list/.*`, whose first
segment is anything — so `androidClaimsPath` is true today for `/book/stats`,
`/author/reviews`, `/series/shows`, `/books/movies`, `/book/list/x`. The only way
to green AC1 literally is to edit the link table, which the body's "No
association document, intent filter or link table entry changes" forbids.

What keeps those paths in the browser is `appLinkTarget`, not the filter:
`isMemberSegment` (`:183`) rejects an unclaimed root, so the target is `web` and
`redirectAppLink` (`mobile/lib/app-link-intent.ts:67`) routes to `/web-link`.

**Posted the amendment as a comment, not a `set-section`**, per the human-edits
guardrail: #3044 is `ready-for-agent`, so its `Acceptance criteria` are not mine
to replace. Note that `triage/validate.ts` does **not** mechanically refuse that
set-section — the fence here is prose only, so it is on the iteration to honour
it. The comment gives the replacement wording verbatim for the coder to work to.
