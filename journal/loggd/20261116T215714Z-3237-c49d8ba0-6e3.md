## Why I did not split it

Seven acceptance criteria, under the 8-box threshold. The surface rule is what
offered it, and on a careful reading it does not fire either: the body names
**web** and **api** ("the mobile API's Book Log reads"), which is two, not three.
Nothing in the edit set runs in `mobile/`.

The mapper bounded the change at about 4-6 files, all web, concentrated in one
component, `src/app/mod/_components/ContentPreview.tsx`. Both drawing criteria live
in that one file AND are governed by one conformance key, so two children would
collide in the same file and race for the same ratchet allowance. There is no seam
to split on. A split here would have produced children that each need the parent's
text, which the role's rules refuse.

Since the ticket is `ready-for-agent`, I could not rewrite its `Acceptance criteria`
(human-edits-first rule). Everything went into one amending comment and no section
or label changed.

## The finding worth remembering: the ratchet has no "add a key" escape

`review-visibility-conformance.test.ts:358` allows
`ContentPreview.tsx#ReviewPreview: 1`. My first draft told the coder they could
either keep the scan in `ReviewPreview` or add a new key to the baseline's "not a
visibility question" group. **Both are wrong**, and I verified it in the file:

- `allowanceFrom` (`:524-526`) gives a key the base branch never had an allowance of
  `0`, so "the baseline never grows" (`:826-837`) reds on any new key. The file names
  that exact move as the case it exists to catch (`:700-703`).
- `ReviewPreview`'s allowance is exactly `1`, and criterion 2 needs `media_type` and
  `external_id` for the comment row too — a second scan.

The passing move is `MOVED_SCANS` (`:471-521`), and it is **three** edits, not one:
add the new declaration's key at `1`, add the `MOVED_SCANS` entry inheriting from
`ReviewPreview`, and delete the `ReviewPreview` key. There is also a second path
that touches the test not at all: `ReviewCommentPreview` already selects
`review_id`, so it can compose `ReviewPreview` for that id and leave the key alone.
The comment gives both and recommends the first.

Three test files also pin `ContentPreview.tsx` **by path** —
`review-visibility-conformance.test.ts:358`, `comment-visibility.test.ts:15-21` and
`read-boundary-conformance.test.ts:184` — so the new loader must stay inside that
file or each allowlist needs a new entry. That is in the comment too.
