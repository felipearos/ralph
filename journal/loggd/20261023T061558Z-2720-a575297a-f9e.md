## What landed

`submitOnboardingStepAction` now parses its `submission` with
`onboardingSubmissionSchema` — the same schema `POST /api/v1/onboarding`
already used — so the username (30) and display-name (50) caps are the
server's rule rather than one transport's. The parse sits *after* the rate
limit and `requireMember`, so an unauthenticated caller still gets the
membership refusal rather than a validation one. Refusal string matches the
route's `"Invalid input"`. Success path unchanged; neither cap was changed
(the ticket forbids it).

## Key decisions

- **AC4 is wrong as written, and the PR body says so.** It asks that a
  30-character username still be accepted. `validateUsername` caps usernames
  at `USERNAME_MAX_LENGTH = 20`
  (`packages/shared/src/account-credentials.ts:30`, reached via
  `profile-write.ts:201`), so a 30-char username never could be accepted. The
  test pins the real property instead: the 30-char username is refused by the
  sign-up rule's own message, not by the new parse — which proves the parse
  widened nothing. Found by the delegated executor, verified by direct probe,
  and independently confirmed by the spec reviewer.
- **The spec axis found AC5 unpinned.** The ordering (membership refusal wins
  over the validation one) was already right, but no test would have caught
  the parse moving above `requireMember`. Pinned in `ba70d00dd`; a mutation
  check showed exactly that one test failing under the move.
- **Declined, with reasons in `.ralph/logs/phase-2720-review.md`:** two
  test-duplication smells the reviewer itself called borderline/style; the
  bare cap numbers and the duplicate wire-contract type (both fixes would
  live in `src/lib/onboarding-submission.ts`, which the ticket forbids
  touching); and an extra valid-username test already covered by the
  profile-step describe.
