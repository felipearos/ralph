## What landed

Two holes in what the gated-off modes serve.

1. `/api/musicbrainz/image-proxy` fetched any `*.archive.org` host
   (`web.archive.org` included) and passed the upstream `Content-Type`
   through, with no timeout and no byte cap. It now matches the visitor's URL
   against the exact two shapes its one producer emits — a
   `coverartarchive.org` `/release/<mbid>/<image>` and the
   `archive.org/download/mbid-<uuid>/<image>` item path — comparing the
   **origin** (so a port or embedded credentials are refused), https only, no
   query or fragment. The upstream type must be in an image allowlist (415
   otherwise); the served type is the allowlist's value, with `nosniff`; 10 s
   abort; 12 MiB cap (413 on a declared length, an errored stream past it);
   refusals carry `no-store`.
2. `API_ROUTE_OWNER` in `src/lib/media-types.ts` classifies the 19
   directories under `src/app/api`, `MODE_API_ROUTE_BASES` derives their
   bases, and `isDisabledPath()` reads both via `DISABLED_PATH_BASES`, so
   `/api/musicbrainz`, `/api/itunes`, `/api/hardcover` and `/api/books` 404
   while music and books are off. `src/proxy.ts` gained the matcher literal
   that gets an anonymous production request to the gate.

## Key decisions

- API bases are deliberately **not** in `MODE_ROUTE_BASES`: that record also
  feeds `isModeRoute()` and `subdomainTargetForPath()`, so an API path there
  would claim a mode's subdomain.
- `next: { revalidate: 86400 }` was dropped from the upstream fetch — Next
  disables the Data Cache when a `signal` is present, and the abort timeout is
  an acceptance criterion.
- Redirects are still followed: the allowlist fences the visitor-supplied URL,
  and `ia*.us.archive.org` is not enumerable. Documented in the route and the
  PR body.
- The drift test's enabled-base assertion started page-only (a deliberate
  decline: the live modes' API bases carry matcher entries for the per-IP rate
  limit) and was **reversed** on Codex's one P2. Filtering
  `RATE_LIMITED_PREFIXES` out is exactly what the decline was protecting, so
  `b45e6a75` derives the enabled modes' API bases from `MODE_API_ROUTE_BASES`,
  drops anything under a rate-limited prefix, and asserts the rest is skipped
  anonymously — re-enabling music or books now fails until the matcher's
  `/api/:base(itunes|musicbrainz|books|hardcover)/:path*` entry loses them.
  `expect(bases.length).toBeGreaterThan(enabledBases.length)` stops the API
  coverage going vacuous. Mutation-checked.
- **Filed #2802** (`needs-triage`, `security`, parent #2686): the standards
  review found `/api/search?type=albums|artists|tracks|books` still calls
  Spotify and Hardcover with no enabled-mode check, which a prefix gate cannot
  fix. Out of scope here; the registry comment points at it.
