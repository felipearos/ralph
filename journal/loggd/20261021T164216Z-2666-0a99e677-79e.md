## What I decided

The frontier offered #2666 as oversize on a **lexical false positive**: `isOversize`
counts 5 criteria (under the 8 threshold) and then matches three surfaces — `web`,
`mobile` (the body says the module is "shaped like mobile's Library Write") and `db`
(the regex `/\bmigration\b/` matching the staffing group name `poster-read-migration`).
By Loggd's written rule it is a one-surface, five-criteria ticket.

It is nevertheless genuinely oversize by the spirit of the bucket, and the mapper is
what settled it: ~22–26 files, a new client module plus a patchable client store, four
components of 460–790 lines (`UserActionBar` 788, `ShowPoster` 708, `MoviePoster` 470,
`EpisodePoster` 463), and a nine-file server cleanup. Not implemented at all at
`origin/main`.

**The seam is NOT the surface seam.** The three dead writers and the `unfollowShow`
rewire live entirely under `src/server/**` and have **zero production callers**, so they
are independent of the client work in either order. That gave:

- **#2715 `dead-writers`** — delete `followShow`, `markEpisodeWatched`,
  `getBatchShowScores`; `unfollowShow` → `setShowFollowCore`. `Blocked by: None`.
- **#2716 `poster-read-migration`** — the module, the patchable `ShowStatusContext`, and
  all four callers. Carries the parent's blockers #2664, #2665.

**Why not three children.** A module-and-action-bar child followed by a three-posters
child is the other natural seam, and I rejected it on a tool constraint rather than on
taste: `add-blocker`'s `issue` must be a real number (`triage/plan.ts:178` + the parse at
`:307-313`), and a `## Blocked by` written into a `create-issue` body cannot name an
issue the same plan is about to create. The posters' child would therefore carry no
edge to the module's child, and a coder could take it first and find no module.

**Groups.** Tree #2653 already uses `poster-read-migration` (#2663 rulo-wip, #2664) and
`title-action-bar` (#2665). #2716 touches `ShowPoster`/`MoviePoster`/`EpisodePoster`,
which #2663 is in right now, so it shares `poster-read-migration`; it also touches
`UserActionBar`, but #2665 is its blocker, so the two can never run concurrently.
#2715's file set (`showFollow.ts`, `episodeWatchStatus.ts`, `scoreAggregate.ts` and
their tests) is disjoint from everything in the tree, so it got its own group.

## Review findings I acted on (two rounds, `ralph-review-spec`)

Round 1 and round 2 both found real defects, all of them inherited from the parent's
prose rather than introduced by the split:

- "`followShow` appears nowhere under `src/`" can never pass: `unfollowShow` contains it
  as a substring, and `unwatchedEpisodes.integration.test.ts:118` /
  `upcomingEpisodes.integration.test.ts:134` define unrelated local helpers of that name.
  Reworded to exports/imports/calls with the exemptions named.
- The test-deletion list was wrong in three places: `scoreAggregate.deletion.integration.test.ts:109`
  is one assertion inside a case that stays, `title-detail-conformance.test.ts:96` is a
  forbidden-bindings entry rather than a case, and deleting `member-refusal.test.ts:37`
  would drop that module's suspended-member refusal check (re-pointed at `unfollowShow`).
- `invalidateCatchUp` already runs inside `setShowFollowCore` (`showFollow-write.ts:47-52`),
  so "invoked exactly once per unfollow" is untestable in `showFollow.test.ts` where the
  core is mocked. Split into: the action must not call it, and `showFollow-write.test.ts:80`
  keeps the once-per-unfollow assertion.
- Child B originally demanded "no local follow state" while follow is not one of the
  module's kinds — unmeetable. Follow now stays on `useShowActions` explicitly, and a
  new criterion covers the real hazard the reviewer found: a title-scope watched write
  carries a follow side effect (`ShowPoster.tsx:268-270`, restored at `:253-256` and
  `:275-276`) that a conforming implementation could silently lose.
- The undo toast, which the parent gives the module, had no criterion in either child.
  It has one now, naming both existing undo paths.
- "The Storybook stories still render" has no check any loop can run (no Storybook
  Vitest project; browser tests need Playwright). Became a typecheck criterion.
- `useShowActions` also owns `handleUnauthorized` (`:66`) and `trackEvent`; neither child
  said that behaviour survives. Added.

Coverage was checked clause by clause in both rounds: nothing from the parent's five
criteria or its `## What to build` is dropped.
