## The fact the whole ticket turns on, established by execution

**PostgREST answers `200` for an RLS-closed table.** Measured against
production, five `curl`s:

| case | status | body |
| --- | --- | --- |
| `profiles.patreon_access_token` — readable, 38 rows | `200` | `[]` |
| `report.id` — RLS admits **no** anonymous rows | `200` | `[]` |
| `notification.id` — RLS admits **no** anonymous rows | `200` | `[]` |
| `profiles.no_such_column_xyz` | `400` | `42703 column does not exist` |

RLS *filters rows*; it does not fail the request — the same property
`security/README.md:87-90` already states. So a `200` proves **the column
exists and `anon` holds SELECT on it**, nothing more, and a `400` is ambiguous
between "revoked" and "gone".

The first version classified on status alone, which was wrong in **both
directions at once**:

- an RLS-closed table read as an open exposure — so the verdict could never go
  green after the #675/#676 *policy* fix that the audit document explicitly
  offers this command as the proof of;
- a credential column **renamed in production** read as CLOSED, i.e. the tool
  would report safe precisely because it had lost track of the credential.

Columns are now classified from three inputs — status, existence in the
deployed schema (from `information_schema.columns` over the privileged
connection, never inferred), and whether the table admits any rows anonymously
— into `open` / `latent` / `closed` / `inconclusive`. `latent` does not fail
the run; `inconclusive` does, and so does a run that measured nothing.

**Do this measurement before designing any probe against PostgREST.** Three
minutes of `curl` against a table you already know is RLS-closed answers what
no amount of reading the code will.

## The review finding I'd most want the next iteration to internalise

Both axes independently caught that my own commit message was false: *"deleting
either `process.exitCode` assignment turns all four red"*. It is true of the
`catch`-path line and false of the success-path one — all four spawn tests fail
inside `requireEnv` or on the first catalog query, so **none of them ever
reaches** `process.exitCode = report.verdict.exitStatus`. Deleting that line
turned **zero** tests red. It is the exact line whose absence is the regression
the test file's own doc comment says it exists to prevent.

The cause was a methodology error worth naming: **I mutated both assignments
together and read "4 failed" as covering both.** Mutating a guard at the same
time as another guard tells you the pair is covered, not the member. Mutate one
thing at a time.

Pinned now with a TypeScript AST walk over the source, the idiom
`src/app/auth-connection-conformance.test.ts` already uses, and the test says
out loud that it proves the wiring is *written*, not that a run *behaves* — the
success path needs a live database and a live PostgREST, so a spawn test cannot
reach it.

## Mutation testing changed the code three times, twice by deletion

- A test asserting the error path redacts the connection string **passed with
  `redactedString` deleted** — postgres.js reports an unreachable host as
  `connect ECONNREFUSED 127.0.0.1:1`, which carries no credential, so the
  assertion could never fail. Deleted, with a comment saying why, rather than
  kept as decoration.
- A backscan rejecting `ALTER DEFAULT PRIVILEGES` and a negative lookahead
  beside it were **mutually redundant** — removing either alone kept tests
  green, which briefly read as "both are dead". Removing *both* is what showed
  the behaviour was real. Kept the lookahead, deleted the backscan.
- `verdicts.length === 0 ||` was genuinely dead: `[].every()` is already `true`.

## The finding I got the label wrong on, and why the label mattered

The grant comparison first reported four tables (`import_job`,
`idempotency_key`, `push_receipt_ticket`, `push_target`) carrying "undeclared"
table-wide `anon` grants. The standards axis pushed back and was right: they
**are** declared, by
`ALTER DEFAULT PRIVILEGES … GRANT ALL ON TABLES TO "anon"` in the baseline — a
standing rule, one per client role.

Two things were wrong with "undeclared". It is false, and it would have meant
**one line of permanent residue for every table this project ever adds**, which
is how a diff stops being read. Parsing those rules as coverage takes the
production residue from 9 to **0**.

Stated correctly the finding is stronger, not weaker: the declared default is
*grant everything to everyone on every future table and let RLS sort it out*,
so a new table is anonymously reachable the moment it exists unless a policy
says otherwise. That is the property that made Finding 1 possible, and it is
#677–#681's territory.

## Other things the axes caught that a local gate never would

- The document said counts were taken with `count(patreon_access_token)`; the
  code deliberately does `count(*) … where <column> is not null`, because
  `count(<column>)` counts non-NULLs and reported `is_draft = 1402` on a table
  holding five drafts. The doc was describing the bug that had been fixed.
- "88 parsed" where the tool reports **95 declared against 95 deployed**.
- `comparePolicySets` matches schema+table+name+command and **not** the
  `USING`/`WITH CHECK` expressions, so "matches version control" means the
  policy *set* matches. Now said plainly, which also weakened — correctly — the
  justification for substituting the local harness for criterion 2's
  ordinary-member probe.
- Grant keys were `schema.table.grantee` joined by `.` and split by `.`; a
  table quoted `"foo.bar"` reported table `foo`, grantee `bar`.
- `compareGrantSets` inferred its schema scope from the deployed rows, so a
  legitimately empty deployed set would silently drop every declared grant
  instead of reporting them all missing. Scope is a parameter now.

## Gotchas for the next iteration

- **`bunx eslint scripts/` has 2 pre-existing errors** in
  `backfill-avatar-variants.ts` and one other. Not yours; check the filenames
  before chasing them.
- **A `*/0` inside a block comment closes the comment.** Cost one typecheck
  cycle writing about `Content-Range`.
- **TS7 requires `NODE_ENV` in a `spawnSync` `env` object** even when the child
  never reads it. TS5.9 does not. Both must pass.
- **`ralph/inspect.sh` review stages survive a session teardown** — they are
  `nohup`ed and detached. After a recovery turn, check
  `ps -eo args | grep '^bash ralph/inspect.sh'` before re-running: mine were
  still going and finished normally.
- **The opencode sandbox denies compound bash.** `&&`, `|`, `;`, `>`, `$(…)`
  are all refused, and two earlier review runs burned their whole budget on
  refused calls. Put the allowed-command list *in the brief*; both passes then
  ran clean.
- **Scope the review brief or it will re-read the baseline SQL forever.** The
  first spec pass spent **30.2M** input tokens, most of it re-reading
  `20260705000000_prod_schema_baseline.sql`. The second, with "do NOT read the
  migrations" in the brief and one commit named, spent **412k** — 73× less, for
  a better report.
- **`db:check-production-migrations` went red on build 1005 and green on 1006,
  same commit.** Production-side connection failure on a check that reads
  `drizzle/`, which this branch never touched. Same shape as #651/#654/#671.
  Re-run before believing it.
- **The pre-merge hook blocks on Vercel**, which fails on every PR from the
  overdue invoice. `LOGGD_MERGE_RED=1` is the documented override and it wants
