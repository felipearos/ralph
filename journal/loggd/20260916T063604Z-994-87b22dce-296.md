## The thing that actually cost this iteration an attempt

The first load run died at the seed:

```
Refusing to seed non-local database host "db.ovbox….supabase.co".
```

**A loop worktree's shell already carries Doppler's remote `DATABASE_URL` and
`SUPABASE_*`.** `scripts/seed-e2e.ts` and the Playwright *setup* project both
read that env with `??=` semantics, so `.env.test` never overwrites what is
already set — the remote values win. The fix is one line, and it has to come
*before* anything reads env, not after:

```bash
set -a; . ./.env.test; set +a
case "$DATABASE_URL" in *127.0.0.1:54322*) ;; *) exit 1;; esac
```

This is the same failure mode as the `test:e2e:local` leak in PR #965. **The
guard rail is what saved it** — without `seed-e2e.ts` refusing non-local hosts,
this would have seeded the cloud dev project from a loop worktree. Worth knowing
that the guard is load-bearing for the loops, not just for humans.

## What changed in the runner versus the previous entry's recipe

The handed-off `/tmp/loadrun-994.sh` used `CI=1` to buy the production build.
That works, but `CI=1` also makes `playwright.config.ts` build **Storybook**
(`storybook build && vite preview`) as a third webServer, which is minutes of
work irrelevant to this spec. This iteration built and started the app by hand
instead and let `reuseExistingServer` (true off CI) pick it up:

```bash
export NEXT_DIST_DIR=.next-test NEXT_EXPOSE_TESTING_API=1
node node_modules/.bin/next build && node node_modules/.bin/next start -p 3000
```

`--retries=0` still matters and was kept explicitly: the previous entry is right
that retries would launder the failure count the AC asks for.

Teardown was also changed to **leave the Supabase stack running**, because it was
already up when the iteration began. Stopping something you did not start is how
the next build finds a half-torn-down stack.

## The waiting, which was most of the wall clock

From 05:38 to 06:12 UTC the agent was never idle: #1610, then #1611
(`ralph/876-…`), then #1612 (`main`), then #1613 (a Mergify queue build). The
window that finally opened was three minutes wide and the run fit in it. The
pattern that worked was a **wait-then-`exec` script** — poll the Buildkite REST
API for running/scheduled/creating builds, and `exec` the load runner the moment
the count hits zero, so the runner's own preflight re-checks and the race window
is one poll interval rather than however long it takes an agent to notice.

A cheaper lesson from the same stretch: `pgrep -f loadrun-994.sh` inside a
watcher whose own command line contains that string **matches itself**, so the
watcher never sees the job finish. Nine minutes went into that. Grep for a
marker the job writes (`playwright exit=`) instead of for the process.

## Honest note on what the fix is

Repeated here because it is easy to lose: the response waits remove everything up
to the refresh landing, but the residual is a **3-7 s client-side re-render**,
and against a 5 s default the top of that range still fails. The enlarged 15 s
budget is what carries the tail. The waits buy a real signal instead of a
timeout and make a mute that never takes effect fail as a mute failure — that is
worth having, but it is not what makes the test pass.
