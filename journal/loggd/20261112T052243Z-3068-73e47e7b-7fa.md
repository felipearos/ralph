## What the review stage caught — 2 blocking, and both would have cost a coder a day

Run as `ralph-review-spec` with the comment pasted verbatim into the brief (no diff exists for this
role; the brief has to BE the change). Nine findings, all acted on. The two that matter:

1. **My draft said `getGlobalFriendReviews` "needs its own guard". It does not** — it is already a
   `rankGlobalReviews` caller (`reviews/global.ts:146`). And the real trap is one I had missed
   entirely: `rankGlobalReviews` has **no media-type parameter**; three callers each push their own
   `eq(review.media_type, …)` into `extraConditions` (`global.ts:129`, `global.ts:150`,
   `community-rankings.ts:152`). Add a parameter defaulting to
   `inArray(enabledMediaTypes())` and leave those `eq`s where they are and you get
   `inArray(tv,movie) AND eq(book)` → **a preview viewer asking `/api/v1/reviews/friends?media=books`
   silently gets nothing.** The comment now leads with this and asks for a test that a preview
   viewer still receives book rows on all three reads.
2. **Three of the surfaces the ACs name cannot reach "all media" at all**, so a test there passes
   with the guard removed and fails AC6. The Feed Section passes `{ media: "showsOrMovies" }`
   (`api/v1/feed/sections/route.ts:53`) and the web's `readWebFeedSectionPlan` is typed
   `"tv" | "movie"` (`feed/feed-section-plan.ts:61-64`); the web Home loaders are typed
   `"movie" | "tv"`. **AC2 has to be tested at the query level.** The comment now lists which
   surfaces can ask for "all" (the two mobile API routes — AC1's and AC3's own paths, which my
   draft never named — plus `/api/v1/reviews/friends`, web `/reviews` and `landing.ts`) and which
   cannot.

The other seven: a fourth `getProfileTags` caller I had missed
(`[username]/(profile)/tag/[tag]/reviews/page.tsx:102`, which an *optional* argument would leave
unguarded with no type error — so the comment now says make it required); my `SQL[]` widening
reason was wrong (`extraConditions` already holds `feedReviewHasContent(): SQL<boolean>`);
`buildMediaCondition` is a model to copy, not drop-in (`MediaFilter` vs `RankingMediaType`, which
includes `"album"`); my `showCount` test reasoning was wrong (one book review *does* move the
count, since `tmdb_id = 0` adds 1 — seeding two is still worth it because the counts drift);
`:233` not `:232`; cite the body not AC4 for the count-2 edge; and the landing-cache "outlive the
deploy" sentence was unsupported, so it is demoted to a PR note.

## Evidence worth keeping (verified twice, at `origin/main`)

- **`enabledMediaTypes()`** (`src/lib/media-types.ts:284-286`, `ENABLED_SUBDOMAIN_TARGETS =
  ["shows","movies"]` at `:323`) is the web/constant answer; **`viewerMediaTypes(browsableTargets)`**
  (`src/lib/api/media-mode-scope.ts:177-181`) is the mobile-API/viewer-derived one. The v1 wrapper
  already hands `browsableTargets` to every handler (`src/lib/api-utils.ts:398-411`) — both tag
  routes receive it and just do not destructure it.
- **The rankings cache is keyed on `(mediaType | null, limit, excludedUserIds)` and nothing
  viewer-specific** (`community-rankings.ts:16-21`), `revalidate: 600`, tag `community-rankings`.
  This is *why* the cross-media set must be a constant: a viewer-derived "all" either leaks across
  viewers or forces the browsable set into the key. Remember this for every future
  "scope a community read by the viewer" ticket.
- `getCachedLandingShowcase` (`landing.ts:74-76`) is a **second** `"use cache: remote"`,
  `revalidate: 300`, with **no `cacheTag`** — unreachable by `invalidateCommunityRankings()`.
  A latent moderation-invalidation gap, unrelated to this ticket.
- **`getProfileTags` is `tag`-driven with two LEFT joins** (`profile-tags.ts:59-72`), which is what
  makes the zero row work. Adding the media predicate to the review join yields a book-only tag
  **at zero** instead of omitting it — AC4's first clause fails while its last still passes. The
  omission needs a tag-row condition (`HAVING`/`NOT EXISTS`), and a bare `HAVING count > 0` breaks
  the zero row. Easiest trap in this ticket.
- `tmdb_id = 0` is the non-TMDB sentinel (`media-types.ts:20-22`, written at
  `externalStatus-write.ts:212,260`), so `showCount: COUNT(DISTINCT review.tmdb_id)`
  (`community-rankings.ts:196-197`) is off by exactly 1 for any number of book reviews.
- **There is no friends'-reviews read on the web Home.** AC2's "the web Home's friends' reviews" is
  a wording slip; on the web they are reached only through `/feed`. Left as a PR note, not a body
  edit.
- Dead cross-media reads that still count books: `getCommunityStats` (`global.ts:46-83`, importer
  `CommunityStats.tsx` is never rendered) and `FeaturedReviews.tsx:139` (imported only by its
  story). AC5's "named with the reason it is safe" cases.
- No migration: `mediaTypeEnum` has `"book"` (`schema.ts:23,28`), column at `:543`,
  `tag`/`review_tag` at `:1006-1033`.
