## Decisions, and where they came from

Felipe owned the product call. Underneath it were three mechanical questions that would
have left the module unfinishable, and child 1 settles them:

1. **A patch is dropped against a baseline, not against itself.** The obvious rule ("drop
   the confirmed patch when a prop answers the scope differently") reverts every write on
   the detail shells and in the Watchlist grid, because the props there carry the
   *pre-write* value — `ShellHandoff.tsx:106`/`:120` pass a literal fixed at click time,
   and `WatchlistGrid.tsx:448-450` re-merges the page-load `statuses` per chunk. With no
   server refresh on watchlist set or title-scope watched, nothing corrects it. The
   module records the server answer per scope as of begin and drops only on a move away
   from that baseline.
2. **The patch store sits above any one provider**, per-session, cleared on sign-out;
   `getStatus(tmdbId)` keeps its signature and answers with the patched title-scope
   entry, so the id-only callers see patches unchanged. The pre-existing tv/movie id
   collision is explicitly out of scope.
3. **The caller passes its current follow value into the write.** The module cannot read
   it — `handleFollowClick` leaves the context stale and a loaded detail page has no
   provider — and hands it back beside the post-write `isFollowing`.

Cited rules in the plan's `decisions`, all three resolving at `origin/main`:
`CONTEXT.md#Server Writes` → Library Write ("No call site picks its own invalidations."),
Viewer Media State ("Every scope answers for itself and never borrows another's",
"Absent is not false: it says the read has no answer").
