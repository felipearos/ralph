*schedules* an Import Run (#655's stateless execution) and outlives the request.

## For whoever takes #659, #660 or #661

- **Add your source to `runImportSource` and return the same `ImportRunOutcome`.**
  Nothing else in the lifecycle changes. The switch throws for an unwired
  source on purpose — reaching it is a bug, not a member's bad file.
- **`claimed_at` is the fence, and you must carry it.** Guarding a write on
  `status = 'processing'` alone is NOT enough: a recovery leaves the row in
  exactly that state, so a hung worker coming back to life matches and
  overwrites the run that replaced it. `heldClaim(job)` is the predicate; use
  it for every write you add after a claim.
- **`releaseImportUpload` must never null `storage_path` for a delete that did
  not happen.** Both ways of getting that wrong were live in the first draft:
  a null store short-circuiting `store?.remove(...)`, and `storeFromSupabase`
  discarding the `{ error }` the Supabase SDK returns instead of throwing.
  Either one forgets where a live object is, which orphans it permanently —
  no code left knows the path, so even fixing it later cannot clean up.

## The thing that would have shipped a cross-account read

**A new `public` table without `ENABLE ROW LEVEL SECURITY` is a hole, and
`drizzle-kit` never generates the statement.** The first draft of 0027 missed
it. Both review axes found it independently and the spec axis wrote out the
whole chain: any authenticated member hits PostgREST with the publishable key,
`update import_job set storage_path = '<victim>/<victim job>', status='queued'
where id = '<their own job>'`, waits ten minutes for the sweep, and the
**service-role** worker downloads the victim's export into the attacker's
account — bypassing the bucket's folder policies, because it is the service
role. `admin.ts`'s own doc comment promised "the worker passes a `storage_path`
it read off the job row", which is only a promise if the row is trustworthy.

The precedent is written into `drizzle/0019` and `0024` in prose. Read one of
them before adding a table; the rule is not in CLAUDE.md.

- **`drizzle/meta/*_snapshot.json` is write-denied at the permission layer.**
  Standards review's P2 was "0027 has no snapshot, so the next `generate`
  re-emits the table" — correct, and not fixable by this loop. `db:generate`
  is *already* broken on `main` (`0023/0024 ... pointing to a parent snapshot
  ... collision`), which is why 0027 is hand-written at all. Documented in the
  migration header and the issue comment; the repair wants its own ticket.
- **`bun lint` has 15 pre-existing errors on `main`**, all in
  `mobile/lib/notification-routing.ts` and `mobile/lib/push-targets.ts`. Proved
  it rather than assuming: `git worktree add /tmp/lintbase origin/main
  --detach`, symlink both `node_modules`, run lint — identical 15. Two minutes,
  and it is the difference between "my diff broke lint" and "it did not".

## Not fixed, deliberately

- **The run's writes are still not transactional** (inherited verbatim from
  #655, whose journal already flagged it). It matters more here: standards
  review's P2 is that two concurrent runs on one job can leave duplicate
  `review` rows, because `review` has no unique constraint. The claim fence
  narrows the window to "a worker hangs past the 15-minute stale lease", which
  `maxDuration = 300` makes unreachable on Vercel but not under `next start`.
  Still nobody's ticket.
- No job-list UI. `listImportJobsForOwner` exists and is unused; #663
  (notify on finish) is the natural home for surfacing history.
