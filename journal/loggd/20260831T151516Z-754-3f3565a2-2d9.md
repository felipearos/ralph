## How to diagnose Buildkite without being able to read Buildkite

The #687 journal established that `BUILDKITE_API_TOKEN` is withheld, `doppler`
is forbidden, the build page 403s anonymously, and therefore the `ci-debugging`
skill is unusable by this loop. All still true. What worked instead:

**1. Find a commit whose diff cannot fail.** This is the whole trick. A
journal-only commit is a natural control: one markdown file, no code, no
config. `main` had two of them, `f63bd0e2` and `aef57b5a`, and both are red. You
do not need the log to conclude "not the diff" when the diff is 145 lines of
prose. **Look for the control commit before you try to read the log.**

Build #1132 was still `pending` when I found it. Waiting ~6 minutes for it to
finish was the single highest-value thing this iteration did, and it cost
nothing since there was no other work.

**2. `docker logs buildkite-agent` gives you job shape.** No commands, no
output — but PID, start, finish and exit status per job, which is enough to
count jobs and time them:

```
#1130  upload 17s/0   sentinel 20s/0   40s/EXIT 1     6m38s/EXIT 1
#1131  upload 18s/0   sentinel 29s/0   5m27s/0        7m32s/EXIT 1
#1132  upload 18s/0   sentinel 23s/0   5m49s/0        7m32s/EXIT 1
```

Two conclusions fall straight out. The long job fails every time, **twice at an
identical 7m32s**, which reads deterministic rather than flaky. And the ~5.5m
job that passes on #1131/#1132 occupies the same agent slot that died at 40s on
#1130 — so that one is `quality`, failing early there and passing since, which
leaves **`e2e`** as the persistent failure. Inferred, not read: the labels are
not in the log. Say which it is.

**3. `.buildkite/pipeline.yml` explains the blast radius.** `e2e` self-skips on
commits that cannot affect the web app (#448), but **a push to `main` runs
everything regardless of paths**. That is why a journal-only commit on `main` is
red while a journal-only PR would be green — and it is why this was invisible
until the loop started pushing journal commits to `main`.

## Ruling things out is cheap; do it before hypothesising

Each of these was one command, and each killed a plausible story:

- **The reboot.** Host booted 08:35 -04 (12:35 UTC), both containers restarted
  with it, `RestartCount=0`. Tidy story — and wrong: #1128 passed at ~13:25
  UTC, *after* the reboot. I had the correlation half-written before checking
  the timestamp. **Check the boundary before you write the causal sentence.**
- **Stale dind state.** `buildkite-dind`: 0 containers, 0 volumes, three default
  networks, all 13 Supabase images present, Docker 29.7.1 healthy.
- **Disk.** 380G free.
- **Live port collision.** Nothing on 3000/3500/54322.

`supabase_db_loggd` and `supabase_storage_loggd` volumes do sit on the **host**
daemon with nothing attached — but Buildkite's stack lives inside
`buildkite-dind`, which is empty, so they belong to the GHA runner or a local
run. Noted in #754 as worth one look, not asserted as the cause.
