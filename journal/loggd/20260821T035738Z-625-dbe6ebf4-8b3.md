**The migration is hand-written, and here is the tooling fact that forced it.**
`drizzle-kit generate` prompts on a table rename, and answering the prompt
(down-arrow, enter, piped in) then **crashes**: `TypeError: Cannot read
properties of undefined (reading 'columns')` at `preparePgAlterColumns`. The
rename plus the nullability change together are what breaks it. So:

- The SQL is hand-written, in the style of `0020_list_membership_identity.sql`.
- The **snapshot** was obtained by re-running generate and answering **"create
  table"** instead, then keeping only `0023_snapshot.json` (renamed to `0022`)
  and discarding the drop-and-recreate SQL it emitted. That works because a
  snapshot describes the *end state*, not the path, and both answers reach the
  same end state — verified statement by statement against the generated SQL:
  same constraint names, same CHECK text, same index.
- **Without that snapshot the next `drizzle-kit generate` anyone runs would diff
  against `0021_snapshot.json`, which still describes `push_subscription`, and
  emit a destructive duplicate.** Both review axes found this independently. If
  you hand-write a migration, you still owe the repo a snapshot.

**`ALTER TABLE ... RENAME TO` renames the table and nothing else.** The unique
constraint, the foreign key, the primary-key index and the sequence keep their
`push_subscription_*` names while `schema.ts` implies `push_target_*`. Four
extra `RENAME` statements fix it. Nothing breaks without them — `ON CONFLICT
(endpoint)` infers by column, not by constraint name — which is exactly why it
would have gone unnoticed until a future migration tried to drop a constraint
that does not exist under that name.
