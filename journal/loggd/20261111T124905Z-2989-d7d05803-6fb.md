## What the spec reviewer caught — one P1 that reversed my headline answer, one P2 that reversed my strongest advice

Both upheld after I checked them in the code myself.

1. **P1 — I had the reachability backwards.** I wrote that an `x-media-mode=books` cookie is reachable on production. It is not. `getServerMediaMode` (`src/lib/media-mode-server.ts:17-20`) reads the **host first** and only falls through to the cookie when the host carries no subdomain; `detectMediaMode` (`src/proxy.ts:10-13`) does the same. On production every rendered page is on `shows.` or `movies.`: the disabled subdomain is 301'd (`media-mode-redirects.ts:97-104`) and the bare apex unconditionally (`:106-110`), with only `LOCAL_HOSTS` (`:30-40`) exempt. Because `getSubdomainMediaMode` is therefore non-null there, `reviews/page.tsx:50` takes the **locked** branch too, so `parseMediaFilter(media)` is unreachable in production as well. The honest criterion-6 answer is **latent on production, live on subdomainless hosts** — localhost, `*.loggd.local`, and the `*.ts.net`/tailnet address `dev-review` serves on. That last point is why the ticket is still worth doing: dev-review runs against production data.
2. **P2 — my reason for "do not gate `buildMediaCondition`'s `all`" was wrong, and the right reason points the other way.** I claimed an enabled-only `"all"` would drop books from Media Mode Preview grantees' mobile reads, undoing #2936. It would not: the Media Mode Scope gate maps `all` to `mode: null` (`src/lib/api/media-mode-scope.ts:45-50`) and only checks a mode the request names (`:187-197`), so a grantee reaches books through an explicit `media=books`. The v1 diary already gates `"all"` enabled-only (`users/diary/route.ts:107` → `buildDiaryConditions` → `diary.ts:80-82`). The real reasons: gating `"all"` there changes four v1 routes' responses, which criterion 7 fences by path; and gating the **explicit `"books"` branch** is the change that *would* break grantees, because a v1 `media=books` passes the scope gate and lands in `buildMediaCondition`.
3. **P2 — the `diaryMediaCondition` pattern I told the coder to copy lives in a fenced file.** Criterion 7 fences `src/server/queries/{activity,diary,stats,profile-reviews,userStats}.ts`, so `buildProfileReviewConditions` (`profile-reviews.ts:28-32`) is off limits. The unfenced seams for the reviews gate are `reviews/page.tsx:50-52` and `ReviewsContent.tsx:50-61`, which holds the built `conditions` array before the query.
4. P3s folded in: `media-filter.test.ts:9` tests `mediaFilterToMediaType`, not `buildMediaCondition` (reference dropped); the adult-gate tests are a viewer *precedent*, not an already-built other-member-versus-self matrix (`ReviewsContent.adult-gate.test.tsx:117,129`).

The reviewer's brief was the comment text pasted verbatim with "the worktree contains none of this" stated up front, plus a "check every file:line" instruction.
