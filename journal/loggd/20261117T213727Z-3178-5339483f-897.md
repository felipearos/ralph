## What shipped

`GET /api/v1/books/authors/<id>` now takes optional, combinable `sort`
(`popularity|newest|oldest|az`), `genre` and `decade` from the shared Book
Browse Catalog. All three are validated before any provider call and applied
by the provider across the whole bibliography, combinable with `role`.
`getAuthorBooksPage` gained a `filters` argument; its two static GraphQL
strings became one builder over the existing `BOOK_SHELF_ORDER` table and
`pushBookFilters`. With no sort and no filter the query and variables are
byte-identical to before, so the existing Author page is untouched.

Files: `src/lib/hardcover.ts`, `src/app/api/v1/books/authors/[id]/route.ts`,
`packages/shared/src/book-author.ts` (doc only), both test files, `CONTEXT.md`.

## Key decisions

- `sort=rating` is refused although the catalog names it: the issue lists four
  sorts, and Browse's rating order needs its `ratings_count >= 25` floor,
  which a bibliography has none of.
- No current-year ceiling on `newest` (unlike Browse's popular grid), so an
  announced edition can lead the page. Deliberate.
- `roles` and their counts stay bibliography-wide; filters narrow `books` only.
- Dropped standards P3s: extracting the third copy of `singleParam` into
  `api-utils` (touches two routes this ticket does not own) and reshaping
  `getAuthorBooksPage` into an options object (other callers).
- Dropped spec suggestion: a full-text comparison of the unfiltered query
  against the base query — whitespace churn for no extra guarantee.
- `CONTEXT.md`'s Book Browse Catalog entry gained the Author's-page clause.

## What the next iteration should know

This ticket cost **eleven shepherding rounds over ~9 hours** for a change that
was code-complete and green by midday, and every one of them was the host, not
the diff:

- **Two `CONTEXT.md` conflicts.** Sibling PRs (#3601, then #3217/#3625) each
  edited the *same parenthetical* of the Book Browse Catalog entry. Both
  resolved by keeping every clause in main's order. If your ticket touches
  that entry, expect to rebase: it is the hottest line in the repository right
  now.
- **One `CHECKS_TIMEOUT` dequeue** (14:23Z) with **no failed job**: Mergify's
  1-hour clock runs from `queued_at`, and the three agent slots were saturated
  the whole window. Requeueing into that would have burned the last round for
  a certain second timeout, so it went `RETRY_LATER` instead — four times, as
  the queue stayed three-to-five cars deep.
- **Measure the concurrency hold, not idle slots** (learning
  `ci-wait-times-out-behind-host-build-queue`, revised in round 6): a build
  whose only log entries are two short upload jobs is *starved* behind
  `loggd/quality` / `loggd/e2e`, even when slots look free.
- **A force-push re-enqueues a dequeued PR by itself.** `.mergify.yml` holds a
  dequeued PR out "until its branch is updated"; round 8's rebase was that
  update, so Mergify took it on its own and §5.6 correctly said not to
  enqueue again. Re-read the labels before posting `@mergifyio queue`.
- Rounds spent against §5.6's cap: 2 of 2 (the dequeue, then the
  rebase-and-re-verify). The merge happened with no round left, on a wait
