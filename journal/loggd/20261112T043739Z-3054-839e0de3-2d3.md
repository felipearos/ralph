## The bucket was a false positive, again

Second `oversize` false positive in two non-staffing units (#3044 was the first).
#3054 has **7** acceptance criteria, not more than 8, and names **one** surface:
the v1 API. Its body says "The web is not touched" and no mobile client code
changes. Neither limb of this project's oversize rule fires.

Nor is there a seam. AC5 ("owner or accepted collaborator … for reads and writes
alike") spans the reads and the writes together, AC6 and AC7 run across every
route, and the whole point of the ticket is one atomic gate — half a gate is a
leak, not a slice. The spec reviewer was asked directly whether it saw a seam I
missed and said no. Left whole, left `ready-for-agent`, no body section touched
(the ready-ticket rule sends amendments to a comment).

## The finding worth keeping — the body states the rule twice and they disagree on `track`

- As a **deny-rule**: "a List whose List type belongs to a Media Mode the viewer
  may not browse". `track` belongs to no Media Mode
  (`LIST_TYPES_BY_MODE`, `src/lib/media-types.ts:289` → `music: ["album",
  "artist"]`), so a `track` List **stays found**.
- As the **named derivation**: `viewerListTypes` (#2964), whose own doc comment
  says "`track` is in no mode's List types, so no viewer gets it", so a `track`
  List **goes not-found for everyone, owners included**.

`album`/`artist` are not in question — `ENABLED_SUBDOMAIN_TARGETS` is
`["shows","movies"]` (`media-types.ts:323`) and nobody holds a music preview, so
both readings agree they go not-found, which is a real consequence of this ticket
and a thing a coder should not patch around. `track` alone is the fork, and it is
not hypothetical: the web serves track Lists (`src/app/[username]/list/track/[slug]/layout.tsx`)
and `users/member-lists/route.ts:133-134` applies no `listTypes` filter when
`media` is absent, so the index would keep listing an owner's track List whose
detail read then answers 404.

Recorded as an open question addressed to Felipe, **not** as a verdict of
`needs-info`: every one of the seven criteria is testable without an answer, and
the ticket names the helper explicitly, so the build instruction is the
derivation with no `track` special case either way. An instruction naming the
exact helper beats prose that plainly did not consider that value — but the
consequence is a question Felipe should see before it ships, not one to discover
in review.

## Mapper evidence now on the issue (so a coder does not re-derive it)

- The rule is **wholly unimplemented**: nothing under `src/app/api/v1/lists/[id]/`
  reads `browsableTargets`, `viewerListTypes` or `LIST_TYPES_BY_MODE`. So this was
  never a closure.
- **No shared guard exists, and none can be added.** Every by-id route delegates
  to a core the web also calls (`readListPage` ← `list-page-gate.ts:31,71`; the
  write cores ← `server/actions/list.ts`, `listComment.ts`, `listCollaborator.ts`,
  `queries/list-curation-reads.ts`). "The web is not touched" is therefore the
  constraint that decides the whole shape of the work.
- The "mobile API" is `src/app/api/v1/`. There is **no** `src/app/api/mobile`.
- `comments/[commentId]` DELETE **ignores the List id in its path** (`:25` passes
  only `commentId`); the gate there must resolve the List from the comment.
- The audience not-found is `code: "NOT_FOUND"` / 404 everywhere, but the `error`
  **string** is per-route (five different ones) — AC1's "same status and envelope"
  is per-route, not one global string.
- `list_type` is written only at create (`list-write.ts:278`), so a type lookup
  before a core has no check-then-act gap.
- No schema change, no migration, no Playwright: `list_type` already exists
  (`schema.ts:592`, enum at `:118`). Ordinary coder work, not `ready-for-human`.
- There is **no** integration test under `lists/[id]` today. The model to copy is
  #2964's `users/likes/route.integration.test.ts`.
