The Expo app's List screen now draws a book List as a grid of covers — title,
author, curator's order, ranks when the List is ranked, paging unchanged. The
server side was already in place from #3057, so the diff is mobile-only: new
types, a `BookListEntryCell`, a branch in the List screen, and tests. Four
commits, the last two being the review fix (wrap the book branch in `BookGate`
itself rather than a copy of it) and a test pinning the chrome that gate sets.

so show and movie Lists are untouched.

## Key decisions

- **Criterion 5 reads the client's settled Media Modes (`useBookGate`), not the
  server's 404.** Mapping a 404 to the not-found screen would have changed what
  a *refused show* List draws, which criterion 6 forbids. Stated in the PR body.
- **The long-press quick-actions sheet ships early**, because it is built into
  `BookCard`. Spec #3027 otherwise owns marks and Fade Watched, and this grid
  mounts no Book Viewer State provider.
- **`isBookListEntry` / `entryName` live in `mobile/lib/list-entries.ts`**, not
  in `@/hooks/useLists`: every List-screen test mocks that hooks module
  wholesale, so a runtime helper imported from it is `undefined` under test.

## For the next iteration

- A first attempt drew `NotFoundScreen` inline and extracted `BookGatePending`
  out of `BookGate.tsx`. The standards axis was right that it lost the
  not-found chrome; that extraction was reverted and `BookGate.tsx` is back to
  `main`. Do not redo it.
- Any new List-screen test with a book fixture needs `Stack: { Screen: … }` in
  its expo-router mock, because `BookGate` renders one.
- `mobile/__tests__/list-detail-like-share.test.tsx` leaves a Jest worker
  hanging after it passes. Reproduced on `origin/main` detached, so it is not
  this diff — use `--forceExit` locally. Not systemic enough for a learning on
  its own, but it will waste a few minutes for whoever meets it next.
- **The merge queue, not CI, was the long pole.** CI was green on round 1
  (build 4760, no flake reds). The merge wait then timed out twice at 3600s
  each while four book-tree PRs (#3559–#3563) sat in one Mergify train; the
  train branch was building live the whole time, so the right call was to hand
  the wait back rather than requeue or block. It merged on round 3. When a
  group of sibling PRs lands together, expect the queue to serialise them and
  budget merge waits accordingly — a `queued` label plus a live
  `mergify/merge-queue/…` build is a working queue, not a stall.
