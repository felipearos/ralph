## The step attribution was wrong too, and that is the reusable part

The hand-off pinned the ~36s failure on `quality` by inspecting the agent's
abandoned checkout: `node_modules` present, no `.next`, no `coverage/`,
therefore it died before lint and the build.

**That inference cannot work.** Buildkite runs three jobs per build (`sentinel`,
`quality`, `e2e`) and the checkout at
`/data/buildkite/builds/<agent>/felipe-aros/loggd` is **per-agent, shared across
jobs** — its contents say nothing about which job last touched it. The same
journal already recorded that stale env files from old builds linger there; the
checkout state is stale for the same reason.

Timing the jobs against #917's known-good run is what actually separates them:

| job | #916 (red) | #917 (green, `main`) | #918 (green, rebased) |
| --- | --- | --- | --- |
| sentinel | 17s ✅ | 28s ✅ | 16s ✅ |
| quality | 4m19s ✅ | 4m55s ✅ | 5m06s ✅ |
| e2e | **38s ❌** | 4m50s ✅ | 5m10s ✅ |

`quality` was passing the whole time. The fast failure was **`e2e`**, whose
early commands (`supabase:reap`, `supabase start`) are precisely the ones that
collide with the shared local Supabase stack — the known
`local e2e vs runner collision` hazard, and the reason the loop never runs
Playwright itself.

## The technique that settled it: poll the agent's live process table

No Buildkite token needed, and it names the running command rather than
inferring it. Sample it on a loop for the whole build:

```bash
docker exec buildkite-agent sh -c 'ps -eo args' | grep -E '^(bun|node|supabase|apt-get)'
docker exec buildkite-agent sh -c 'grep -h BUILDKITE_STEP_KEY= /tmp/job-env-*'
```

At 15s intervals that produced an exact command timeline for #918 —
`bun install` → `supabase start` / `bun lint` → `playwright install` →
`test:e2e` alongside `mobile lint` → `mobile test` → `test:coverage` →
`bun run build` → `supabase stop`. A red build read this way tells you the
failing command in one observation.

Also worth knowing: the **step key is in the job-env file** and maps cleanly to
a job id, so `grep -l "$sha" /tmp/job-env-0*` narrows to your build's jobs and
each one's `BUILDKITE_STEP_KEY` names it. That is the identification the
checkout heuristic was reaching for, and it is exact.

## Generalise: a fast failure that alternates with a pass is contention until proven otherwise

Two consecutive journals (#653 and this one) have now recorded the same shape —
a repo-wide-looking red that was neither a break nor the standing suspect
(`db:check-production-migrations`, blamed by four journals and never once
guilty). #653 got it right and said so; #661's hand-off talked itself out of the
contention reading because 913's pass "seemed to confirm" the timing story.

The cheap control is the one that was sitting there both times: **find a build
on plain `main` and watch what it does.** If `main` is green on a real build,
the command everyone suspects is passing, and no amount of reasoning about
production state changes that.
