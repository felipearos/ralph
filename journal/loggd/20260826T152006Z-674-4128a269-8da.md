## Read this first: `supabase start` proves nothing about `supabase db reset`

The previous hand-off left three hypotheses and could not read the Buildkite log.
None of them was needed. The failure is deterministic and reproduces in one
command:

```
Resetting local database...
Could not find the supabase-go binary required to bootstrap the local database.
```

Both CI agents install the Supabase CLI as a **standalone release binary** —
a single ELF at `/usr/local/bin/supabase`, baked by
`.buildkite/agent/Dockerfile`'s `ARG SUPABASE_CLI_VERSION=2.111.0`. That binary
can `supabase start`, which the e2e job has always proved. It **cannot**
`supabase db reset`: the reset is delegated to a sibling `supabase-go` helper
that only the npm package ships. `bunx supabase@2.111.0 db reset` — same
version — replays all 13 migrations fine.

`security/harness/global-setup.ts` preferred PATH over `bunx`, on the reasoning
that using the binary the job already proved works keeps the step honest. That
reasoning is the bug. It killed the `e2e` job **64 seconds in**, one command
past `supabase start`.

## How to read a red Buildkite job without the API token

Three techniques, in the order they pay off. The first two are from #661's
journal and they work; the third is what actually ends the argument.

| step | command | what it gives |
| --- | --- | --- |
| per-job timings | `docker logs buildkite-agent \| grep -E "Starting job\|Exit Status"` | which job failed and how long it ran |
| live command timeline | `docker exec buildkite-agent sh -c 'ps -eo args'` on a 10s loop | the exact command in flight |
| **run the job's own commands** | `docker exec buildkite-agent sh -c 'cd /data/buildkite/builds/home-loggd-N/felipe-aros/loggd && …'` | **the actual error text** |

The third one is the one to reach for earlier than I did. The agent's checkout
survives at the failing sha with `node_modules` and the minted
`supabase/signing_key.json` still in place, so the job's opening commands can be
replayed verbatim. That turned ~20 minutes of inference into one observation.

Build 924's shape, for calibration: sentinel ✅ 20s, quality ✅ 3m37s,
**e2e ❌ 64s**. A `quality` that passes while `e2e` dies fast is not the
repo-wide block two previous journals chased.

**The contention reading was checked and ruled out**, so do not re-run it:
`main`'s build 922 was green end to end at 14:42, `buildkite-dind` had zero
containers, and 924 failed on a completely idle runner. #661's "fast failure
that alternates with a pass is contention until proven otherwise" is good advice
and it did not apply here — the tell is that this one did **not** alternate.

## A hazard ruled out that is worth knowing about

The Buildkite agent's environment carries a **production** `SUPABASE_DB_URL`
(`postgresql://postgres.liuuaowngrfjgsfndeeu:…`), and the Supabase CLI binds
some `SUPABASE_*` env vars to flags. If `db reset` honoured it, the e2e job
would have been replaying migrations over **production** on every build.

Probed directly with a bogus loopback value: it does **not**. `supabase db reset`
targets the stack named by `supabase/config.toml` and answered
`supabase start is not running`. No exposure. Recording it because the next
person to read that env var will have the same jolt.

## The first fix was wrong, and both review axes caught it

Round one derived the pin from `supabase --version`, reasoning that the reset
should run under the CLI that started the stack. On this desktop PATH is
Homebrew's **2.75.0** — the version this repository has *already recorded* as
unable to `db reset` at all (it fails on the ES256 signing key
`supabase/config.toml` pins). It would have fixed CI by breaking the laptop.

The shipped answer is one constant, `SUPABASE_CLI_VERSION` in
`global-setup.ts`, with `.github/workflows/ci.yml` moved off `version: latest`
onto the same number, and a new assertion in `scripts/buildkite-pipeline.test.ts`
holding all three equal to the agent's `ARG`. The sentinel runs it on every
build, so the next drift names itself.

**Generalise:** "use the same tool the surrounding job uses" is a good instinct
that fails whenever the tool is a *family* of installs with different
capabilities. Pin, and assert the pin.

## Two other findings worth the diff

- **`expectWriteDenied` accepted a witness that could not bear on the write.**
  It took an `unchanged` row; for a denied **INSERT** that is no evidence at all,
  since a row the write never touched is unchanged whether the forgery landed or
  not. The helper's own error message *instructed* maintainers toward that
  useless remedy. The witness is now a union — `unchanged` for UPDATE/DELETE,
  `absent` (counted privileged either side) for INSERT — and all four
  forged-insert assertions carry one. Today they all get an explicit `42501`, so
  the path is dormant; the point is that a sibling ticket cannot silently turn a
  successful forgery into a passing denial.
- **`reports.security.test.ts` blamed the wrong sibling ticket.** Its header said
  the two staff reads pass "only because `profiles` is world-readable" and that
  #675 would break them. Checked against the baseline: `report_select_mod`'s
  subquery is narrowed to `profiles.id = auth.uid()`, so it reads the caller's
  own row and **#675 leaves these green**. **#678** — moving `role` into
  server-only storage — is what breaks them. A wrong pointer in a header is worse
  than none; it sends the next ticket looking for a regression that is not there.
