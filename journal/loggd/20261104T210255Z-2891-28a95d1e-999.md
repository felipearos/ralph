## Three facts the next agent should not re-derive

1. **Every authenticated `/api/v1` request is a Bearer request.** `withAuth`/`withOptionalAuth` (`src/lib/api-utils.ts:193`) go through `requireMemberForRequest`, which reads only the `Authorization` header; the web's authenticated reads use the cookie path. `CrewPicksManager.tsx:46` fetches `/api/v1/shows/search` from the web but anonymously. Consequence: on `/api/v1/users/me` there is nothing to key on, which is why #2895 needs no predicate and is independent of #2894.
2. **The override must read the header, not tag the identity.** `resolveShowAdultContent` takes `Pick<User,"id">`, and every caller hands it the plain user object (`member.member.user`, `(await getViewer())?.user`, `authenticateRequest(…).user`), so a tag on `ActingMember` never arrives. Dozens of call sites also reconstruct a viewer as `{ id: … }` on BOTH transports, so any default for an absent tag is wrong for half of them. #2894 settles on `await headers()` and names the two constraints: the `!user` guard must precede the header read (the `"use cache: remote"` landing path at `src/server/queries/landing.ts:74-75` reaches the helper with a null viewer and `headers()` throws there), and direct-call tests must mock `next/headers` in all three states.
3. **A pile of existing v1 tests assert the opposite of the new rule.** `src/app/api/v1/browse-adult-gate.test.ts` signs in with `Authorization: Bearer test-token`, not a cookie, so its opted-in cases must flip — as must the web-vs-v1 equivalence suites, whose "both transports answer the same" claim no longer holds for an opted-in viewer. #2894 lists them and requires the PR body to account for each. The suites that mock `viewerAllowsAdultContent` outright (`movie-page-adult-gate.test.ts:53-61` and two others) are not evidence either way.

## The review earned its cost twice

Two `ralph-review-spec` passes, and the first draft would have shipped three impossible tickets.

- **Pass 1** killed a premise I had written from the mapper's report: I claimed a web client component fetches `/api/v1` "with the cookie session". It fetches it anonymously, because that route is `withOptionalAuth` and Bearer-only. Two whole criteria hung off that error — a child asking for cookie-session behaviour on a Bearer-only route, and a "these tests pass unchanged" list naming a Bearer test. It also found that `await headers()`, which I had mandated, throws in every direct-call unit test and inside a `"use cache"` scope.
- **Pass 2**, on the rewrite, killed the replacement mechanism: tagging the transport on the resolved member cannot reach the helper, and the "three synthesised `{ id }` sites" I had listed are actually dozens. It also caught that `ProfileFormData.show_adult_content` is a required boolean always filled by `profileFormFromRow`, so #2895's "the form carries no `show_adult_content` key" was unmeetable without changing the core the ticket forbids changing — reworded to "carries the stored value rather than the patch's".
- **#2897 exists because of pass 2.** `mobile/lib/query-persistence.ts` busts its on-disk cache on the account id alone, so an upgrading member's first frames can still be adult posters cached under the old build. Neither the body nor the brief mentions it.

**Lesson for this role:** a mapper's report is evidence, not fact. Both passes' most expensive findings were wrong premises I had copied from it without checking the wrapper the cited line sits inside.
