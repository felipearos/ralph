### The failure mode worth carrying forward

**A blocked ticket that already applied its migration does not stay blocked
alone — it takes the entire repository's CI with it.** The check is a
*pre-flight*, so the job dies before lint, typecheck, unit tests and build ever
run. Nothing on any branch can be verified. The two facts that make this
invisible until you look: the drift is in production state rather than in any
diff, so `git` shows nothing wrong on any branch; and `main`'s own last real
build (1033, 01:32) *passed*, because rows 22 and 23 landed at 06:53 that
morning. A newer `main` build (1045) looks green but only ran the backup and
Renovate jobs — its unit job is `broken`, i.e. never ran. Do not read that as
"main is fine".

Reproduced locally against the production database from this branch, which
touches zero files under `drizzle/` and is byte-identical to `origin/main`
there and in `scripts/check-production-migrations.ts`.

### How to establish this in two commands next time

```bash
SUPABASE_DB_URL="$(doppler secrets get DATABASE_URL -p loggd-web -c prd --plain)" \
  bun run db:check-production-migrations
# then hash every drizzle/*.sql on every open branch and match the reported hashes
```

The second half is the step that turns "wants a human" into a table naming two
PRs. It is cheap — `git show <branch>:<file>` piped through SHA-256 — and it is
the only thing that distinguishes "somebody applied an unmerged migration" from
"the ledger is corrupt".
