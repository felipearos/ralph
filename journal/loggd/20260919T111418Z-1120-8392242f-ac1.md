## The design decision worth arguing with: the follow-back state lives in the query cache

The web answers "do I already follow this person?" by fetching the viewer's **whole** following set, and only when the bell page holds a `new_follower` row (`NotificationBell.tsx`, `loadNotificationData`). Mobile cannot afford that: `useUnreadCount` polls the same endpoint every 60s with `limit=1`.

So `GET /api/v1/notifications` now answers `followedBackUserIds` — the subset of the followers **named by the returned page** that the viewer follows. `filterFollowedUserIds` short-circuits an empty candidate list without a query, so the badge poll costs exactly what it did.

The client half is the part worth arguing with. `NotificationFollowBack` holds **no** follow state. The follow mutation already writes optimistic state into every cached list carrying it (Members directory, Network); the bell's array is now a third such cache, patched in `onMutate`, rolled back in `onError`, settled in `onSuccess`. That buys three things a `useState` would not: the flip survives FlashList recycling the cell; the Notifications screen and the Activity tab agree instantly because they share the query; and the rollback can be **narrow** — one boolean per cached notifications query, for this member only — where writing a whole captured response back would also undo a dismissal that landed while the follow was in flight. The directory rollback beside it already makes exactly that argument; I had to change the delegated version, which snapshotted the whole response, to match it.

`["notifications"]` is deliberately **not** in `invalidateFollowScopedQueries`. That is not an omission: a refetch there would produce the right answer on its own and make every optimistic assertion pass with the optimistic code deleted — the trap the #1118 journal names.

## The finding I accepted, then found unreachable, then found reachable again

The spec axis reported that `disabled={isBusy}` on a Pressable nested in the row's Pressable falls through to the row and navigates, because React Native's Pressability returns `!disabled` from `onStartShouldSetResponder`. True in general. I removed `disabled` — and then **mutation-tested the removal and the mutant survived**: the optimistic patch replaces the button with "Following" in the same press, so a busy button is never rendered and the state is unreachable. So I deleted `isBusy` entirely and said so.

The second spec pass then found the state *is* reachable, by a different route: any refetch of the notifications query — pull-to-refresh, focus refetch, the invalidation a mark-as-read on another row fires — lands the server's pre-follow answer on top of the optimistic patch while the POST is still open, and the row goes back to offering a button whose press the mutation lock then silently drops. The fix is to read the in-flight request as well as the cache (`isFollowing || isBusy`), which is *not* what `disabled` would have done.

The generalisable part: **a mutant surviving tells you your test is weak or your code is dead, and those are different conclusions.** I took the second and was wrong. What settled it was a test that drives the reachability claim directly — press, then `refetchQueries` while the request is open — and that one fails against the mutant.

## A test that passed alone and failed in its own file

That refetch test asserted synchronously and was flaky: green run alone, red in the full file, green again after I added a `console.log`. The state settles across more than one commit, so the sync assertion races it. `waitFor` fixed it and is still discriminating — without the in-flight read the row reads "Follow back" forever, since the POST never resolves, so the `waitFor` times out. Four consecutive full-file runs green afterwards. **A sync assertion straight after an `act`-wrapped refetch is a race; the fact that it passes in isolation is not evidence.**
