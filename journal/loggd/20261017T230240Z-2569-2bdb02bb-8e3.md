**What shipped.** `src/server/auth/apple-revocation.ts` builds an ES256 client secret with node:crypto, exchanges the client's Apple authorization code at /auth/token, and revokes the refresh/access token. The v1 delete-account route calls it before deleteAccountCore when the account has an apple identity. A failure goes to Sentry and an Axiom warn, and the deletion still goes ahead. The shared deleteAccountSchema gains an optional appleAuthorizationCode field. The APPLE_SIGNIN_PRIVATE_KEY, KEY_ID and TEAM_ID env vars are optional (env.js, .env.example, ARCHITECTURE.md §22).

**Key decisions.**
- Used the authorization-code design: the server never stores an Apple token, so the client supplies a fresh code at deletion time. The client id stays dev.loggd.app, as the spec says.

This stops a code from another Apple user revoking that user's token. Replied on the thread.
