## The actual bug, and why every local gate lied

`emailRedirectFor` (`src/server/auth/account-creation.ts:143`) reads
`env.NEXT_PUBLIC_SITE_URL` **at call time**, and
`src/server/auth/account-creation.test.ts` never mocked `~/env`. So the
assertion "sends a native caller to the app's own HTTPS callback" was reading
whatever the ambient shell carried:

- **Locally**, `ralph.sh` starts the iteration under Doppler, so the var was
  `https://loggd.dev` and the assertion passed.
- **In CI**, the Buildkite `quality` step runs with **no application env at
  all**. The `?? origin` fallback took over and the link came out
  `https://loggd.test/...`. Red.

**Generalise this: §4 tells you to run the gate bare *because you already have a
real environment*, and that is exactly what makes your local `test:coverage` a
weaker check than CI's.** Any suite that reads ambient env passes for you and
fails there. The reproduction that finally worked, and which is worth reusing:

```bash
env -i PATH="$PATH" HOME="$HOME" TERM=dumb CI=true \
  ACTION_RESULT_BASE_REF=origin/main CONFORMANCE_BASE_REF=origin/main \
  NODE_OPTIONS=--max-old-space-size=6144 bun x vitest run --coverage
```

It reproduced CI's failure in 86s against CI's 90s. **Run it before believing a
green `bun run test:coverage`**, at least whenever a diff touches `src/env.js`
or anything reading `env`.

The fix mocks `~/env` with a mutable `mockSiteEnv` (the `mock` prefix is
required — vitest hoists `vi.mock` and refuses other outer references), resets
it in `beforeEach`, and adds the `origin`-fallback and the no-destination arms,
neither of which had coverage.

## How the failing CI command was identified without `BUILDKITE_API_TOKEN`

Extending #656/#657's technique, because durations alone were ambiguous — the
`quality` and `e2e` jobs both take ~5m here, so "which job failed" is not
answerable from `docker logs` timings:

- `docker exec buildkite-agent sh -c 'for f in /tmp/job-env-01*; do grep -hE
  "BUILDKITE_(STEP_KEY|BUILD_NUMBER|BRANCH)=" "$f" | tr "\n" " "; echo; done'`
  identifies **every live job at once**, which disambiguates two same-length
  jobs on one build.
- Then poll `docker exec buildkite-agent ps -eo etimes,args` every 3s and keep
  the last command seen before the agent logs the non-zero exit. That is how
  `bun run test:coverage` (dying 90s in) was named, and later how build #884's
  `quality` was watched all the way through `build` → `build-storybook`.

Both files vanish when a job ends, so you must catch it live. Command *output*
is still unrecoverable locally.
