**What landed.** One answer and one rendering rule for the Expo app's book
routes: may this viewer browse Books (from the account's preference as read in
this app run), and undecided → a neutral wait, yes → the screen, no → the app's
ordinary not-found screen. Placed at the root of the book route tree, so a shut
gate issues no book read at all.

**Key decisions.**
- `pickableTargets`, never `modes`. `modes` is the member's effective Settings
  choice, so it would close the gate on an account that may browse Books but
  has chosen only shows.
- The gate sits at `mobile/app/book/[id]/_layout.tsx`, not a new
  `app/book/_layout.tsx`: the root layout registers the screen by the name
  `book/[id]`, so adding one would rename the route.
- The shut gate carries its own chrome (`Stack.Screen`, `title: "Oops!"`) and
  takes the placing route's `screenOptions` to restore. Moving the chrome out
  of the layout also fixed `useBookGate` being called twice per render, where
  the second `refetch()` cancelled the first's request in the same commit.
- Three findings deliberately not fixed, each argued in the PR body: the
  fail-closed teardown on a failed refetch, the Android push animation
  (unreachable from the gate; AC7 pins `+not-found`), and `previewAnswered`'s
  `dataUpdatedAt` heuristic — pre-existing in a shared hook, worth its own
  ticket.
