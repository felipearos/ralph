## READ THIS FIRST: `git checkout -- <file>` during mutation testing ate three
## uncommitted fixes, and the tests still passed

rafa's #1072 entry warned about exactly this and I did it anyway, one step
removed: my mutation loop restored each mutation with
`git checkout -- src/server/queries/friendsActivity.ts`, which restores from the
INDEX — so it reverted the three uncommitted review fixes living in that same
file alongside the mutation. I only noticed because a newly added test failed
with "expected watched, received reviewed": the fix it was written for had
silently vanished. Had that test not existed, the PR would have shipped the diff
I believed I had written, minus three changes, with a green gate.

**The rule that actually works: commit before you mutate, never during.** A
mutation loop and uncommitted work must not share a file. I now commit the fix,
then mutate, then `git checkout --` is safe because the index holds the fix.

## The second lesson: mutation-test the assertion, not just the guard

Four of my own assertions did not survive mutation, and three were the kind that
look thorough and prove nothing:

1. **The empty-state test asserted on the pending render.** `renderStrip()` then
   `waitFor(() => expect(mockGet).toHaveBeenCalled())` — the call fires long
   before the promise resolves, so the strip was still `isLoading` and rendered
   `null` for that reason, not because the read answered empty. Removing the
   `friends.length === 0` guard entirely left the test green. Fixed by flushing
   with an `act`-wrapped `setTimeout(0)` BEFORE asserting absence.
2. **The season SQL assertions read clause text only** (`"review"."season_number"
   = $`). `eq(review.season_number, tmdbId)` renders the identical string. Fixed
   by pulling `dialect.sqlToQuery(clause).params` and asserting the bound value
   is `3`, not `42`.
3. **The rating fix's WHERE-clause half had no coverage at all.** The row fixture
   returns its review row whatever the predicate says, so restoring
   `isNotNull(review.content)` kept all four ranking tests green. The fix is half
   in the clause and half in the loop; only the loop was tested. Fixed with a
   clause assertion (`not.toContain('"review"."content" is not null')`, plus
   is_draft/is_hidden still present).
4. The first attempt at mutation #1 mutated the wrong function — the string
   `isNull(review.episode_number),` also appears in `getPopularReviewsFromFriends`
   200 lines earlier, and `str.replace(old, new, 1)` took that one. A mutation
   that "passes" should be treated as suspect until you have seen the diff.

## The real bug the spec reviewer found, older than this branch

`getFriendsActivityForShow` scanned reviews with `isNotNull(review.content)`, then
used that same map as the rating source for watch-status friends — under a comment
promising a rating "even without content". The log sheet writes a score with a
null body, so every rating-only friend was filtered out at the database and no
later logic could recover them: no stars on the movie or show strip, while the
season and episode strips (which scan scores separately) showed them. Dropping the
filter and deciding "reviewed" from the content — the shape my season read already
had — fixes the acceptance criterion and the web's `FriendsActivitySection` too.
It is strictly additive: a score-only friend with no watch status still does not
appear, because the reviewer loop now skips them and nothing else picks them up.

Related and NOT fixed, out of scope: `getFriendsActivityForShow` has no
`isNull(review.season_number)` predicate despite its comment claiming "not
episode/season reviews", so a season review counts as a title review there. My
season read pins both columns; the title read's widening is pre-existing web
behaviour and changing it belongs in its own ticket.

  season page reuses the SHOW-level read, i.e. every season of a show answers the

  `enabled` so it never fires.

  mirroring `media-people.ts`, `useFriendsActivity`, `FriendsActivityStrip`, and
