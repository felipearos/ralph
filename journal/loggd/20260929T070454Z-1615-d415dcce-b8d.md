# 2026-09-29 — #1615 Show detail renders one responsive tree

**Outcome: merged.** PR #1788, merged 2026-09-29T07:03:02Z, issue #1615 auto-closed. Two CI rounds: red on Buildkite 2574 (Playwright), green on 2579.

**What changed.** `src/app/show/[id]/ShowContent.tsx` returned two trees — an `lg:hidden` mobile one and a `hidden lg:block` desktop one — each placing the server-section props, so Friends Activity, Reviews and Lists+Similar sat in the DOM twice at every width and `castSection` appeared in the desktop tree plus the mobile Cast tab. It is now one tree that switches layout at `lg`, each section placed once. New `ShowContent.test.tsx` counts placements and pins the mobile reading order.

**Key decisions.**

1. **Flex goes on at `lg`, not off at it.** Every one of these sections carries a trailing `mb-8` and no top margin, and flex items do not collapse margins — so a flex column *below* `lg` would widen two mobile gaps (cast/crew pane → reviews wrapper 32→64px; reviews' inner `mb-8` → Lists wrapper 32→52px). Above `lg` flex is spacing-neutral. So the column is `lg:flex lg:flex-col`, DOM order is the **mobile** order in plain block flow, and `lg:order-1..4` restores the desktop order. A mapper stage measured those margins; that measurement is what flipped the design.
2. **Crew must stay conditional.** It has no desktop slot, so mounting it behind `hidden` would have put crew markup on every desktop page for the first time. Found by writing the test, not by reading the diff.
3. **Positioning is faithful, not merged**: `lg:relative` on the container, `lg:static` on the content div.
4. **The RSC flight payload was never doubled.** Each section is a single `ReactNode` prop, serialised once and rendered twice; the doubling was SSR HTML + hydration. This corrects the ticket's own wording and the spec reviewer's framing.
5. **Measured**: real first flush 40,077 B / 483 el → 33,281 B / 376 el (−17.0% / −22.2%); the page emitted 9 copies of its 6 sections and now emits 5. Numbers in `.ralph/logs/size-1615.md`, method and limits in the PR body.
6. **Out of scope on purpose**: the two `Backdrop`s (#1586 story 15 keeps them), the per-breakpoint hero chrome (`loading.tsx`/`ShellHandoff` mirror it, and `e2e/README.md` #317 depends on which `featured-episode` copy sorts first), `DesktopSidebar`'s `require()`s (#1604), and `ReviewsSection`'s own internal split.

**The CI failure, and the generalisable lesson.** Build 2574 failed only the Playwright job, two real tests, one root cause — and the root cause is the restructure's. Merging the two trees while leaving the hero chrome split (decision 6) means the desktop-only sidebar and hero (`hidden lg:block`, carrying `DesktopSidebar`, the desktop `SeasonsSection` and its "MORE SEASONS" button) now **precede** the mobile tab nav in document order. Nothing the phone renders changed; what changed is which copy a bare positional `.first()` resolves to at a phone viewport. `e2e/README.md`'s own ladder already says `.first()` is "only safe when the extra matches are the *same* element rendered twice" — here the extra match was a different, hidden element, so those sites were never safe.

The fix was spec-only; `src/` is untouched by it. The three tab sites took the ladder's second rung — `getByRole("button", { name: "Seasons"|"Cast", exact: true })`, since `Tabs` gives each tab a plain button whose accessible name is just its label, the role engine drops the `display:none` desktop subtree, and `exact` stops a substring match reaching "MORE SEASONS". `e2e/lists.spec.ts` (two 375px sites) was **latently** exposed to the same ordering change and passed only by luck — the desktop sidebar's `UserActionBar iconOnly` now precedes the mobile bar, and its label reads "In your Watchlist" for a watchlisted-but-unrated show — and was guarded with `.filter({ visible: true })`.

**For the next iteration.** Sibling **#1618** (movie detail) is the same shape and can copy this pattern — but audit `movie-detail.spec.ts`'s mobile `.first()` sites *before* pushing it, because it will hit this same locator class. `e2e/poster-sizing.spec.ts` is the real gate for this family: three full-page show-detail screenshots at 375/768/1280 against committed baselines, masked review columns and `maxDiffPixels: 6_500`, so a diff there is real and the fix belongs in the component — never update a baseline.
