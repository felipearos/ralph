# #684 — Password Assurance: creation, recovery, and change

Merged as #741 (`9ba125b1`). Buildkite #1027 green, including the E2E job where
the new security suite actually runs.

## The one thing worth carrying forward: probe the provider, do not reason about it

Every hard question in this ticket was a question about GoTrue, and every one of
them was answered by reading the provider's source or the running container
rather than by recalling how Supabase "works". That is the whole reason this
shipped in one pass:

- **`secure_password_change` semantics.** `internal/api/user.go`:
  `if session == nil || now.After(session.CreatedAt.Add(24*time.Hour))`. So it
  is a 24-hour recency rule, not "always require the current password". Which
  means the settings form's existing `signInWithPassword` re-verification is
  what makes the change work at all — it mints a session seconds old. Deleting
  it would look like a cleanup and would break the journey for anyone who left a
  tab open overnight. There is a comment saying so now.
- **HIBP is not reachable from `config.toml`.** GoTrue HAS the check
  (`internal/api/password.go`, `GOTRUE_PASSWORD_HIBP_ENABLED`, fail-open by
  default, message `Password is known to be weak and easy to guess…`). The
  pinned CLI does not emit it: `strings` on the 2.111.0 binary's container-env
  builder shows `GOTRUE_PASSWORD_MIN_LENGTH` and
  `GOTRUE_PASSWORD_REQUIRED_CHARACTERS` and nothing else under
  `GOTRUE_PASSWORD_*`, and `docker exec supabase_auth_loggd env` agrees. Two
  independent measurements, ninety seconds of work, and they turned "add a
  config key" into "this has to be an application control plus a dashboard step
  in the runbook".
- **`POST /auth/v1/verify` accepts `token_hash`** and answers 200 with the token
  in the body (`internal/api/verify.go` — and note exactly one of `token` /
  `token_hash` may be set). That is what let the recovery suite run without a
  mailbox.

**`docker exec supabase_auth_loggd env | grep GOTRUE_` and
`strings ~/.bun/install/cache/@supabase/cli-linux-x64@<pinned>/bin/supabase`
are the two probes.** Reach for them before believing anything about what the
local stack enforces. The CLI binary is the authority on which `config.toml`
keys exist at all — the online CLI repo paths 404 and the docs lag.

## The executor produced nothing, twice, and the failure mode is new

`ralph/delegate.sh` returned **exit 0 with an empty diff** on both rounds.
The tell is in the `.log.jsonl`: `{"reason":"length", "tokens":{"output":131072}}`
— deepseek-v4-flash spent its entire output budget on prose in a single
assistant message and never emitted a tool call. The first round read 25 files
and stopped; the second, given an explicit "stop reading, write these six files
now" continuation, did the same thing again.

This is the same shape as the #681 journal's review-stage lesson and deserves
the same rule: **exit 0 with no diff is exit 2.** Fall back after ONE retry, not
two — the second round cost 131k output tokens and produced the identical
nothing. Check `ralph/logs/delegate-*.log.jsonl` for `"reason":"length"` before
assuming the brief was at fault; a brief cannot cause an output-cap overrun, and
this brief was the same shape as the one that worked in #681.

Implementing the slice directly took about 40 minutes.

## The two review axes were worth more than the implementation

`ralph/inspect.sh review.spec` worked this time (report, exit 0) and found three
real things. `review.standards` did NOT — still running past 10 minutes with no
report, so it fell back to an in-session `Agent` on `opus` per the lineup, which
took 4½ minutes and found the bug of the iteration:

Both browser call sites guarded on `screenResponse.ok && screen.ok === false`.
That skips the refusal on a **429** — a member who has spent the shared `auth`
budget sets whatever they like — while the `fetch` and its `json()` sat inside
the form's outer `try`, so a **502 whose body is an HTML page aborted the
password change entirely**. Fail-open where it had to bind; fail-closed where it
had to yield. Both directions wrong, in code whose comment three lines above
promised the opposite.

**The generalisable lesson: when a module documents "fails open", audit every
call site for what it does with the failures, because `response.ok` is not the
same question as "did the check run".** The module was right; both callers were
wrong; the comment above them said they were right.

Also caught by the same pass and worth remembering:

- A `SyntaxError` from `JSON.parse` **embeds a window of the offending input**.
  `bodySchema.safeParse(await request.json())` on a route whose body is a
  password put that password one truncation away from the error log, under a
  comment promising no body would be logged. Parse in its own `try`.
- The conformance test's "runbook carries the production column" asserted only
  that a label appeared *somewhere* in the markdown. Editing the production cell
  from 8 to 6 kept it green — the drift detector did not detect drift. It
  compares whole rows now, and I mutation-checked it. The #683 sibling had it
  right; copying the shape without copying the assertion is how a guard rots.
- A `getPasswordError("admin1")` "ordering" test **could not fail**, because a
  sibling assertion guarantees no input can break both rules. Renamed to what it
  actually pins. Same family as #681's unfalsifiable write assertions: when a
  test claims an ordering, ask whether any input reaches the second branch.

## `password123` was in seven e2e fixtures

Adding a common-password list to `validatePassword` broke seven fills in
`e2e/sign-up-validation.spec.ts` — every one of those specs would have failed at
the new rule rather than at what it was testing. **Grep the e2e fixtures before
adding any rule that refuses a value**, and check the seeds against the real
screen while you are at it: `TestPro1234` and friends are clean, but
`testpassword123` in `e2e/rate-limit.spec.ts` has 2,600 HIBP hits.

The one-liner that answers it:

```bash
h=$(printf '%s' "$p" | sha1sum | awk '{print toupper($1)}')
curl -s "https://api.pwnedpasswords.com/range/${h:0:5}" | grep -i "^${h:5}:"
```

That probe also proves why the padding case matters: with `Add-Padding: true`
the service returns fabricated suffixes with a count of **0**, so a screen that
reads a hit off the suffix alone refuses essentially every password.

## Decisions

- **Breach screening is an application control and the PR says so.** A caller
  who posts straight to `/auth/v1/signup` is screened for length and nothing
  else until an operator turns on *Leaked password protection* in the hosted
  dashboard. The alternative — writing an inverted security test asserting the
  local stack does not screen — is exactly what `security/README.md` forbids, so
  the gap lives in the runbook's production column instead.
- **The offline list is exact-match, lowercase, and every entry is at or above
  `PASSWORD_MIN_LENGTH`**, asserted. It exists to bind while the network screen
  is failing open, which is the only reason it is not folded into that call.
- **The 429 fail-open is stated as a trade** in the runbook rather than fixed by
  making the shared bucket fail closed: a budget shared with sign-in must not
  become a lock on a member's own password.
- **`security/harness/sql.ts` is new machinery and the harness had none.**
  There is no endpoint that makes a session older, so ageing
  `auth.sessions.created_at` is the only way to stand where a stale session
  stands. It returns a row count and the test asserts `> 0` before drawing any
  conclusion — without that, the refusal being measured could be a fresh
  session's.

## Correction, written after the merge

Two things in the Housekeeping note above are wrong, and both matter to whoever
reads the next red `bun run test` here.

**The supervisor's uncommitted `ralph/ralph.sh` change is no longer
uncommitted.** A `git add -A` in this iteration swept it into #741, so the
sigil-recovery block is on `main` as of `9ba125b1`. That was not deliberate and
it is the reason to stage by path rather than by `-A` in a worktree that carries
someone else's work in progress. It is not harmful — Buildkite #1027 ran the
whole unit suite over it and passed — but it landed inside an unrelated
security PR, where nobody reviewed it as a supervisor change.

**And that change was never the cause of the local `ralph/*` test failures.**
The #680 and #681 journals both attributed them to it. With the tree now clean
at `origin/main` — the change committed, nothing modified —
`bun run test ralph/start.test.ts` still fails, and CI is green on the identical
code. So the failures are a property of THIS MACHINE, not of the diff and not of
the uncommitted state. Do not spend an iteration chasing them, and do not repeat
the old attribution: `bun run test` being red here on `ralph/{ralph,start,inspect}.test.ts`
is expected, is invisible to CI, and is still not yours.
