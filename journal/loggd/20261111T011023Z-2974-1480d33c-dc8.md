## The product question, and the two edges

The issue's title — "the server **refuses** to resolve, dismiss or reopen it again" — settles resolve-again as a refusal rather than idempotent success, so no `decisions` block was needed and none was written. Worth knowing for the next ticket in this area: **both cited precedents do the opposite.** `list-collaborator-write.ts:488-515` and `privilege-event-write.ts:361-392` re-read the row on an empty `.returning()` and report success when it already reached the requested state. The body now says "copy the fence, not the recovery" in so many words, because a coder who copies the precedent literally ships idempotent success and contradicts the title.

Two edges the issue leaves genuinely open were resolved as *keep today's behaviour* and flagged as such in the body rather than decided:

- `pending -> resolved`/`dismissed` without passing through `investigating` stays allowed — the UI offers both buttons on a pending Report today and the Resolve button has no status gate.
- `investigating -> investigating` stays a success. An earlier draft fenced `updateReportStatus` to `from pending` only, which refused the self-loop; the reviewer was right that the issue's complaint is only about *reopening a closed Report*, so the from-states are now `["pending", "investigating"]` and the self-loop is a no-op success. ## Two review rounds, both about vacuity

Round one killed the obvious test plan. `report.test.ts` mocks `~/server/db` with `select` and `insert` only (5–6), and **a `vi.fn()` chain resolves `.returning()` to `[]` whether or not the status predicate is in the `WHERE`** — so every mock-based refusal test stays green with the fence deleted, and the criterion's own mutation check stays green with it. It would have gone red against *today's* code (today never calls `.returning()`), which is exactly the kind of false confidence that gets a bad PR merged. The closed-Report refusals now have to run on `createTestDatabase` (`src/test/database.ts:581`, pattern: `list-collaborator-write.integration.test.ts`); `new PgDialect().sqlToQuery(...)` (`review.test.ts:719`) is allowed on top for the two diff-readable criteria but not as a substitute. Round one also caught that a bare `success === false` assertion passes when an unwired `requireAssuredStaff` mock returns `undefined` and the catch block converts the TypeError into a failure, and that "emits no audit event" had no positive control.

Round two caught two things I would not have seen:

1. **A `WHERE` cannot constrain the value being written.** Criterion 4 had asked for "a written status of `investigating`" pinned in the predicate, which is unbuildable. It now pins the target with `.set({ status: "investigating" })` and the from-states with `inArray`.
2. **A blanket mutation rule condemns correct tests.** "Any new test that stays green with the predicate gone must be replaced" would have failed the positive controls, every success path, and the non-`investigating` early return — all of which are supposed to stay green. Criterion 8 now names exactly which tests the deletion must redden and says the rest are out of scope for the check.

**For the next triager on this project: both of those are general.** A mutation-check criterion needs an explicit list of which tests go red, or it fails a correct submission; and a "the fence is in the `WHERE`" criterion cannot be verified by a test that mocks the db client.
