## THE FINDING THAT MATTERS FOR EVERY LATER ITERATION

**No plan that creates an issue can be applied on loggd right now.** `stepwiseRefusals`
(`triage/simulate.ts:251-293`) walks every prefix of the ordered writes and refuses when
ANY ready task in the frontier sits in an ungrouped tree. That check is **unconditional**,
not relative to the starting state — `newlyMalformed` is diffed against the start, the
`ungroupedTrees` loop right below it is not. It only runs at all when the plan contains a
`create-issue` (`created.size === 0` returns early), so comments, labels and sections are
unaffected.

Two issues trip it today, neither in any tree I touched:

## What the two review rounds caught (5 blocking findings, all real)

Both rounds ran as `ralph-review-spec` with the proposed text pasted verbatim into the brief.
Round 1 found five blockers, round 2 found four more in my round-1 fixes. The ones worth
keeping:

1. **Parent AC1 is unbuildable as written.** "appears in their Member Lists with
   `media=books`" — `MEMBER_LIST_MEDIA` is `["shows","movies"]` and the refusal is pinned
   deliberately (`packages/shared/src/member-lists.ts:122`,
   `src/lib/api/media-mode-scope.ts:209-213`, `src/lib/api-utils.test.ts:643`). Resolved by
   blocker: #3055's title literally says "Member Lists accept media=books from a preview
   viewer" and it is already a blocker of #3057. **Read the blockers' titles before calling
   an AC unbuildable** — I nearly widened the children to cover it.
2. **I invented a second 404.** My draft prescribed `bookNotFound()` for the no-preview
   refusal; #3054 (a blocker) already answers a book List as not-found by id with the same
   envelope an out-of-Audience List gets (`lists/[id]/route.ts:83-85`). Two shapes = an
   existence leak. A triager restating a blocker's contract is how contradictions get into
   a tree.
3. **PATCH was a hole the schema change opens by itself.** Widening `listItemSchema` makes
   `updateListContentSchema.items` accept books whether or not the ticket asks. And the
   refusal has to be addition-only (`list-content-write.ts:496-503, 628-631`), because
   Manage List's Save sends the complete sequence (`read-list-page.ts:229-231`) — refusing a
   stored summary makes the List permanently unsaveable.
4. **"Refused on add" is four different shapes at `main`**: refuse on the single membership
   write (`list-membership-write.ts:375-384`), partition on the batched one (`:722-726`),
   drop-unless-empty on create (`list-write.ts:216-226`), skip-as-addition on PATCH. A
   blanket "refused" AC would have been written against none of them.
5. **"Out of the page AND the counts" forces resolving the whole List**, which is not the
   shelf read's short-page contract (`users/books/route.ts:28-32`). Two guards came with it:
   resolve nothing when `limit === 0` (that call is the web book List layout's existence
   gate, `list-page-gate.ts:29-35`) and keep a placeholder on a provider failure instead of
   throwing (`read-list-page.ts:394-401`) — otherwise a Hardcover outage turns a web page
   that renders today into an error page.

Plus: `externalId` is `z.string().max(200)` while `findBook` takes a number, so a book id
must be constrained to a positive-integer string; and the Edit Read must answer summaries
and unavailable entries or the first Save deletes them.
