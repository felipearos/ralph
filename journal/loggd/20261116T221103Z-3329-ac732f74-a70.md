## The decision: not oversize

Seven acceptance criteria, under the eight-checkbox line. Surfaces named: the
mobile API and the web — and the web limb is a no-change assertion ("the web's
onboarding action keeps reading the launch constant alone"). That is two, not
three, so neither limb of the Loggd oversize rule fires. The mapper bounded the
change at 6–8 source files and about 8 test files, all server-side: one module
(`src/server/queries/onboarding.ts`) plus the v1 routes that call it. A split
along the surface seam would produce a web child whose entire content is
"nothing changes", which is not a child.

So: no split, body unchanged, stays `ready-for-agent`, amended by one comment.
Same shape as #3237, #3208, #3259 earlier today.

## What the mapper found

- Nothing of it is built at `main`. `availableTargets` is the launch constant
  for every viewer (`onboarding.ts:264`); the Media step drops `books` for
  everyone (`:299-301`); `seenTargetsFor` (`:172`) filters to enabled modes and
  `countSeenTitles` (`:194-210`) reads `watchStatus` only.
- The per-viewer helper already exists and `withAuth` already passes it:
  `browsableTargets` at `src/lib/api-utils.ts:253`, from
  `browsableMediaModeTargets` (`src/lib/media-types.ts:421`). The v1 onboarding
  routes just never read it. `src/app/api/v1/users/me/route.ts:49-54` is the
  precedent to copy.
- Books on Read/Reading live in `read_status` (`schema.ts:1633-1648`) and there
  is **no** reusable count helper — the Books count is a new query, not a
  parameter on `countSeenTitles`.
- Web and v1 share every function under the transports, so the browsable set has
  to arrive as an argument that defaults to the launch modes.

## The amendment

One added acceptance criterion plus two scope notes, posted as a comment (the
ticket is `ready-for-agent`, so its `Acceptance criteria` is not mine to
replace).

The criterion: **every** v1 route that answers the onboarding snapshot carries
the same per-viewer `availableTargets` — `GET`/`POST /api/v1/onboarding`,
`/back` and `/seen`, including `back`'s lost-race branch. The body says "the
snapshot a submission answers … follow[s] the same rules" but names no route,
and four call sites reach the same builder; threading the browsable set into
some and not the others is the bug this catches. A preview viewer who steps back
to the Media step would otherwise lose `books` from the snapshot #3333 renders.

Scope note 1: books are marked in setup through the Book Library Write path
(#3291 read, #3296 grid, #3334 tab), **not** through
`POST /api/v1/onboarding/seen`. So `ONBOARDING_CANDIDATE_TARGETS`
(`src/lib/onboarding.ts:512`, `["shows","movies"]`) and the seen-mark wire stay
as they are. The mapper flagged the absence of a books tab in the candidate grid
as a gap in #3329; reading #3334 showed it is a sibling's job, not a gap.

Scope note 2: `seenTargetsFor`/`countSeenTitles` are also called by the welcome
card (#3330 owns that count) and onboarding favourites (#3332), and by every web
path. Those behave as at `main`.

## The review stage earned its keep

`ralph-review-spec` found three real things, all of which changed the comment:

1. My first draft named only `/back`, while its own rationale ("the body names
   neither this route") applies equally to `/seen` and to `back`'s
   `snapshotAsItStands` branch. Reworded to cover every snapshot-answering
   route.
2. I wrote that `ONBOARDING_CANDIDATE_TARGETS` holds `tv`/`movie`. It holds
   `["shows","movies"]` — targets, not media types. Verified and corrected.
3. My note prescribed a default-argument design on `countSeenTitles`, which
   takes media types and cannot express a browsable-targets default. Restated as
   behaviour to preserve instead of a design, and the web import route dropped
   from the at-`main` list (it shares `advanceImportSetupStep` with the v1
   importer, so a web-only rule there is one a shared function cannot hold).
