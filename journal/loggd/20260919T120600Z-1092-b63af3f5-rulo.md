## READ THIS FIRST: a backgrounded `sleep` does not pass wall-clock time

I lost roughly twenty tool calls to this. Foreground `sleep` is blocked by the
harness, so I reached for `run_in_background: true` on `sleep 300` and polled
`ListAgents` between them. Every one of those calls returned **immediately** —
backgrounding a sleep backgrounds it, it does not make the parent wait. I read
`ListAgents` saying "started 2m ago" five times in a row and concluded the two
review subagents were hung, and was about to abandon them and self-review. Then
I ran `date`: **two minutes really had elapsed.** The agents were fine; my
clock was the broken instrument.

The thing that actually blocks is an `until`-loop on a real condition, in the
foreground, with a long `timeout`:

```bash
D=~/.claude/projects/<proj>/<session>/subagents
until grep -lq '"type":"result"' "$D/agent-<id>.jsonl"; do sleep 15; done
```

Both axes then landed within one 600s window. **Before concluding any
background work is stuck, run `date` and compare against when you started it.**
"I have made many tool calls" is not evidence that time has passed.

## READ THIS FIRST: `set-state-writes.integration.test.ts` runs on PGlite, not a database

The standards axis's strongest finding was that the new write core had no test,
and pointed at `src/server/queries/set-state-writes.integration.test.ts` — the
repo's dedicated suite for exactly this class of core (`setReviewLikeCore`,
`setShowFollowCore`, `toggleUserFollowCore`, `toggleWatchStatusCore`…), each
proving "leaves one row after the same request is delivered twice".

I nearly skipped it on the assumption that "integration test" meant a database
the loop cannot reach (`DATABASE_URL` points at a local Supabase stack that is
not running, deliberately). **It does not.** The file spins up `PGlite` — an
in-memory Postgres — replays the real migrations into it, and `vi.doMock`s
`~/server/db` to point at it. It runs bare, in about three seconds, with no
Doppler and no network. Adding `setPersonFollowCore` to it took ten minutes and
gave the only effect-level assertion on the branch.

The case that earns its keep is the role-scoped one: follow `["actor",
"director"]`, unfollow `["director"]`, assert `["actor"]` survives. Deleting
the `inArray(personFollow.role, roles)` narrowing fails it. That is the whole
new behaviour — the old action deleted with `eq(role, role)` for a single role
— and nothing else on the branch touched it.

## The design decision I want argued with

Person follow is **per credited role**: `person_follow` is unique on
`(user_id, person_id, role)`, and `checkFollowedPeopleJob` aggregates on
`(person_id, role)`. So "follow this person" is not a question the data model
answers — only "follow this person as a director" is.

The mobile screen already had role tabs. I put the button **above the tabs**
rather than in the header, acting on the active role. The alternative I
rejected: a header button doing follow-all, mirroring web's
`followAllPersonRoles`. It reads better and is a worse answer — the follow-all
the web offers is a convenience over a role list the *page* knows, and on
mobile the role list comes from the read, so a header button would either pick
a role silently or invent a notion the job has no concept of. The visible label
names the role when there is more than one; the accessibility label always
does.

If a later ticket adds #1066's item 15 (role in the route), this control gets
simpler, not harder — it already reads the active role.

## What the two axes found that I would have shipped

Both ran on the full branch diff. Six real findings between them, and the three
mobile ones were genuine defects, not style:

1. **The hydration bounce.** `if (!session) router.push("/auth/sign-in")` looks
   obviously right and is wrong here: the auth store starts
   `{ session: null, isLoading: true }`, so a signed-in member tapping Follow
   before `INITIAL_SESSION` lands gets kicked to sign-in — which returns them to
   the tabs, not the person. The repo already knew this: `CreateListButton`
   guards `!session && !authLoading` and `EpisodeWatchedToggle` carries a
   comment spelling out the rule. I had told the executor to copy
   `profile/FollowButton.tsx`, which *has the bug*, so the brief propagated it.
   **A brief that says "copy X" inherits X's defects — name the behaviour, not
   the file.**
2. **Absolute cache writes clobber a concurrent role.** The in-flight lock is
   keyed per role, so Director and Writer can be in flight together. Both
   `onSuccess` and `onError` wrote the whole `followedRoles` list — last
   response wins, and a Director failure wiped Writer's optimistic add outright.
   Fixed by making every cache write set the membership of exactly the role
   that was tapped (`patchRole`/`setRoleMembership`), success included: the
   server's list is true for the moment it was computed, not for now.
3. **Missing `expectedUserId`.** Every other viewer-scoped mobile PUT passes it
   (`useFavoritePeople`, `useFavoriteTitles`, `useProfileLists`); `api.put` has
   no options parameter at all, which is *why* it was missed — you have to drop
   to `api.request`. A token refresh across an account switch would otherwise
   write the follow against whoever is signed in now.

Both mobile fixes were mutation-tested: dropping the `authLoading` guard fails
the hydration test, and reverting `onSuccess` to an absolute write fails the
concurrent-role test. One mutant each, both killed.

## The unreachable branch, and why the fix was a type change

Both axes independently flagged `if (!result.success) return apiError(...,
"FOLLOW_FAILED")` as dead: the core either returns `{success: true, roles}` or
throws. The route test "maps a core failure to 400 FOLLOW_FAILED" fed the mock
a value production cannot produce — a test that names a behaviour it does not
have.

The tempting fix (delete the branch) does not compile: `ActionResult<T>` is a
union, so reading `.roles` *requires* narrowing. The branch was load-bearing for
the type and dead at runtime, which is the signal the type was wrong. So the
core now returns `PersonRole[]` directly, with a comment saying why: it refuses
no state, so its only failure is a thrown database error and each transport
decides what that becomes (here, `withAuth`'s 500 — which the test now asserts).
That also deleted the duplicate `SetPersonFollowResult` type the standards axis
flagged separately. **One wrong return type was generating three findings.**

`showFollow-write.ts` returns an `ActionResult` because it *does* refuse a
state (a show that has ended). Copying its signature without asking whether
this write refuses anything is how the dead branch got there.
