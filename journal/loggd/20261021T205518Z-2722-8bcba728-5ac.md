## The one correctness decision the split had to make

#2722 said the already-finished answer makes each route "report `setupStep` as
`undefined`" but never said what `advanceImportSetupStep` returns. The spec reviewer
caught that A3/A4/A7 could not all hold under the natural reading. Only one answer
works: **return `undefined`**, type `Promise<ImportSetupStepResult | undefined>`.

Both routes spread the two response keys only when `setupStep === undefined` is false
(`src/app/api/import/jobs/route.ts:69-74`, `src/app/api/v1/imports/jobs/route.ts:172-177`),
and the web uploader redirects on `typeof accepted.onboardingStepAdvanced === "boolean"`
— advanced *or not* (`useImportJob.ts:325-326`). So `{ advanced: false, completed: false }`
would still sweep a finished member to `/onboarding`, and suppressing that would mean
editing the v1 route, which #2722's own criterion 7 forbids.

Derived from code the ticket itself names, not from a product rule, so `decisions` is
empty — a citation I could not support is a refusal, and there was no domain rule in
play.

## Three breakages #2722's criteria would not have led a coder to

All three came out of the review passes and are now in #2744:

1. `src/app/api/import/jobs/route.test.ts` sends `onboarding: USER_ID` in **four**
   places — `:183`, `:218`, `:231` expect the step to advance and go red immediately;
   `:206` is the foreign-id case #2722 mentions. #2722 named only `:206`.
2. `src/lib/api/onboarding-equivalence.test.ts` stubs `~/server/db` at the chain level
   (`:100-123`) and queues exactly one profile row (`:735-736`). The new
   `onboarding_completed_at` read consumes it, leaving `answerStep` with `[]` and a
   "Profile not found" refusal (`src/server/queries/onboarding.ts:508-509`).
3. That same stub **ignores the select projection**, so it cannot distinguish a real
   guard from a vacuous one: a read that aliases the column (as `needsOnboarding` does)
   reads `undefined` off every mocked row. The proof moved into
   `src/server/imports/onboarding-step.test.ts` with a mutation check — and that file
   does not mock `~/server/db` today (`:12-18`), so the coder has to add it.

Two edges #2722 left silent are now pinned in #2744: **no profile row at all** also
resolves to `undefined` (the reading `needsOnboarding` already takes —
`src/server/queries/onboarding.ts:315-316`, "No row yet … is not a reason to gate"),
and **a throw** resolves to `{ advanced: false, completed: false }` with a logged
warning, keeping the module's never-raise contract.
