## The verdict, and why it is not a split

#2716 asked for a web Library Write module plus four callers migrated onto it. It IS
oversize — 7 certain production files (6 existing ones totalling 2,768 lines plus a new
module), 5-8 likely, ~12 test and story files, against a mobile reference that is 878
lines with an 819-line test. So the bucket was right about the size even though its
trigger was lexical again (`SURFACES` matched `web`, `mobile` from the reference path,
and `api` via `\bserver\b` in "server auto-follow"; nothing under `mobile/`,
`src/app/api/**` or `src/server/db/schema.ts` is required).

But I could not split it, because the core child would have carried an unresolved
**design** question, and a child that carries one is not ready on its own terms:

**Making `ShowStatusContext` patchable makes the patch visible to all nine of its
consumers, and four of them change a rendered set or a count** —
`useFilteredShows` (browse's watched filter, which removes shows at `:139-143`),
`useWatchedCount`, `PersonFilmography.tsx:139-141` and
`PersonMobileView.tsx:462-468`. With a watched filter on, marking a poster watched
would make that poster vanish from under the member's finger. `CONTEXT.md` settles
Fade Watched (it removes nothing) but says nothing about whether a *filter* re-runs on
an optimistic patch, and `docs/adr/` holds one unrelated ADR. That is a UX call, so by
the readiness rules it is `ready-for-human`, not mine.

So: `ready-for-agent` off, `ready-for-human` on, and one comment that both asks the
question in two concrete shapes and resolves everything else, so one reply makes the
ticket splittable.

## The five things the comment DID settle, each from a cited rule

1. **The patch layer must be keyed by Media Scope** — `CONTEXT.md#Server Writes` →
   Viewer Media State, *"Every scope answers for itself and never borrows another's"*.
   The context map is keyed by `tmdbId` alone, not even by media type, and
   `UserShowStatus` is title-level, so episode and season state has no slot at all;
   patching an episode's like under its `showId` would spill across every episode of
   that show on the liked-episodes grid.
2. **A rollback at a scope that had no answer must restore *absent*, not `false`** —
   same entry, *"Absent is not false…"*.
3. **There is no blanket client refresh** (criterion 6 was wrong) —
   `CONTEXT.md#Server Writes` → Library Write, *"It also decides, per kind, which
   surfaces refetch at once… No call site picks its own invalidations"*, plus
   `src/server/actions/watchStatus.ts:27`, *"These actions do not revalidate the title
   path themselves."* Rate, like, episode and season already `refresh()` server-side
   through `refreshQuickActionState()` / `refreshEpisodeWatchState()`; watch status and
   watchlist deliberately do not. The comment replaces criterion 6 with a per-kind table.
4. **The action bar's like must actually reach the store** —
   `CONTEXT.md#Server Writes` → Quick Action. `handleLikeToggle` (`:357-371`) never
   calls the server and says so in its own comment.
5. **`useShowActions` cannot be deleted and the trim is exactly one function.**
   Criterion 7 offered "or both are deleted"; unreachable. Three callers outside the
   ticket's four still use it (`ShowContent.tsx:91`, `SeasonPoster.tsx:165`,
   `UnwatchedEpisodes.tsx:53`), and I checked every handler: `handleLikeChange`,
   `handleRatingChange`, `handleSeasonWatchedToggle`, `handleEpisodeWatchedToggle` and
   `handleFollowChange` all keep a consumer. **Only `handleWatchStatusChange` becomes
   unused.**

## Two things worth carrying forward

**`decisions[].rule` needs a real markdown heading, and the comment must name the rule
string.** My first dry run was refused (exit 3, zero writes) on four of five citations:
`CONTEXT.md#Viewer Media State` → *"CONTEXT.md has no heading"*, because CONTEXT.md's
glossary terms are **bold**, not headings — the enclosing `##` heading is
`## Server Writes`. The validator also requires that a comment op on the unit contain
the rule string verbatim (`triage/validate.ts:785-789`), so the citation has to be
visible on the issue and not only in the plan. Use `CONTEXT.md#Server Writes` for
anything in the glossary from line 346 down.

**A split CAN be serialised without a child→child edge — use the parent's existing
staffing group.** The #2676 entry concluded that `triage-apply.ts` cannot express an
edge between two issues one plan creates (true: `add-blocker.issue` must be a real
number, only `blockedBy` may name a `ref`) and so split by a seam needing no ordering.
There is a second option it missed: the frontier offers **one ticket per staffing
group** and breaks ties on the lower number *"so an authored batch order survives"*
(`frontier/next-tasks.ts:919-935`). Creating children in order inside one group
therefore serialises them exactly as a dependency would, with no edge at all. The
comment hands the next triager a 3-child sketch on that basis, and tells it to keep the
parent's own group `poster-read-migration` rather than invent one — a new group would
also de-serialise the children from the siblings that share these files.

## The review earned its keep

Pass 1 found eight real problems and I rewrote the comment around all of them. The two
that mattered most: I had said **two** non-poster consumers when there are **four** (the
two person surfaces make the same set-changing call), so the blocker was stated at half
its width; and I had called criterion 5's test-file parenthetical "factually wrong" when
it is **true as written** — it speaks only about `UserActionBar` and `ShowPoster`, which
genuinely have no tests. It also caught me citing `useSyncedState` as the pattern to
follow when it is the anti-pattern here (it discards the local value whenever the source
identity changes, and both live-prop providers hand down a fresh object every time), and
caught me inserting the word "only" inside a quotation and calling a client refresh a
"breach" of the conformance fence when that fence is a lexical check over server modules.

Pass 2 then found three more, all of which widened or corrected the blocker rather than
polishing it, and all of which I verified before patching:

- **The blocker was still too narrow.** `useFilteredShows` is called from **six**
  surfaces, not just browse — the Watchlist grid and all four List grids and
  `InfiniteShowGrid` — and it filters on **five** fields, not one: `watchedFilter`,
  `likedFilter`, `ratedFilter`, `loggedFilter`, `watchlistFilter` (`:139-154`). Every one
  of those is a module kind, so a like, rating, log or watchlist write makes a poster
  vanish exactly as a watched write does. Someone could have answered "1" or "2" without
  knowing they were deciding it for List pages.
- **Option 2 is not uniform, and I had said it was.** Rate, like, season and episode each
  call `refresh()` on the server, which re-renders the `statuses` prop map a round trip
  later — so "filters stay still" is true only for watch status and watchlist, the two
  kinds that do not refresh. The honest statement is *still for two kinds, delayed by one
  round trip for the other four.*
- **Follow is a second undisclosed divergence from the same rule.** `CONTEXT.md:401`
  defines Library Write as "a Quick Action, a watchlist **or follow** set, a watched
  mark…", so follow IS one by the glossary, while #2716 and #2666 both keep it outside
  the module. I had been repeating "follow is not a module kind" as plain fact; it is a
  deliberate departure and now says so.

It also caught that the per-kind stale table was client-side only: every one of those
actions ALSO calls `revalidateUserStats(userId)`, which is precisely what Library Write
means by "only marked stale", so a "stales exactly that set" test written off my table
would have asserted a smaller set than the code has.

And two structural gaps in the split sketch, both now fixed: **child 3 depends on child 2
as well as child 1** (its `handleWatchStatusChange` trim cannot land while
`UserActionBar.tsx:111,330,336` still calls it — the staffing-group order happens to
serialise that, but a re-staffed child 3 would fail typecheck, so it belongs in prose),
and **criterion 7's module half belongs to child 1**, not child 3: the `trackEvent` and
`handleUnauthorized` survival test is on the module's path, so the child that builds the
module must carry it or it can ship one that drops both.
