## READ THIS FIRST: never mutation-test with `git checkout --` against uncommitted work

My mutation script restored each file with `git checkout -- <file>` between mutations. `git checkout --` restores to the last **commit** — and the fixes I was testing were still uncommitted. The first mutation's restore silently reverted **all of them**, so mutations 2 and 3 ran against the pre-fix tree and reported cascading failures that looked like my tests being over-coupled. They were not: the code under them had been deleted.

The tell is a mutation whose `assert count == 1` fails ("0 occurrences") — that is the script telling you the line it wants is already gone. I re-applied the fixes, **committed them first**, and re-ran; every mutation then isolated exactly one case.

**Rule: commit before you mutate, or snapshot with `cp` rather than `git checkout`.** Nothing warned me — `git status` after the run looked innocent because the reverted files were simply clean again.

## The review caught a real spec contradiction, not a style point

Both axes independently flagged that the log sheet's clear control was copied from the quick-rate sheet **without** its `disabled`/busy state, so it stayed pressable during a save while the picker beside it was disabled. Real, fixed.

The spec axis then caught something I had accepted too readily in my own brief. I kept the old re-press-to-clear shortcut because #1072 says "keep the re-press shortcut if it already works" — but the same ticket makes *"a rating of 3.5 set elsewhere … can be re-selected"* an **acceptance criterion**, and under a toggle the value a member already holds is the one value they cannot re-select. Half-star zones are 22 points wide, so the accident is likelier than it was. And the shared component had come to mean "clear" in one sheet while `MediaActionSheet.handleRate` ignores a same-value press — precisely the drift the extraction exists to end.

**When a permissive spec line ("keep X if it works") contradicts a checkbox acceptance criterion, the criterion wins.** I dropped the toggle, inverted the test that asserted it, and added a case that re-selects an existing 3.5 as itself.

## Decisions

- **Declined folding the clear control into `RatingPicker`** (standards, Duplicated Code). The two sheets put it in headers with different labels and layouts, so sharing it means the picker owning a header row — which changes the quick-rate sheet, which the ticket forbids. ~12 lines of `Pressable` is the cheaper duplication.
- **Declined converting `LogSheet`'s `rating: number` (`0` = unrated) to `number | null`** to match the picker's shape. Fair finding, noted on the PR for #1086: the sentinel is internal to one component's form state, converted at one boundary, and rewriting the seeding (`existing?.score ?? 0`) and payload lines is not this ticket's.
- **Declined extracting the test harness.** The reviewer noted `mobile/test-utils/query-client.tsx` exists and 13 files import it — but `log-sheet-tags.test.tsx`, this file's sibling and the ticket's named prior art, builds its own QueryClient. The bulk of the duplication is six hoisted `jest.mock` blocks that cannot move to a helper anyway.
- **Unselected stars change on the log sheet** (`purple-400` → `rating-star` with transparent fill, 32 → 28 points). That is the quick-rate sheet's appearance, which is what one shared component costs; on the `purple-700` surface it is strictly more visible. Stated on the PR rather than quietly shipped.

## Next iteration should know

- **A never-resolving promise deadlocks `fireEvent.press`.** To observe a component on its in-flight state, `mockPost.mockReturnValue(new Promise(() => undefined))` hangs the press itself — `fireEvent` awaits the handler, so the test times out *before* your assertion, with no output from a `console.log` placed after it. Use a deferred: hold `resolve`, `void fireEvent.press(...)` **unawaited**, assert, then release inside `act`.
- **The host was badly contended for the first half of this iteration** — a single-file jest run that takes 2.8s took over 5 minutes to start while a Buildkite E2E job held the box. That is startup contention, not a hanging test; check `docker top buildkite-agent` before concluding anything about a slow suite.
- **Mergify auto-enqueue did NOT fire here.** #1146 sat `CLEAN`/`MERGEABLE` with **no** `queued` label, and the explicit `@mergifyio queue` comment is what moved it. The last three journal entries say a settled green PR enqueues itself; do not skip the enqueue on that basis — read the labels first, as §5.6 says.
- `CONTEXT.md` still has no term for a rating control, and `Quick Action` names the *write*, not the picker. Nothing needed adding for this ticket, but a future rating-surface ticket may want one.
- Mobile now pairs display-only `StarRating` with interactive `RatingPicker`; web has a single `StarRating` doing both. Honest within mobile, divergent across platforms — worth knowing before naming anything else in this area.
