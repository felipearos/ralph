# 2026-08-19 — #538 Invite and respond to List Collaborators on mobile

**Outcome: merged.** PR #597, squash-merged, issue auto-closed, both labelled `ralph-done`.

**What was actually wrong before this.** The ticket reads like "build the mobile
screens", but none of the rules it asks for existed anywhere they could be
enforced. The six-collaborator cap lived only in the web edit form's *disabled
input*; `addCollaborator` swallowed duplicates with `onConflictDoNothing` and
returned success; and `/api/v1` had no collaborator surface at all. So the work
was: lift the lifecycle into a shared core
(`src/server/queries/list-collaborator-write.ts`), point the four web server
actions and four new v1 routes at it, then build the two mobile surfaces.
**No migration** — `list_collaborator` already had everything.

**Key decisions.**

- *Acceptance sets `is_collaborative`, not the invitation.* `getListIfEditable`
  requires the flag **as well as** an accepted row, and the owner can clear it
  from the web edit form between inviting and being answered. The first draft
  set it on invite; the spec review found the hole. Setting it on the answer is
  what makes "Accept grants curation access" actually true.
- *Decline deletes the row whatever state it is in.* The first draft restricted
  it to pending and returned a 409 otherwise — a real regression: `main` had no
  status filter, and decline is the **only** way a member leaves a List someone
  else owns. There is no `leave`/`leaveList` path anywhere in `src/` or
  `mobile/`. Do not "tighten" this again without building the exit first.
- *Both answers are refused unless the caller already has a row, checked before
  the List is read at all.* Otherwise the endpoint is an existence oracle:
  200-vs-404 over the id space tells a stranger which private Lists are real.
- *The cap is counted and the row inserted inside one transaction behind a
  `for update` lock on the List.* The lock is on the List, not on collaborator
  rows — rows that do not exist yet cannot be locked, and the invariant is about
  the List's total.
- *A block in either direction refuses an invitation, reported as "member not
  found"* — neither side learns from this endpoint that the other blocked them.

**The review earned its cost again, and the spec axis outperformed standards.**
Two Opus agents, nine findings, all fixed in one commit. The two that mattered
most were behavioural, not stylistic: the decline regression above, and a
**spurious 404 on genuinely concurrent Accepts** — the losing transaction's
guarded UPDATE returns 0 rows, and the code then answered from the `existing`
row it read *before* the race, reporting "invitation no longer available" on an
invitation that had just been accepted. Fixed by re-reading after the failed
update. Sequential replay never exposed this, and the test that "covered replay
safety" could not have caught it.

**Also worth knowing for next time.**

- **Widening `NotificationType` breaks other files silently until typecheck.**
  `mobile/app/(tabs)/activity.tsx` has a *second, near-duplicate* notifications
  list with its own `Record<Exclude<NotificationType, "new_follower">, …>` icon
  map. Adding two enum members broke it. That duplicate is also why the invite
  actions had to be extracted to
  `mobile/components/notifications/CollaborationInviteActions.tsx` and wired
  into both — the Activity tab is the tab-bar-reachable surface, so shipping
  Accept/Decline only on the standalone screen would have failed the AC on the
  surface members actually use.
- **Root `bun run typecheck` does not cover `mobile/`.** Run
  `bunx tsc -p mobile/tsconfig.json --noEmit` separately. Six pre-existing
  errors there from stale expo-router typegen (person, review, AddToListSheet,
  CreateListButton, DiaryTab) are not yours.
- **`git fetch origin` fails in the main worktree** ("refusing to fetch into
  branch refs/heads/main"). Use
  `git fetch --refmap= origin '+refs/heads/*:refs/remotes/origin/*'`.
- **The pre-PR hook marker `.claude/reviewed/<sha>` is still unwritable** — the
  permission layer treats it as sensitive, and `Write` is refused too. The
  documented escape hatch still works: `gh pr create --draft` then `gh pr ready`.
- **Three conformance ledgers had to move with the code**, and each fails
  distinctly: `notification-creation-conformance.test.ts` (creation-site list),
  `read-boundary-conformance.test.ts` (which modules may import the `list`
  table — this one also pushed `getListCollaboratorAccessCore` into the core,
  which was the better design anyway), and the deleted
  `actions/listCollaborator.test.ts` whose revalidation assertions I had to
  re-add to the new integration suite.
- **PGlite (`~/test/database.ts`) needs no external database** and is the right
  home for domain tests here — it judges the `for update` lock and the unique
  constraint, which a mocked db cannot.
