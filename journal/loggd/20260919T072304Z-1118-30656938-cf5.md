## READ THIS FIRST: a background jest run that times out can leave your mutant in the tree

I mutation-tested the hook by editing the file, running jest, and restoring — all in one compound command. Twice the command was moved to the background and killed at its timeout **before the restore line ran**, leaving the mutant in the working tree. The first time I then read `git diff --stat` (12 insertions), read only the first 30 lines of `git diff`, saw my intended change at the top, and concluded it was clean. It was not: the next 20 lines were the mutant, and I built two more edits on top of it before a test failure exposed it.

**The rule for next time: never put a mutant and its restore in the same backgroundable command.** Apply, run, and restore as three separate calls, and after the restore assert on the *content* (`grep -n` for the exact line you expect) rather than on a diff stat. `git checkout HEAD -- <file>` is the reliable restore; a `cp` from a `/tmp` backup is only as good as the command that reaches it.

The second escape was worse in principle and harmless in practice: the file I shipped was correct only because a test caught the leftover. Nothing about "the diff looks right at the top" is evidence.

## READ THIS FIRST: `onSettled` invalidation makes optimistic-update tests pass for free

Four cases in this branch could not fail as first written, and all four had the same shape. `useDismissNotification`'s `onSettled` invalidates `["notifications"]`; the refetch then produces the right list, the right unread count **and** the restored row on its own. So:

- "the row is gone once the request resolves" passed with the whole optimistic half deleted — deleted the case, it was subsumed.
- "the unread count falls" passed with the decrement deleted — now asserted with the request held open.
- "the row comes back on failure" passed with the rollback deleted, because the server never lost the row — now the **refetch is held open too** (`mockGet.mockImplementation(() => new Promise(() => undefined))` after the initial load), which leaves the rollback as the only thing that can put the row back.

**Any test of an optimistic update whose mutation also invalidates must assert before the request settles.** Holding the request pending is not enough where the refetch alone would answer; hold the refetch too.
