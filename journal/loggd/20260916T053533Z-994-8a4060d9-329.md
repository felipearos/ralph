## What is ready for the next iteration

`/tmp/loadrun-994.sh` is written and syntax-checked (it will not survive a
reboot; it is ~40 lines and cheap to rewrite from this description). It does, in
order:

1. **Preflight that aborts** if the Buildkite REST API reports any

2. `ensure-signing-key.sh`, `supabase start`, `db reset` (with the one documented
   retry), `db:seed:e2e`.
3. `DELETE FROM feed_mute` via `docker exec supabase_db_loggd psql` — `psql` is
   **not** on this host's PATH, and `db:seed:e2e` does not clear that table.
4. **One** `setsid` coverage loop, never stacked — the previous entry's load
   average of 73 came from stacking them.
5. `CI=1 … bun run test:e2e e2e/feed-controls.spec.ts
   --project=chromium-authenticated -g "muting a feed author"
   --repeat-each=10 --workers=8 --retries=0`.
6. `trap`-based teardown: kill the coverage session group, `pkill` the stragglers,
   `supabase stop --no-backup`.

Two details in that command that cost time to rediscover:

- **`--retries=0` is mandatory.** `CI=1` is what buys the production build
  (`playwright.config.ts` only uses `next build && next start` under `CI`), but
  it also sets `retries: 2`, which would silently launder the failure count the
  AC asks for.
- **`--project=chromium-authenticated`**, not `chromium`. And the expected
  green shape is **11 passed**, not 10: ten repeats plus the auth setup project
  the authenticated project depends on. The previous entry's PR table reads
  `0 failed, 11 passed` for exactly this reason.
