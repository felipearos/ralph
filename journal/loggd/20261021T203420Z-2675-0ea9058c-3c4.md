## What landed

`runListEditSave` (`@loggd/shared/list-edit-save`) owns the stale-re-read-and-retry
loop, three rounds as before; both edit hooks call it and keep only a transport
(`save`, `readLatest`) plus the mapping onto their own outcome.
`parseListEditSnapshot` / `restoreCreationSession`
(`@loggd/shared/list-edit-snapshot`) replace the near-identical copies in the two
creation adapters, with each caller's media-type and tag rules passed in as guards.
`setListCoverPinsCore` and the mobile `list-cover-pin` List Write kind are deleted;
`writeCoverPinStrip` stays at `src/server/queries/list-cover-pins-write.ts` because
`cover-pin-writer-conformance.test.ts` scans `src/**` lexically for exactly that path.

## Key decisions

- **A Save's confirmed state — and its item set — is the server's, on both
  clients.** The web used to adopt its staged copy. Worse, *both* clients kept
  every staged item, so a title the server refused
  (`partitionByTmdbExistence` → `rejectedCount`) stayed in the new baseline and
  the session read clean against a List that does not hold it. A staged item is
  now kept only when the canonical items hold its key; display data and notes
  still come from staged, since the canonical items carry no `name`/`posterPath`.
  The local spec review found this. Mobile's behaviour changes here, toward the
  ticket's own rule.
- **The transport is handed `staged`** rather than re-reading the session — one
  duplicated read gone on each client, plus an unreachable mobile branch.
- **A test that passed for the wrong reason.** The first web creation-adapter
  media-type test passed under a deliberately broken guard: changing an item's
  media type changes its `mergeItemKey`, so the draft was refused for having no
  row for a staged item and the guard was never reached. Only the mutation check
  caught it; the variant now moves the item's row with it. Worth repeating as a
  habit, not a one-off.
- **Deliberately not done:** sharing `savedListEditState` (web) / `savedState`
  (mobile) — same algorithm over two different response shapes, #2657 does not
  ask, and the one place they had drifted (mobile's per-pin `Array.some` vs the
  web's `Set`) is fixed so they stay line-for-line comparable. Also not touched:
  `docs/architecture-review/README.md`, a dated snapshot of the review this
  ticket came from.
