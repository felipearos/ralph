**Key decisions.**
1. The block gate sits ABOVE the audience clauses in both the SQL and the TS, so it refuses
   a *public* List too. That is the AC's literal wording and #2684's "Block rule on reads".
2. The audience's two reads are `allSettled`, not `all`: either can decide the rule alone, so
   a failed block read must not turn a non-follower's 404 into a 500. Only admission needs
   both, and it cannot fail closed. `list-audience.gate-failure.test.ts` pins all six cases.
3. **A trigger on `user_block` was built and then withdrawn** — the one thing to carry
   forward. Rounds 3–5 of review correctly found that a block filed over PostgREST skips
   `blockUserCore` and leaves the pair's follows standing, and an AFTER INSERT trigger looked
   like the fix. It changes what an INSERT on that table MEANS for every writer; **37 test
   files seed a block through Drizzle**, and `friends-feed.test.ts` pairs a block with a
   follow deliberately, so it broke. Nothing in `src/`, `mobile/` or `packages/` writes
   `user_block` through PostgREST, so one more revoke in `0075` closes it with no blast
   radius and makes the server core the only writer of a block. **If a future ticket reaches
   for a trigger on a table 37 fixtures write, measure the blast radius first.**
4. `friends-feed.ts` deliberately untouched: #2669 / open PR #2751 is editing that exact
   function. The feed is correct today because no cross-block edge survives, not because the
   reader is symmetric. Said so in the suite rather than implied.
5. One drive-by, declared: `lockMemberPair` lower-cases ids before sorting. `z.guid()`
   accepts upper-case hex, so the two writers could compute two keys and serialise nothing.
