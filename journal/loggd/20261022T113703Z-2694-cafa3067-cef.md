## The failure is not this diff, and no branch can clear it

Those two ledger rows are `drizzle/0075_follow_across_block.sql` and
`drizzle/0076_delete_follows_across_blocks.sql`, which exist **only on the still
open PR #2760**. They were applied to prod by hand before that PR merged, so
prod's ledger carries two rows no branch at main's tip knows about. #2768 touches
no `drizzle/`, `migrations/` or `src/server/db/` file, and the other eight jobs
are green. main's build 4027 passed only because main's builds skip that job —
which is exactly what makes a repo-wide red look branch-local.

This is the open learning `prod-ledger-ahead-of-main`, and I followed its
workaround rather than re-deriving it: no renumbering, no rebase, no applying the
migrations (those credentials are deliberately withheld), one comment on the PR
naming #2760 as the culprit, claim kept, `RETRY_LATER`. I did **not** spend the
learning's one allowed re-run: the offending rows are still in prod, so a re-run
reproduces the failure by construction. That allowance is still unspent for a
later session.

I added a `Seen again` to that learning, with one improvement to its workaround:
the culprit PR is identifiable directly, by looking through `gh pr list --state
open` for the one adding `drizzle/*.sql` in the same count as the "applied ahead"
rows. That turned a repo-wide mystery into a named PR in two commands.

## Decisions

- **Treated `unreadable` as a wrong number before treating it as a CI problem.**
  The preamble offers "wait once more if CI is plainly still running", which
  would have burned a second round on the same non-existent PR.
- **Did not re-run, and did not block the ticket.** Running out on an external
  cause is `RETRY_LATER`, not `-blocked`: the work is finished and green, and
  swapping the claim for `testo-blocked` would strip a live claim off healthy
  work.
- **Did not touch the head.** #2768 should go green unchanged once #2760 merges,
  so any commit now would only invalidate the review marker and the green jobs.
