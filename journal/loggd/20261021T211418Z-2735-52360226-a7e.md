## What the two review passes actually bought

This is the clearest case so far that the spec stage earns its cost on a
label-free ticket. Pass 1 and pass 2 together produced:

1. **Amendment 3 cancels work the body asks for.** The body (my own, from iteration
   16) claimed the gate's `profiles.show_adult_content` select would consume a row
   queued for `hydrateProfiles` in `activity.test.ts` and that fixing its queue was in
   scope. Wrong: the queue matches on the **selected field set** (`:207`), and its
   profiles entry is `selecting(profiles, "id","username",…)` (`:142`), which a
   single-field `{ show_adult_content }` select cannot match, so the gate's read
   resolves to `[]` (`:208`) and the queued row survives. A coder would have spent an
   hour "fixing" a green suite.
2. **The `commented` criteria were partly vacuous.** `commented` entries come only
   from `fetchIncomingCommentKeys` (`activity.ts:727`, called at `:1284`), gated on
   `shouldShowIncoming` (`:1255-1257`); those tabs are `OWN_TABS` (`:1308`) and
   `readMemberActivityPage` returns an empty page for an `OWN_TABS` read by a
   non-owner (`:1347`). So criterion 2's anonymous comment assertion is true whatever
   the gate does, and criterion 3's "present for all three viewers" is unsatisfiable
   for a comment item. Amended: the comment case is a self-read on `incoming` for the
   two signed-in viewers; `friends` + `includeIncoming` is explicitly ruled out
   because that branch returns empty before any incoming source runs unless the
   viewer follows someone (`:1192-1207`), which would have passed the "absent"
   assertion vacuously.
3. **The gate's generic makes the body's literal instruction uncompilable.**
   `gateAdultStatsTitles` is `<T extends { tmdb_id: number; media_type: "tv"|"movie" }>`
   (`adult-gate.ts:136-142`); review/watchlist rows carry the 12-member schema enum
   and like/comment rows use `review_tmdb_id`/`review_media_type`. Amendment 1
   prescribes the caller-side movie-only key list, after
   `gateFeedRowsByAdultContent` (`friends-feed.ts:88-111`), and names three traps the
   precedent would otherwise walk the coder into: filter by **withheld** indices not
   by survivors (`:105-107`) — the survivor reading drops every TV, book and
   person-follow row — only movie rows in the list, and do **not** copy
   `friends-feed.ts:104`'s `null` user, which would withhold adult movies from
   opted-IN viewers.
4. **Criterion 10's command covered neither guard it needed to.** Added a second run
   for `server-action-surface.test.ts` and `src/app/api/v1/activity`.

Pass 2 also caught five off-by-one citations in my pass-1 text (`adult-gate.ts:143`

body specifies filters by the movie's flag and not by who wrote the row. Rather than

not to this ticket.

## One judgement call of mine, flagged as such

Pass 1 noted that seeding `adult: false` rows in the four existing suites is optional
— the table is the hard requirement, and without a seeded row the gate falls back to
each suite's `getMovieBasicOr404` mock, whose fixtures carry no `adult` field, so
`resolveMovieAdultFlags` resolves `known, adult: false` (`mediaMetadata.ts:275-276`)
and the title is kept anyway. Amendment 5 **requires** the seed regardless, and says
so as a decision rather than a necessity: a suite that passes because a TMDB mock
happens to omit a field is pinned to the mock's shape rather than to the gate's
contract, and it reaches the fallback path on every read. Two traps named with it: the
seed needs a non-null `title` (`src/test/database.ts:420`) and an explicit `false` —
a null `adult` falls straight through to TMDB (`mediaMetadata.ts:261-262`) and quietly
undoes the amendment.
