## What shipped

A Pending Intent record now carries `runId` (a nonce minted once per app
process) and `capturedAt`. `consumePendingIntent` refuses an **unbound** record
(`userId === null`) unless `isFreshFromThisRun` holds — same run, at most 30
minutes old. Bound records are exempt from both checks, so a record written by
an older build (neither field present) is refused when unbound and still
consumed when bound. Four commits: the library change, the gate-seam regression
test plus a `CONTEXT.md` glossary entry, four whole-record assertions in two
sibling suites relaxed to `toMatchObject`, and the review fixes.

## Key decisions

- **Ruled out a sign-up-attempt marker written by the auth screens.** The
  ambient `usePathname()` capture in `MediaActionRow.tsx:62-64` *is* the
  mechanism AC2 names; a second explicit signal would duplicate it, and
  discarding the ambient record would break AC2 outright. Codex's single P1
  thread asked for exactly that marker and was answered with this evidence and
  no code change — a finer-grained rule needs a second capture signal, which
  belongs to parent spec #2478.
- **Accepted limit, stated in the PR body:** an email-confirmation link that
  *cold-starts* the app loses the capture, because that is a new run. This is
  the module's own trade — one missed resume, never a wrong one.
- Web needed no code change; the spec reviewer confirmed that independently.
- `delegate.sh` ran both implementation slices (library + unit tests; gate test
  + glossary), one round each, exit 0. The review fixes and the assertion
  relaxations were small and findings-driven, so I wrote those myself.

## What the next iteration should know

**The branch was never the problem — ten iterations of this ticket were spent
waiting out a repo-wide CI deadlock.** `production-migrations` (the production
Drizzle ledger audit) was red on *every* open PR in the repo from build 3665
onward, with the same `classification=ledger-check` line and no migration in any
of the diffs. Nine `RETRY_LATER` rounds; then an operator reconciled production's
`__drizzle_migrations` and the original head `1d45212d1` merged unchanged — no
rebase, no empty-commit re-run, no block. Three things that cost rounds and are
worth skipping next time:

- A theory that waiting for the migration PR (#2493) to merge would clear it was
  **wrong**: #2493's own build 3675 carried `0067`/`0068` and failed the same
  job. Learning `prod-ledger-ahead-of-main` was revised in place to say so.
- A build on `main` that "passed (8 jobs)" is not the all-clear if its
  `production-migrations` job is **`broken`** — the job never ran and has no
  log. Only a green *run* of that job counts; check the job state before
  reading it as a signal.
- This block is never `needs-migration:` when the PR carries no migration of its
  own, and `RETRY_LATER` (§1's external blocker) is the right ending, not the
  blocked exit — the credential is withheld from the loop by design, so the
  audit is unreproducible here and there is nothing on the branch to fix.

Both learnings (`production-migration-ledger-drift`,
`prod-ledger-ahead-of-main`) stay **open**: their Fix is the operator
reconciliation, not #2486, so this PR worked around the problem rather than
fixing it and closed neither.
