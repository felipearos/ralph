## READ THIS FIRST: a test can pass *because of the host*, and CI is the wrong host

The executor wrote a test for the one deliberate behaviour change in this diff
(formatting TMDB release dates with `timeZone: "UTC"`, so a viewer west of UTC
stops seeing the previous calendar day). It picked an instant — `02:30Z` — that
is the previous day "in every US zone", and asserted the UTC answer.

That test is green on this box (TZ `-03`) and green in CI. **It is only a real
test on the first one.** CI runs UTC, where `toLocaleDateString` returns the
same string whether or not you pass `timeZone: "UTC"` — so the assertion that
exists to pin the option passes identically with the option deleted. I only
know that because I mutated it and ran it under `TZ=UTC` as well as bare.

The generalisable shape, and it is *not* the same as the usual "mutation-test
every guard" note: **run the mutation under the environment CI will use, not
just yours.** A guard over anything environment-derived — timezone, locale,
platform, `process.env` — has a host-shaped hole, and the host that matters is
the one that gates the merge. Mine looked killed and was not.

Fix was to pin `process.env.TZ = "America/New_York"` inside the test with a
`finally` restore. Node honours a TZ reassigned at runtime (probed it — do not
reason about this, it is not a language guarantee).

## Hermes has no `Intl.DisplayNames`, and jest will never tell you

This is the design decision the whole ticket turned on. Country names had to
come from somewhere, and the obvious move — resolve them in the component, as
the web tab does — would have **passed every test and crashed on device**:
mobile jest runs on Node with full ICU, the device runs Hermes, and
`Intl.DisplayNames` is not in Hermes's Intl subset (`Collator`,
`DateTimeFormat`, `NumberFormat` are).

So `include=releases` resolves country names server-side and answers
display-ready data, and `groupMovieReleases` takes the resolver as an argument
rather than constructing one. Web passes a browser `Intl.DisplayNames`, the
route passes a Node one, mobile passes nothing because it never calls the
grouper — it renders the route's output.

**Next iteration: any `Intl.*` beyond DateTimeFormat/NumberFormat/Collator
reaching `mobile/` is a device crash that mobile tests cannot see.** Grep before
you ship it. `mobile/lib/watch-region.ts` uses `Intl.DateTimeFormat`, which is
fine.

## Both review axes found the same two things, independently

Third journal in a row where that happened, and both were real:

- **The accessible row swallowed the note.** The mobile date row is one
  `accessible` unit with an `accessibilityLabel` built from date + countries.
  RN merges children under an accessible container, so the per-country `note`
  ("Cannes Film Festival") — the entire reason `detailed: true` exists for
  Premiere — was announced to nobody. Visible on screen, invisible to a screen
  reader, and the existing test only asserted the label for a *non*-detailed
  category, so it could not catch it. **An `accessible` container is a
  whitelist: anything not in the label does not exist.**
- **Two `TMDBReleaseType` declarations.** The executor added a const-object +
  union to `packages/shared` beside the existing nominal `enum` in
  `src/lib/tmdb-client.ts`, and justified it in a comment as cross-package
  assignability. It compiled only by numeric-enum structural luck. Fixed by
  deleting the web copies and re-exporting the shared ones — cheap, because
  nothing used the web enum as a *value* any more once `TYPE_ORDER` moved.

Gotcha on that fix: `export { X } from "…"` does **not** bind `X` locally, so
`tmdb-client.ts` (which uses `TMDBReleaseDatesResult` in `TMDBMovieDetails`)
needed an `import type` alongside the re-export. Typecheck caught it.

The spec axis added a third worth keeping: **every mobile test hand-built its
`MovieReleaseCategory` fixtures**, so renaming `detailed`/`type`/`groups` would
have stayed green on both sides of the wire. Added a test that runs the real
`groupMovieReleases` over raw TMDB shapes and renders its output.

## Decisions and what was ruled out

- **Grouping lives in `packages/shared`, not duplicated.** The web has had this
  algorithm since forever in `MovieReleasesTab`; it moved out verbatim and the
  web tab now renders byte-identical JSX from it. Ruled out: writing it twice
  (#1088's review found a third un-deduped copy of its provider logic and this
  is the same trap), and having mobile call the grouper itself (Hermes, above).
- **`include=releases` is non-blocking** (`.catch(() => null)`), like `override`
  and `watchProviders`, with a route test asserting `data.movie` survives the
  outage. This is now settled route policy, pinned by #1088's review.
- **Shows untouched.** `/release_dates` is movie-only; TV has content ratings,
  which #1090 does not ask for.
- **Flagged, not changed:** `MOVIE_DETAIL_INCLUDES` gains `releases`, so every
  movie detail view costs one extra TMDB fetch. Same trade `watchProviders`
  made, and what a Details-tab section requires, but it is an always-on cost on
  an opt-in mechanism. Said so on the PR rather than silently absorbing it.
