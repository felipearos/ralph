## Why the column could not be avoided

I spent real time looking for a design without it, because a migration ends the
iteration. Acceptance criterion 3 — "the member's list-visibility choice is
captured with the job and applied consistently during retries" — kills both
alternatives:

- **Put it in the uploaded object.** Criterion 1 requires the stored object to be
  the member's *original* ZIP, so anything wrapped around it violates that.
- **Re-ask on retry.** A recovery sweep runs with nobody watching; there is no
  one to ask.

A per-job durable option is the requirement, spelled out. `options jsonb`,
nullable and additive, is the smallest thing that satisfies it. It is now a
glossary term (**Import Options** in `CONTEXT.md`) because the concept is
source-neutral and the next source with a choice will reuse it.

## The trap #659's journal warned about was real, and bigger here

That entry said: "Letterboxd (#660) has the same shape — check where its summary
numbers come from before wiring `beforeWrite`, or it will publish the same
placeholders." Correct. `runLetterboxdImport` ended with **four** post-write
`count(*)` queries feeding `summary.watchStatus.watched`, `.watchlisted`,
`reviews.total` and `lists.total`.

But Letterboxd is harder than IMDb was, and the next source will be too: its
write phase was *interleaved* with its planning, not merely trailing it. The
diary loop inserted each review and used the returned id to attach tags; the
list insert returned ids the item inserts needed. Splitting it meant building a
`diaryPlan` of `{ values, tags }` and keeping the `.returning({ id })` in the
write phase, iterating the plan. The dedup state (`seenReviews`, `diaryKeys`) is
pure computation and moved into the plan untouched.

**Generalise it:** "restructure plan-then-write" is a one-line brief for IMDb and
a careful one for any source whose writes feed later writes. Say in the brief
which returned values later steps depend on, or the executor will flatten them.

## The other thing that had to change: the job payload is bytes now

`ImportUploadStore.download` answered a `string`, `processImportJob` took `text`,
`runImportSource` handed `text` on. A ZIP does not survive that. The payload is
`Uint8Array` end to end and the two CSV sources decode at their own dispatch
arm. Cheap, mechanical, and it had to happen before Letterboxd could be wired —
worth knowing that the next binary source costs nothing here.

## jsdom eats fflate — this will bite the next test that builds an archive

`bun run test` runs under jsdom, whose `TextEncoder().encode()` returns a
Uint8Array **from a different realm**. `instanceof Uint8Array` is false for it,
so `fflate`'s `zipSync` treats the bytes as a nested directory object and
produces an archive whose entries are `a/watched.csv/0/`, `a/watched.csv/1/`, …
It looks exactly like a parser bug and it is not one — the same code is correct
in `bun -e` and correct on the server, where there is one realm.

The fix is one line, `new Uint8Array(new TextEncoder().encode(s))`, and it is
commented at both call sites (`src/lib/letterboxd-import.test.ts`,
`src/server/imports/letterboxd.test.ts`). I lost ~10 minutes to it.

What worked, and is worth copying:

- **Slice the ticket by seam, not by file.** schema (mine, hard rail) → run
  entry point → plan-then-write → transport → screen → e2e. Each brief named the
  worked example in the repo (`runImdbImportFromCsv`, `ImdbImportPage`) and the
  executor matched it closely enough that review was fast.
- **Poll for the `.usage` file, not for a process name.** `pgrep -f delegate.sh`
  matches nothing useful (the work runs as `opencode`), so a `until ! pgrep`
  loop exits immediately and reports a finished run that is still going.
  `until [ -f ralph/logs/delegate-<stamp>.usage ]` is the reliable wait.
- **A brief that names the traps gets them right.** Every brief carried the
  glossary terms, `~/` vs `@/`, the solid-colour rule and the `as`-assertion
  hook. Zero of those came back as review findings.
