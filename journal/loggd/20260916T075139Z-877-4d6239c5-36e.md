## The finding this iteration exists for

The first version of this branch had an **account-hijacking hole in the native OAuth flow**, and it is worth understanding because it is a class, not a slip.

The web flow keeps its CSRF state in an httpOnly cookie. Native has neither half of what that relies on — the system browser holds no Loggd session, and Patreon returns to a server redirect URI — so I built a server-owned one-time token (the Patreon Link Handoff) that binds the attempt to the member who started it, and had the callback write the Patreon Link for the member the handoff named. That reasoning is seductive and wrong. **Whoever presses Allow at Patreon is not provably the member who started the attempt.** Any member can mint an authorize URL and forward it; the recipient consents in their own Patreon session; and the callback dutifully writes *their* Patreon identity, credentials and paid tier onto the *sender's* account, while locking the real owner out as `already_linked`.

What the cookie actually provides is a binding to the **user agent**, and no amount of server-side state substitutes for it. I spent a while looking for one — PKCE, a confirmation secret returned to the app — and each candidate failed the same way: the attacker holds whatever the initiator holds.

The fix is to move the write to the side that has a session. The callback now validates that the attempt was one Loggd started and hands the **authorization code** back to the app; the app redeems it at `POST /api/v1/users/me/patreon/complete` **over its own Bearer token**, and that request is what names the member. In the attack the victim's app receives the redirect, so the link lands on the victim — the correct outcome rather than a refused one. The code in a `loggd://` URL is fine: single-use, short-lived, unusable without the client secret the server never discloses (RFC 8252's shape).

**The local spec review found this, on the Opus axis, from the acceptance criterion "rejects … cross-account replay".** I had written a comment in the callback explaining why cross-account replay was "a non-event rather than a check". The review read the code rather than the comment and walked the other direction. That is the single highest-value thing that happened this iteration, and it argues for keeping the spec axis adversarial and criterion-by-criterion rather than asking for a general opinion.

## Second review finding worth keeping

A state matching no row — expired past the purge, truncated, forged — fell through to the web branch, which answered the *system browser* with `memberRefusalResponse`'s raw 401 JSON page. The browser never returns anything, the member dismisses it, and `openAuthSessionAsync` reports `cancel`, whose copy is deliberately empty. A silent dead end with no way out.

Fixed by having a native state announce its destination in the clear: `state = "n<destinationIndex>.<32 random bytes>"`. Unknown states with a recognisable prefix are redirected into the app with `invalid_state`. The prefix is not a secret and is not load-bearing — forging it buys a redirect to Loggd carrying an error.

## The mistake I made, and the test class that caught it

`drizzle/0058_patreon_link_handoff.sql` **shipped with its header comment and no DDL.** The cause is a Python one-liner that is worth never writing again:

```python
open(p, "w").write(header + open(p).read())   # truncates before it reads
```

`open(p,"w")` is evaluated first and truncates the file, so the inner read returns `""`. Typecheck, lint and every mocked test stayed green — the only thing that noticed was `patreon-lifecycle.integration.test.ts` failing with `relation "patreon_link_handoff" does not exist`, and it was the **delegated executor** that reported it rather than me. I have since added `patreon-link-handoff.integration.test.ts`, which replays the real migration against PGlite and exercises the unique index, the FK cascade and the one-time `DELETE … RETURNING`. Any branch adding a table should carry one; it is the only test that can tell a migration file from a comment.

## Design notes

- **Cores, per AC2:** `readPatreonLinkStatusCore`, `linkPatreonAccountCore`, `unlinkPatreonCore`. The web action, the web half of the callback and four v1 routes are thin over them. `effectiveTierOf` lifted out of `getUserTier` into `tier-utils` so a gated feature and the screen explaining it cannot disagree about a Comped Entitlement.
- **Vocabulary:** `CONTEXT.md`'s Patreon Link entry lists **Subscription** under `_Avoid_`. The settings destination keeps that name (web parity, and it is the ticket's word), but no identifier or copy calls the *record* a subscription — it is the Patreon Link, and what it earns is Loggd Pro. New glossary entry: **Patreon Link Handoff**, with `_Avoid_: OAuth State` because that is the URL parameter the handoff is found by, not the thing itself.
- **iOS:** the external Support link is Android-only. Connect Patreon ships on both, which is the open human decision — #877's own criterion asks for an App Store policy review before release, and the loop did not make that call.
