## The fact the whole design turns on, established by execution

**PostgreSQL enforces COLUMN privileges inside an RLS policy expression.**

Nine policies on `report`, `roadmap_item`, `roadmap_suggestion` and
`show_media_override` decide staff authorization with
`EXISTS (SELECT 1 FROM profiles WHERE id = auth.uid() AND role = …)`. If that
is true, revoking `role` and `is_admin` from the client roles does not tighten
those policies — it *breaks* them, and the moderation queue and three admin
surfaces start raising `permission denied for table profiles`.

I did not reason about it. In a scratch database (`CREATE DATABASE rls_probe`,
dropped afterwards — never the app's stack, never production):

| probe | result |
| --- | --- |
| policy referencing a column the role may NOT select | `permission denied for table p` |
| the same policy referencing a column it MAY select | row returned |
| the same lookup behind a `SECURITY DEFINER` function | row returned |

Three queries, and the design followed. That is why the diff contains two
`SECURITY DEFINER` predicates and nine rewritten policies for a ticket whose
title is about reads: they are a consequence of the revoke, not a second idea.

The same scratch database then ran the real migration end to end against a
five-table fixture and a stub `auth.uid()`, and every row of the behaviour
table in the PR body is a measured result rather than a claim. **Do this.** A
migration nobody can apply is exactly the one that most needs proving before it
is handed over, and a scratch database costs two minutes.
