## The decision: no split

Loggd's rule did not fire — 7 acceptance criteria (it fires above 8) and one
surface, the v1 API, with no mobile client code, no web change and no schema
change. The mapper bounded it at 10–13 files.

There IS a real seam here, unlike #3070: the renderer files
(`src/server/story-card/{ReviewStoryCard.tsx,styles.ts,render-review-story-card.tsx}`)
and the route files (new route, new query, `story-card-response.ts`) do not
overlap at all, and the renderer half does not wait on #3071 as the route half
does. Kept whole anyway, for two reasons:

1. The card types are `"tv" | "movie"` at every site
   (`review-story-card.ts:29`, `styles.ts:31,221,261`, `ReviewStoryCard.tsx:125`),
   so the route half cannot draw a book until the renderer takes book data. The
   seam is a one-way sequence, not two parallel children — and a plan cannot
   express that edge (`add-blocker` takes a plan-local `ref` only in `blockedBy`),
   which is the same wall #3070 hit.
2. Both halves land in `book-log-share`, which already serialises them through CI
   and the merge queue. A renderer-first child would also ship code nothing calls.

## What the two review rounds were worth

Round 1 caught the thing that would actually have broken the ticket, and it is
worth knowing outside this issue: **the `review` table's schema comment
(`schema.ts:531-532`) says `tmdb_id` holds the Hardcover id for books, and every
writer on `main` contradicts it** — book rows go in with `tmdb_id: 0` and the id
in `external_id` (`externalStatus-write.ts:250`, `:298`), and the readers key on
`external_id` (`review-hydration.ts:162`, `diary-page.ts:186`). A coder following
the comment would refuse or misdraw every real Book Log. Round 2 then showed the
obvious test for that guard proves nothing: a "wrong book" seed with `tmdb_id: 0`
passes whether or not the guard is right, so the seed has to set `tmdb_id` to the
path id and `external_id` to something else. #3069's fixture id `"hc:3069-card"`
is also not a servable id (`isServableBookId` wants the canonical decimal
string), so copying it into a happy-path test gives a row the route cannot reach.

Round 1 also took a product-shaped claim off me, the way #3070's second round
did: I had written that criteria 1 and 7 collide on
`STORY_CARD_TEMPLATE_REVISION`. They do not — the file says to bump it "whenever
what a card looks like changes **for the same data**", and a book branch does not
change a show card for its data. The real risk is narrower and I would not have
found it alone: the version hash digests `JSON.stringify({template, card})`, and
`JSON.stringify` keeps `null` and `false`, so a new field on the shared
`ReviewStoryCardData` filled on show rows silently rotates every show ETag.

Round 2's other keeper: **criterion 7 ("byte for byte as at `main`") has no guard
in the repo at all.** No golden PNG, `render-review-story-card.test.tsx:40`
renders with `version: "v1"`, and the integration tests only assert that
`version` changed. The comment now names what makes it checkable (a tree snapshot
of one tv and one movie fixture, plus pinning the hashed input rather than a
literal ETag, since the hash covers an env-built `url`).
