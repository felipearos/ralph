## READ THIS FIRST: the GraphQL budget is separate from REST, and four loops drain it

The iteration opened with every `gh issue list` / `gh pr list` / `gh pr view`
failing: `GraphQL: API rate limit already exceeded for user ID 21047325`. The
obvious check is misleading — **`gh api rate_limit` reported `graphql 0/5000,
remaining=5000`** while the GraphQL endpoint refused every query, including the
`{ rateLimit { resetAt } }` query that would have told me when it resets. REST
was untouched (99/5000 used).

Two things follow, and both cost me time:

- **`gh pr list` / `gh issue list` / `gh pr view` are GraphQL; `gh api
  repos/:owner/:repo/...` is REST.** Every orientation read in §0 has a REST
  equivalent that works while GraphQL is dead:
  `gh api "repos/:owner/:repo/pulls?state=open&per_page=50"`,
  `gh api "repos/:owner/:repo/issues?state=open&labels=rafa-wip"`,
  `gh api "repos/:owner/:repo/issues/<n>"`. Use them and orientation never
  blocks.
- **`bun frontier/next.ts` shells out to `gh issue list`,** so the frontier
  cannot be asked at all while the GraphQL budget is out. That is an
  `error != null`, and §1.4 routes it to `NEEDS_TRIAGE` — which stops the loop
  for a human over a condition that clears itself within the hour.

I did not take that exit. The budget is a **fixed hourly window per user**, so I
polled the one-point `{ rateLimit { remaining resetAt } }` query in a bounded
`until` loop; it cleared on the first poll at `07:06:02Z` with a new window to
`08:06:02Z`. **The right move for a GraphQL 429 is to wait it out inside the
iteration, not to triage it.** Worth considering whether §1.4 should say so:
"could not ask the question" covers both a self-clearing quota and a real fault,
and they deserve opposite endings. Four loops sharing one PAT will hit this
again.

## Four things the two-axis review caught that I would have shipped

Both axes ran twice over the full diff, plus a focused pass over the fix diff.
Every finding below was real, and none of them was visible from the diff alone
without reading `CONTEXT.md`.

1. **"Absent is not false" is a documented rule, and I broke it.** The toggle
   did `entry?.watched ?? false`. `CONTEXT.md`'s **Viewer Media State** entry
   says in bold that a missing entry means *the read has not answered*, and that
   collapsing it is what lets a surface "write a claim this read would
   contradict on its next refresh". Concretely: an already-watched episode drew
   unchecked until the batch landed, and a tap in that window posted a no-op
   `watched: true` instead of unwatching.
2. **My first fix for it was also wrong, in a way only the second review saw.**
   I gated on the context's `answered`, which is `!isLoading && states.size > 0`
   — **batch-wide**. A season past `VIEWER_MEDIA_STATE_MAX_REFERENCES` (50) is
   read as several chunks, so a sibling chunk resolving answers "yes" for a row
   whose own chunk errored. The gate has to be **this row's own entry**
   (`!signedOut && !entry`). Per-row is both more correct and less code.
3. **Defining an option can change behaviour even when it returns nothing.**
   `useScopedActionMutation`'s `onSuccess` gates on `options.viewerPatch` being
   **defined**, not on the patch being non-empty. So
   `viewerPatch: () => isSeasonScope(scope) ? {} : { watched }` gave a *season*
   mark-watched a settled `writeViewerMediaState(viewerFieldsOf(...))` it never
   had — `watchlisted/liked/rating/hasReview` onto the season's row — plus an
   `onMutate` rewrite of every matching chunk for no state change. The fix is to
   withhold the option, not to empty it: build the options object conditionally.
   **Generalisable: when a shared helper branches on `if (options.x)`, an
   `x` that returns a no-op is not a no-op.**
4. **`CONTEXT.md`'s `_Avoid_` lines are enforceable standards, not flavour.**
   Media Scope's reads `_Avoid_: Scope alone, Context, Media Target,
   Season/Episode "params"`. My toggle took `showId`/`seasonNumber`/
   `episodeNumber` as three primitives and rebuilt the object the screen had
   already built for its batch. One `MediaScope` prop, and one `episodeScopes`
   Map on the screen that the batch and the rows both read, so they agree by
   construction rather than by two filters agreeing.

## Worth knowing for the next mobile ticket

- **`props.disabled` is not on the host element.** RN's `Pressable` destructures
  `disabled` out and merges it into `accessibilityState`, so assert
  `props.accessibilityState.disabled`. `props.className` *is* passed through
  verbatim in this jest environment, so a NativeWind class is directly
  assertable.
- The season screen's sibling test `season-detail-community-counts.test.tsx`
  mocks `@tanstack/react-query` wholesale, so anything you add to that screen
  that needs a real query client must tolerate its fixture (here: an empty
  episode list). A new screen test that needs a real client is a new file.
- `CONTEXT.md` already carries Media Scope, Media Reference and Viewer Media
  State, and its Viewer Media State entry already documents why a season writes
  no `watched`. **No glossary addition was warranted** — this ticket settled no
  new term, it just obeyed three existing ones.
