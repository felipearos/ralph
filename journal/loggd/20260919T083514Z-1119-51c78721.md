## READ THIS FIRST: a mutation test that outlives its timeout leaves the mutant in your tree

The #1118 journal already warns that "a background jest run that times out can leave your mutant in the tree." It happened again, one iteration later, and the reason is worth writing down properly because avoiding it is not "be careful".

I ran two mutants in one compound command — mutate, test, `git checkout HEAD -- <file>`, repeat. The first pair finished; the second pair's jest run crossed the 600s tool timeout and was backgrounded **mid-command**, so the restore had not run yet. `git status` showed `M mobile/hooks/useNotifications.ts`: a live mutant, sitting in the tree, at the exact moment I was about to commit and push.

Two things made it survivable, and both were deliberate:

1. **I had committed before mutating.** So the restore was `git checkout HEAD -- <file>` against a known-good commit rather than against nothing, and losing the working copy cost zero.
2. **I checked `git status` before trusting the run's output**, rather than reading the last line and moving on.

The cause is contention, not slowness in my own work: `pgrep -fa jest` showed the **ralph-loop worktree running its own jest at the same time**. That is the host-RAM starvation the backlog already knows about, and it means a mobile jest run's wall-clock is not a property of my suite. **Do not put a mutate/test/restore cycle in a compound command with a timeout.** One mutant per tool call, restore in its own call, and `git status` between each.

## The one bug both review axes found, independently, again

`ShowGroupHeader` holds the unfollow mutation's state — and FlashList **recycles cells**. The standards axis found it by pattern-matching the sibling `DismissibleNotificationRow`, whose doc block literally says "Give this a `key` of the notification's id at every call site. FlashList recycles cells…", and noticing that my new header had no `key` while the row beside it did. The spec axis found it from the other end, by reading `RenderStackManager.ts` and working out that FlashList v2 reuses a render-stack key for a different `stableId` once the old index leaves `engagedIndices`, then constructing the scenario: unfollow Severance at index 2, scroll until Breaking Bad's group lands in the recycled cell, and Breaking Bad's header renders disabled and labelled "Unfollowed Breaking Bad" without a request ever having been sent for it.

That is three iterations running where the two axes converged on one defect from different evidence. The generalisable part is not "FlashList recycles": it is that **this repo had already written the warning down, on the component directly beside the new one**, and the delegated executor did not read across. When adding a sibling to an existing component in a recycled list, the first question is what invariants the existing sibling's doc comment claims — they are almost never local to it.

## The decision worth arguing with: a group key needs an ordinal, not just a label

I keyed a group's expansion on `${label}#${tmdbId}` rather than the web's bare `tmdbId`, so a show with rows under both "Today" and "This Week" expands each independently. Straightforward.

The spec axis then pointed out that the label alone is not enough either, and the reasoning is one I would not have found: `getTimeGroup` is monotone in time **except for future-dated rows**. A `created_at` ahead of the device clock is neither `isToday` nor `isYesterday`, but it *is* `isThisWeek` — so the bucket sequence becomes `This Week, Today, Yesterday, This Week`, two buckets spelled identically, sharing one key. Expanding one expands the other, and `keyExtractor` emits a duplicate.

Clock skew is the realistic trigger, so this is reachable in production and cost one integer to fix (`${bucketIndex}#${label}#${tmdbId}`). The lesson: **"the list is sorted, so equal labels are contiguous" is an assumption about the data, not about the code**, and a bucketing walk should carry its own ordinal rather than re-deriving identity from a value it does not own.

## CI: the E2E job failed without running a test, and it was not the diff

Build 1811's Playwright job exited 1 on `Supabase Auth was not stable within 120000ms after 239 attempts ... HTTP 502 x239`. **No test ran.** Before touching anything I checked the neighbouring builds, which is the cheap move the backlog keeps re-learning: build **1812** started two minutes later on `rafa/1084` and its E2E **passed**, so the hermetic stack was healthy and 1811 lost a race rather than hitting an outage. `docker ps` showed the shared `supabase_*_loggd` containers up two days, and two root-owned `next start -p 3000` processes belonging to the Buildkite agent still alive — the documented port-3000/shared-stack collision, not something my branch caused.

Two things that cost time and are worth knowing:

- **The Doppler Buildkite token cannot retry a job.** `PUT .../jobs/<id>/retry` answers `403 {"message":"Your access token doesn't have the write_builds scope"}`. This is the same shape as the known `read_pipelines` gap — and note the failure mode when you pipe it through a JSON parser: the fields come back `None`, so it *looks* like an empty success. Print the HTTP status.
- **`buildkite/loggd` is a commit status, not a check run**, exactly as the #1112 journal says of `Vercel`. There is nothing to re-request and no API retry available, so the only retrigger is a new commit. An `--allow-empty` commit explaining the infrastructure failure is the honest version, and the `.claude/reviewed` marker is sha-keyed so it must be re-touched for the new head.
