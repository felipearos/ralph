## READ THIS FIRST: `gh pr checks` in a 60s poll loop exhausts the account's
## GraphQL budget for every loop at once

Two `gh pr checks 1171` calls a minute, from a Monitor, plus three sibling loops
doing the same, and the account hit `API rate limit already exceeded for user ID
21047325` — on GraphQL, which is what `gh pr checks` and `gh pr view --json`
use. It took out `gh pr comment` too, so I could not even enqueue.

**The fix that works: poll REST, not GraphQL.** They are separate budgets, and
REST sat at 5000/5000 the entire time GraphQL was exhausted.

```bash
gh api "repos/felipearos/loggd/commits/$(git rev-parse HEAD)/status" \
  --jq '.state, (.statuses[] | "  \(.context): \(.state)")'
gh api "repos/felipearos/loggd/pulls/1171"          --jq '"\(.state) \(.merged)"'
gh api "repos/felipearos/loggd/issues/1171/labels"  --jq '[.[].name]|join(",")'
gh api "repos/felipearos/loggd/issues/1171/comments" -f body="$(cat body.md)"
```

`gh api rate_limit --jq '.resources.core.remaining, .resources.graphql.remaining'`
tells you which budget you are actually short of. Poll at 90s, not 60s, and
prefer one REST call per tick over `gh pr checks`'s several.

## A mutation that cannot be killed is sometimes a dead field, not a missing test

I mutated `showId: context.scope.tmdbId` → `showId: 0` expecting a failure, and
23 tests passed. The reason is not weak coverage: **`ReviewCardData.showId` is
declared and read by nobody** — not `ReviewCard`, not any of its seven other
producers. Writing a test to pin it would have been writing a test for dead
code. Check `grep -n "\.showId" ` before you treat a surviving mutant as a
coverage gap; the honest outcome was to leave the field alone (removing it
touches six unrelated call sites) and say so in the PR.

## What the two axes found that I would have shipped

Both axes ran as Opus `Agent` calls. Codex was out of review quota this window,
so this was the only review the PR got — the case the pre-PR hook exists for.

1. **The tab strip could grow a tab under the member's finger** (spec axis,
   confirmed). The block runs three independent React Query reads and painted on
   whichever landed first. Popular at 200 ms → block appears, member starts
   reading; Friends at 600 ms → a Friends tab materialises *to the left* of the
   active one, becomes active, and the three cards swap. The web has no such
   window because `MovieReviewsSection` awaits one server read and hands
   `ReviewTabs` all three lenses at once. Fixed by painting once, after every
   enabled read has settled. **A disabled query does not block this**: in
   TanStack v5 `isLoading = isPending && isFetching`, and a disabled query is
   pending-but-not-fetching, so the signed-out friends read reports `false`.
2. **A follow never refreshed a title's own friends feed** (standards axis,
   confirmed). `useUserFollowMutation` invalidates `["reviews", "friends"]`; the
   scoped feed's key is `[prefix, tmdbId, "reviews", season, episode, filter,
   limit]`, which that prefix does not match. Follow someone, open a show they
   reviewed, and the Friends tab stayed pre-follow for the whole 5-minute
   `staleTime`. The mismatch predates this branch — putting a friends feed on
   four always-visible detail screens is what made it matter. Fixed with a
   predicate on `queryKey[2] === "reviews" && queryKey[5] === "friends"`.
   **Check the negative assertions when you add a predicate**: the existing test
   pins `["profile","ana","reviews","all"]` as NOT invalidated, and that key has
   `"reviews"` at index 2.
3. Both axes independently flagged `title={show?.name ?? ""}` on the season and
   episode screens — before the show read lands, `mediaScopeLabel` yields
   `" Season 2"`, so the More button announces "More Popular reviews of  Season
   2" and every card gets an empty heading. The `?? ""` is the established
   pattern (`FriendsActivityStrip` does the same), but the block is the first
   consumer that *renders* the value, so it is the first place it shows.

## The deliberate cost: three parallel reads per detail screen

"A tab appears only once its read has content" requires all three reads, so
opening a show now issues three `?filter=…&limit=10` requests to render three
cards. It is inherent to the web-parity behaviour, not an oversight, and the
responses are the subpage's own cache entries so some of it is recovered on
More. If this ever shows up in the Vercel runtime bill, the lever is a single
server read answering all three lenses, as the web's `getShowReviews` does —
that is a server ticket, not a client fix.
