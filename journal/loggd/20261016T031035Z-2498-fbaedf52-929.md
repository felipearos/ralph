## Harness bug found: `add-blocker` is broken, 422 on every numeric target

The first plan used the `add-blocker` op for the sibling edge. It failed deterministically, twice:

```
triage-apply: stopped at 2498-a1-edge-2499: gh: Invalid request.
Invalid property /issue_id: `"5877389442"` is not of type `integer`. (HTTP 422)
```

`triage/apply.ts:230-232` posts `-f issue_id=${id}`, and `gh api -f` sends every value as a
**string**; GitHub's issue-dependencies endpoint wants an integer, so it needs `-F`. This is not
transient and re-running the plan cannot clear it — exit 1 every time, and because ordering puts the
edge before the comment, **zero writes landed** on the first two attempts (the contract held: I
verified #2498 had only the claim comment and #2499's `Blocked by` was unchanged). Fix is a one-
character change, `-f` → `-F`, at `triage/apply.ts:231`.

**Workaround, and it is a fair one:** `Blocked by` is one of the five managed sections, so the edge
went in as a `set-section` replace on #2499 — `- #2479` / `- #2498` — which is what the frontier
parses anyway. Next triager wanting a native dependency should expect the same 422 until the harness
is fixed.
