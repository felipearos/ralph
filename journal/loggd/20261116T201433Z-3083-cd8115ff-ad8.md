## The three calls past the mapper's literal overlap map

1. **One nine-ticket notification lane, not the mapper's G1/G2 + separate job.** The
   decisive fact is that this repo keeps a *per-type record* in six places (the bell and
   push maps in `notify.ts`, the `push-payload.ts` switch, two icon `Record<NotificationType>`
   tables, and the `FIXTURES`/`ROUTES`/`EXPECTED_KIND` records in the shared and mobile
   tests) and each must cover **every** type. So #3084 and #3254, each adding types, red
   each other's own tests if they run together — this is not a merge-conflict argument but a
   failing-test argument, which is stronger. #3089's created-at change sits in the same
   `notify.ts` hunks #3254 edits; #3092/#3279 edit the same two mobile test records.
2. **`src/lib/hardcover.ts` was left as a cross-group file rather than used to merge.**
   #3086, #3260 (reads) and #3089, #3266 (the job) all append a batch fetch there. Merging on
   it would have produced one lane of sixteen — two thirds of the spec. The mapper itself said
   the edits are appended functions, so I wrote fence 2 instead: append-only, no ticket in
   this tree may rename or re-shape an existing export in that module. **This is the
   judgement call most worth revisiting** if a coder reports a real conflict there; the
   precedent in #3028 went the other way, but there the routes *reshaped* `hardcover.ts`.
3. **#3270 is in `book-follow-server`, not with the settings UI.** Its live collision is
   `account-export.ts` with #3085 and #3258. Its tie to #3254 on
   `src/lib/notification-preferences.ts` is not live: #3254 is its blocker, so they are never
   in flight together. Same reasoning as #3063's #3265 call — blocker edges, not just path
   sets, decide which collision is live.

## A tool note

`section` is refused with two messages per op. The dry run caught it, cost nothing, and is
the reason to always dry-run first.
