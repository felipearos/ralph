## What shipped

`src/server/imports/generic-csv.ts` no longer imports `~/server/db` or the
schema. It parses, resolves each row to a Media Reference, adapts rows into
`LibraryMergeEntry`s (watched, not watchlist, a per-media log when the row has a
rating or review text), plans, publishes the outcome, runs the Import Job fence
(`beforeWrite`), reports `writing`, then applies. Contract mapping per #761:
inserted → inserted; updated → updated + unchanged; skipped → unmatched +
rejected; rejected entries land in `errors` by label.

ordering. `generic-csv.release.test.ts` runs on the PGlite embedded database
with literal review scores (`"4.8"`, `"4.3"` — the `decimal(3,1)` column rounds
half away from zero), `rewatched`, a second-upload no-op, and a duplicated new
title producing one row and one review.

## The one thing that cost the iteration

**The first CI run was red on a test nobody in the brief or the reviews looked
at: `src/app/api/import/csv/route.test.ts`.** It stubbed `~/server/db` with
select/insert/update only and the schema with two tables, so the run's new
`applyLibraryMerge` hit `db.transaction is not a function`. It is a transport
test, so the right fix was to mock `runGenericCsvImport` whole, not to teach
the stub a transaction.

Rule for the remaining #761 siblings (#779 IMDb, #780 Letterboxd, #781
watchlist upload): **before opening the PR, grep every test that mocks
`~/server/db` and imports the run you changed**, directly or through a route.
`grep -rl "imports/<run>" src --include='*.test.ts'` then check each for a
`vi.mock("~/server/db"`. The `route.test.ts` under `src/app/api/import/<source>/`
is the one that will bite each time. A wider local gate — `bun run test
src/server/imports src/app/api/import` — would have caught it in four seconds.

## Two things about this host, for the next iteration

- **The worktree was moved to detached `origin/main` between my turns** (the
  previous turn ended without a sigil while blocking on CI in a background
  task, and the recovery turn found HEAD at main's tip with the branch intact
  and pushed). Nothing was lost, but a full-suite run I did right after was
  against main's code, not the branch's, and I nearly read it as green. Check
  `git branch --show-current` before trusting any local result in a recovery
  turn.
- **Do not put the §5.4 CI wait in a background task.** The tool's foreground
  cap is 10 minutes, a build here is 7–9, so a foreground poll loop with a
  ~570s deadline and a second call if needed is the shape that works. Also,
  `gh pr checks` reports `fail` on a build that is still running once one job
  fails; poll the commit status description until it says `passed` or
  `failed (…)`.
