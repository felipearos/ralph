## What was wrong with the ticket, and what I changed

**It claimed to be unblocked and was not.** The body said `## Blocked by: None. Builds
on #2706's helpers.` But `refuseBlockedViewer`, `cachedSubjectBlockedViewer` and
`refuse-blocked-viewer.conformance.test.ts` exist nowhere under `src/` at
`origin/main` (`db2055416`) — `profile-request.ts` exports only
`cachedGetProfileByUsername`, `cachedGetViewerId`, `isProOwner`. All three arrive with
#2706, which is still open with `ralph-wip` (PR #2777). Every single criterion called
one of them, so a coder taking this today would have had nothing to call. `Blocked by`
now names #2706.

**Half the stated scope was already implemented, by a different mechanism.** AC1 asked
the `list/**` pages to call `refuseBlockedViewer`. They do not need to:
`viewerIsInListAudience` (`src/server/queries/list-audience.ts:53`) and the SQL
predicate `listReadableBy` (`:120`) both apply `blockExistsBetween` in either
direction; the six List layouts `notFound()` on a null `readGatedList`; and
`list/{book,track}/[slug]/{page,comments/page}.tsx` refuse on their own
`cachedGetListBySlug(..., viewerId)` rather than leaning on the layout. That landed in
#2661/#2689. The criteria now ask for a regression test instead of a reimplementation.

**The real remaining gap is the 43 member-title pages** under
`src/app/[username]/{movie,show,book,album,track}/[slug]/**` (incl. season and episode
trees). They resolve the subject and never ask about the block, so a blocked member
can read `/<blocker>/movie/<slug>/r/1` today. The criteria now name the seams exactly,
because the obvious reading of the old AC1 ("use the shared helper") is wrong twice
over: `MovieUserPageLayout` is synchronous and streams the page body beside itself
under its own Suspense, so the movie seam is `getMovieUserPageData` in
`movie-user-page-request.ts` and not the layout; and the other four
`<Type>UserPageLayout.tsx` resolve the user **twice**, once in the exported
`get<Type>UserPageData` that `diary`/`lists`/`reviews` bodies call directly and once
inside the layout component. ~15 pages (every `(review)/page.tsx` and
`r/[reviewNumber]/page.tsx` across the five types, plus the episode `likes` page) reach
no seam at all, and **no seam covers `generateMetadata`** — each page runs its own
inline `profiles` query.

## The one thing I did NOT decide

The six List layouts' `generateMetadata` reads the List as a **signed-out** viewer on
purpose (`list/show/[slug]/layout.tsx:59-67`, quoting #2661: "reading the viewer here
would make every List route's metadata request-time"). So a blocked viewer's `<head>`
still carries a public List's name, description and OG image while the body 404s —
which is *not* the answer an unknown username gets, and so is a genuine residue of the
original issue's "the same not-found, body and metadata".

**ADR 0002 and #2661 point opposite ways, and no documented rule settles the
trade-off** (symmetry vs. every List route's metadata becoming request-time). Per the
role's rule I did not decide it from judgement: it is carved out of scope in
`What to build`, the widened conformance scan allowlists those six `generateMetadata`
blocks with the #2661 reason, and the triage comment asks a human to rule. If symmetry
wins, that is a follow-up ticket and the allowlist entries are where it starts.
No follow-up issue was filed — that call belongs with the operator.

Also worth a human's line: #2706's `docs/adr/0002-blocks-are-symmetric-on-reads.md`
says the List pages "still read without this refusal; #2776 extends it to them".
That is now inaccurate on both counts. Whichever PR lands second should fix it.

## Harness friction — `add-blocker` is broken

`add-blocker` fails **deterministically** with HTTP 422 from GitHub:

```
Invalid property /issue_id: `"5963564861"` is not of type `integer`
```

It sends the resolved node id as a *string* where the issue-dependencies REST endpoint
wants an integer. The apply exited 1 after the three `set-section`s had landed. Exit 1
says "re-run, the op ids make it idempotent" — but re-running cannot help here, the op
can never succeed. I dropped the op and re-ran: the three applied sections were skipped
on their opIds and the labels plus comment landed (`3 writes, 3 already done`).

**For the next iteration:** the native dependency edge is redundant insurance — the
frontier derives blockers from issue prose too, and `## Blocked by: #2706` carries it.
But until this is fixed, **no triage plan should include an `add-blocker` op**; it will
cost you a partial apply every time. Worth an issue on felipearos/ralph.
