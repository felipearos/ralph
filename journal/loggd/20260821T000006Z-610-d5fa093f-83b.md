**The one thing that turned out to be substantive rather than cosmetic.**
`sourcemaps: { disable: true }` is not a cosmetic flag. Inside the installed
`@sentry/nextjs`, `getFinalConfigObjectBundlerUtils.js:170` short-circuits on it
before reaching `incomingUserNextConfigObject.productionBrowserSourceMaps = true`
— so the option is the *only* reason Next was emitting client source maps at
all. A local `bun run build` went from emitting them to zero. Worth checking a
vendor's source for this class of change: "we set a flag that means we do less
work" is a claim, and the mechanism is where you find out whether it is true.
(The 1,863 `.map` files under `.next/server` are Next's own server build and are
unrelated.)

**Both review axes converged on the same defect, from opposite directions, and
it was the one that mattered.** The analytics conformance test walked only
`src/**/*.ts(x)`. Verified with probes: a `.js` helper in `src/`, anything in
`packages/shared`, anything in `.storybook/`, and a root-level `.mjs` could all
import `@vercel/analytics` ungated with the suite green. Stories 10 and 14 claim
it is *impossible* to add a bypassing tracking call; the assertion as written was
narrower than the property it advertised, which is worse than no assertion
because a reviewer trusts it. Both walks now start at the repository root with
the same extension set (`.ts .tsx .js .jsx .mjs .cjs .mts .cts`) and a skip set
holding only generated trees.

Two smaller versions of the same "scans less than it claims" failure, both fixed:
the manifest check looked up `patchedDependencies['@vercel/speed-insights']`, but
bun keys that block `name@version`, so a patched entry was invisible — it needs a
prefix match. And the walk used `statSync`, which follows the **eighteen
symlinks** `mobile/` carries into `mobile/.agents/skills/`; one dangling link
would have surfaced as an unattributable ENOENT inside the Speed Insights
assertion. `lstatSync` and skip symlinks.

**Write the sensitivity probe, always, and probe the gap you think exists.**
Every claim above is "verified with probes" because a passing conformance test
proves nothing on its own. The probes took two minutes and found four real holes.

**What an import-site assertion cannot buy, now written in the test's header.**
A re-export from a permitted module (`export { track } from "@vercel/analytics"`
inside `lib/analytics.ts`) keeps the import-site set at exactly two files while
handing every component an ungated `track`. So does a hand-rolled `fetch` at the
collection endpoint, or a computed specifier. The test is still worth having, but
its header now names those so nobody reads it as a total guarantee. Good default
for conformance tests generally: say what you cannot see.

**Documentation the change falsified, all of it found by review, none by me.**
`.env.example` told a new contributor both packages were "installed and
configured in src/app/layout.tsx" — neither true even before this ticket, and
precisely the re-introduction vector the new test exists to block.
`ARCHITECTURE.md` §7 claimed source maps are uploaded and omitted the variable
that now controls it. `docs/todo/HOSTING_ANALYSIS.md` listed the package as live.
When a ticket removes a thing, grep the whole tree for its name and read every
hit — the manifests and modules are the easy half.

**A latent hole documented rather than fixed.**
`@sentry/bundler-plugin-core` loads `.env.sentry-build-plugin` and
`Object.assign`s it onto `process.env` *after* `next.config.js` has evaluated the
decision, so a token supplied only through that file gives the plugin upload
credentials with nothing to upload — the exact mirror bug the module's own doc
comment says one input makes impossible. Latent, because Vercel supplies a real
environment variable. The doc comment now states it and says explicitly not to
"fix" it by reading the file from the module: the point of that module is that it
reads nothing.
