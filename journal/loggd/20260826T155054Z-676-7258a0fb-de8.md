## The design decision, and why it is not the obvious one

The obvious fix for "a member can set `role` on their own profile row" is a
**column-level grant**: revoke the table-wide UPDATE, re-grant
`UPDATE (bio, full_name, …)` to `authenticated`. That is what the spec's wording
("a narrow trusted contract") reads like at first, and it is wrong here.

`grep -rn 'from("profiles")' src mobile` finds **four** call sites and every one
is a `.select`. Nothing in the product — web, mobile, `e2e/`, `scripts/`,
`.storybook/` — writes this table through a Supabase client. Every profile
change already travels through server code over Drizzle as the database owner
(the settings write in `src/server/queries/profile-write.ts`, plus onboarding,
notification preferences, the avatar route), and the sign-up row comes from the
`SECURITY DEFINER` `handle_new_user` trigger, which these grants do not touch.

So a column allowlist would grant a capability nobody uses, and it would have to
be **extended by hand for every new protected column** — the exact drift the
ticket's "fail closed for future protected columns" criterion exists to prevent.
Revoking the write privilege outright fails closed for every column a later
migration adds, for free. Migration `0029` revokes
`INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER` from `anon` and
`authenticated` and drops `profiles_insert_own` / `profiles_update_own`.
`SELECT` is untouched — that is #675/#677.

**#675 and #677 inherit a consequence of this.** `expectWriteDenied` accepts the
silent-refusal shape (no error, no rows) only against an `unchanged` witness,
because that shape is *also* what a write that succeeded against a row the actor
may not read back looks like. Right now every denial here arrives as an explicit
`42501` and the witness never fires. The moment those tickets filter the
`RETURNING` projection on `profiles`, the witness becomes load-bearing — and a
payload equal to what is already stored defeats it, because a landed no-op write
leaves the row byte-identical and `profiles` has no `updated_at` trigger. Both
review axes found this independently. It is why the column-enumeration test
carries `TAMPER_VALUES` rather than writing each column's stored value back.

## The one todo that was replaced rather than flipped

`it.todo("#676: a member can still edit their own bio through the narrow profile
contract")` could not become the test its title describes. The contract is
`updateProfileForUser`, server-side, and `security/README.md` forbids importing
from `src/` — a harness that reached into a server action to prove edits still
work would trade away the property that makes every denial in it meaningful. It
is now an assertion that the owner cannot edit their own bio *over PostgREST*
(the transport this ticket closes) with a comment naming where the positive
control lives. `security/README.md` gained a paragraph legitimising that move,
since it is the first case.
