## Read this first if you are the next iteration

**Three things about this host, in descending order of how much time they will
cost you.**

1. **`/tmp` is a 16 GB tmpfs and it filled up mid-iteration.** Every tool call
   that produced output started failing — `echo alive` returned exit 1 with an
   empty result, `git status` exited 128, `df` printed nothing. The tell is
   that a command with **no** output (`true`, `:`) still succeeds while any
   command that writes one **fails**: the Bash tool writes its result to
   `/tmp`, and that write is what is failing. Vitest names it honestly one
   layer down — `Unknown system error -122, write` is EDQUOT.
   The cure is a command that itself prints nothing:
   `rm -rf .next /tmp/<your logs> >/dev/null 2>&1; exit 0`. Removing this
   worktree's `.next` was enough. **`/home` had 341 G free the whole time** —
   do not go looking there. The standing occupants are
   `/tmp/loggd-feed-postmerge` (5.7 G) and `/tmp/pytest-of-faros` (4.3 G),
   neither this loop's; I left them. **Do not redirect a `bun run build` log
   into `/tmp`** — that is what I did, twice, and the cron routes' PPR bail-out
   stack traces make it enormous.

2. **Something outside this session moves HEAD in this worktree.** The reflog
   shows `checkout: moving from rafa/779-… to origin/main` at 01:12 and back at
   01:17, neither issued by me. My first commit landed on the **detached** HEAD
   in between, and the move back to the branch silently deleted the new
   untracked test file and reverted two others. Nothing in `ralph/*.sh` or
   `ralph/*.ts` does this (I grepped); it predates this iteration —
   `HEAD@{4}` and `HEAD@{5}` have the same shape. **Check
   `git branch --show-current` immediately before and after every commit**, and
   if a commit vanishes, `git reflog` still has it: mine fast-forwarded back

3. **Never write `git checkout HEAD -- <file>` to undo a mutation test.** It
   restores the last *commit*, not the state you were in, so it silently
   deletes every uncommitted change in that file. I did this twice and had to
   reconstruct `imdb.ts` from my own transcript the first time. Copy the file

## The ticket

`runImdbImport` stops touching `watch_status` and `review`. It builds
source-neutral entries — a whole Media Reference, a watched flag, a watchlist
flag, a label, and at most one **per-media** log — and hands them to
`planLibraryMerge` / `applyLibraryMerge`. `imdb.ts` now imports nothing from
`~/server/db`.

**Do not pre-fold the entries in the source.** The old run folded a rated row
and a watchlist row for one title into one `wsData` entry before writing. The
merge already folds per Media Reference (`watched ||`, `watchlist ||`), so the
run hands over **one entry per resolved row** and deleting the local fold is
part of the switch. #780 will want the same shape.

**Counts.** `inserted` → `inserted`; `updated` → `updated + unchanged`;
`skipped` → unresolved **rows** + `rejected`. That keeps every member-visible
number where it was: a replay used to count every touched row as `updated`, and
now counts it as `unchanged`, which the sum absorbs.

## The finding both axes found, and it was my brief that caused it

I told the executor to append the merge's rejection messages to **both**
`errors` and `unmatched`. Both review axes came back with the same objection,
independently, and they were right: `packages/shared/src/imports.ts` defines
`unmatched` as "the subset that reached title resolution and matched nothing",
and a rejected entry **matched**. Worse, `summary.failures` is the same list
under IMDb's own name and the screen labels it with `tmdb.failed` — so a
rejection-only run would have rendered an empty failure list with a zero
header, and a mixed run would have under-counted it.

`unmatched` and `summary.failures` are now TMDB-only; rejections travel in
`errors` and in `skipped`. **The lesson is about briefs, not about the
executor**: it implemented what I wrote, faithfully, and neither of us read the
contract's own docstring. Read `packages/shared/src/imports.ts` before writing
a brief that touches those three arrays.

## The two axes disagreed once, and the spec axis was right

Standards said the reachable rejection was an out-of-range score; Spec said
`imdbRatingToScore` clamps to `[0.5, 5]` and the reachable one is the date. I
had already written a comment asserting the first. Ten seconds of `bun -e`
settled it: `imdbRatingToScore(11) === 5`, and `Date Rated` is trimmed and
`.slice(0, 10)`'d but **never validated**, so `new Date("not-a-dateT12:00:00Z")`
is an Invalid Date that `z.date()` rejects. That is now a release-test case.
**When two reviewers disagree on a fact, run the fact.** Neither report is
evidence.

## "Batched, not per-row" is a mechanism AC, so I asserted the mechanism

The third AC says existing-row updates must be batched. The merge shipped in
#777 with a `for (const update of updates) await tx.update(...)` loop, so
satisfying the AC meant editing **#777's module**, which I did knowingly: group
by the `(watched, watchlist)` pair, one `inArray` statement per group per 200-id
chunk. The guard is a function of those two flags alone, so every row in a group
shares it — the transitions are identical.

The file's own header says to assert rows and never statements, and that rule is
right for the conflict table. It cannot express this AC: one UPDATE per group and
one per row apply the same 300 transitions. So the test counts statements, and
says in a comment that it is doing so on purpose. Getting the spy right took a
detour worth writing down: **`vi.spyOn(client, "query")` sees nothing**, because
PGlite hands `db.transaction`'s callback a separate `Transaction` object with its
own `query`. Spy on `client.transaction` and wrap the `tx` it is about to pass on.
Reverting to per-row fails the test with `expected 300 to be less than 10`.

## Mutation-testing found nothing wrong, which is the point of doing it anyway

Eight mutations, eight killed: the merge lowering status, the merge clearing the
watchlist, `skipped` dropping rejections, the summary reading counts instead of
totals, `updated` dropping `unchanged`, the log identity flipping to
per-viewing, rejections leaking back into `unmatched`, and the per-row loop. Two
weak assertions the Standards axis named — `toBeInstanceOf(Date)` on the undated
rating, and an empty-list `toEqual([])` that would pass if the merge were never
called — were replaced with a `before`/`after` bracket and a
`toHaveBeenCalledTimes(1)`. Both then had teeth.
