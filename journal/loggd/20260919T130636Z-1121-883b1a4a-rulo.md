## READ THIS FIRST: a plain `View` is not how you spell "inert" inside a row

The chips sit inside the notification row's own `Pressable`. The known trap,
documented on `NotificationFollowBack`, is that a **`disabled`** child declines
the touch (`Pressability` returns `!disabled` from
`onStartShouldSetResponder`) so the row underneath takes it and navigates. I
followed that advice and rendered the inert chip states as plain `View`s.

**A press on the settled `View` still reached this component's mutation** and
re-posted a write for an episode already watched. I have the run: `DBG post
[["/episodes",{...,"watched":true}]]` with the `View`, `DBG post []` with a
`disabled` Pressable, same fixture. I did not pin the path down — a later
reviewer read RNTL and RN and could not reproduce it from the tree either — but
the observation is reproducible and the fix is provable, so the code uses
`disabled` and a test pins it. **The generalisable bit: "has no onPress" is not
the same claim as "declines the touch". If you need inert, use the prop whose
job is inert, and mutation-test it.**

The follow-on is the interesting design point. `disabled` means the tap lands
on the row and opens the episode — which is *right* for the settled and
unanswered chips (the episode screen is where you unmark, and where an answer
this row lacks can be had) and *wrong* for the in-flight one, because the
mutation explicitly expects an impatient second tap. That one stays enabled
with a no-op `onPress` so it swallows the tap. Three inert states, two
different correct behaviours; the distinction is not decoration.

## The read I reached for first was a cache nobody fills

First implementation read watched state from `useMediaActionState(scope, {
enabled: false })` — a cache-only peek, no request per row. It typechecked,
every test passed, and it was wrong in the ordinary case: only the episode
screen and a poster's sheet ever write `mediaActionsQueryKey(<episode scope>)`,
so on a bell page the entry is absent, the code fell back to the mutation's own
`isSuccess`, and an episode the member had already watched was offered a live
"Mark watched".

The right read was already in the repo — `ViewerMediaStateProvider` +
`useViewerMediaStateFor`, exactly as `EpisodeWatchedToggle` uses it on a
season's episode list, one batched request per screen. **Checking what actually
*writes* a cache before reading it is the step I skipped**; "this key exists
and is free to read" is not the same as "something populates it".

`CONTEXT.md`'s Viewer Media State entry then decides the rest: absent is not
false, so the chip is dimmed and inert until *this row's* entry arrives, not
until the batch reports answered (a failed chunk would otherwise unlock its
rows on an answer that never comes).

## A chunk keyed on its own reference set blanks on removal

`useViewerMediaState` keys each chunk on the references it covers, and its
docblock reasons carefully about *appending* pages — earlier chunks stay
byte-identical, so a new page refetches at most the partial tail. **Removal
from the middle is the case that reasoning misses.** A bell page dismisses
rows; the reference set shrinks, the key changes, the new query has no data,
and every chip on the page falls to unanswered at once. Fixed with
`placeholderData: keepPreviousData` on the chunk query, which is also an
improvement for the grids that append.

Generalisable: **when a query key is derived from a collection the surface
mutates, enumerate insertion *and* removal.** A comment that only covers growth
is a comment that will be read as covering both.

## Gating on the read made a test racy, and the race was real

Once the chip waits for an answer, a test that pressed straight after the rows
rendered was pressing the *unanswered* chip — which falls through and
navigates. It failed as "does not navigate … Received number of calls: 1". Not
flake: the test was asserting against a state the member can genuinely be in.
`renderScreen` now waits for the deterministic state before handing the screen
back, and the wait differs per branch because the settled chip is deliberately
disabled and `toBeEnabled()` never comes true for it.
