## READ THIS FIRST: an expired claim lease does not mean the other loop is dead

This is the whole lesson of the iteration and it cost a full iteration of work.

#1120 carried `remo-wip` from 09:36:02Z. remo's lease expired at **10:10:30Z**.
The frontier reaped it and relabelled the ticket `ralph-wip` at 10:32:35Z, with
`obstructed: []`. Everything about that read as "remo died after claiming":
no `remo/1120-*` branch on the remote, no PR, no draft, and a claim comment
sitting alone on the issue for an hour.

**remo was alive the whole time.** It was working locally, unpushed, and
landed #1190 an hour later. The lease is a *heartbeat*, and a long iteration —
a slow executor, a stuck jest, a delegate timeout — outlives it without the
loop being in any trouble at all. Mine did exactly that this iteration: I ran
for over three hours.

What I actually checked in §0/§1 was the *published* evidence — remote
branches, PRs, labels — and there was none, because a loop that is mid-work
publishes nothing until it pushes. **There is no observable difference between
"died after claiming" and "still working, hasn't pushed yet."** The lease was
the only signal, and I trusted the frontier's reaping of it.

Concretely, for the next iteration:

- **A reaped lease whose issue still carries a claim comment from under an
  hour ago deserves suspicion, not confidence.** Read the claim comment's
  timestamp. remo's said 09:36Z; I claimed at 10:32Z. Fifty-six minutes is
  well inside one normal iteration here.
- The cheap check I did not do: `ps`/`pgrep` for the other loop's worktree, or
  `ls -la ../remo-loop/.ralph/logs/` for a recently-written brief or delegate
  log. Another loop's worktree is on this same host and its activity is
  visible from mine. I killed a stale jest in *my* worktree by exactly that
  method later in the iteration, so the tool was in my hand.
- Worth raising as a harness question rather than a habit: either the lease
  TTL is too short for the iterations this backlog now produces, or the
  frontier should not reap a lease whose issue carries a claim comment newer
  than the TTL. Three of my last four iterations ran longer than remo's lease
  lived.

I do not think §1 is wrong to trust the frontier. But "the frontier said
`obstructed: []`" is not the same claim as "nobody else is working this", and
I treated them as one.

## READ THIS FIRST: `git checkout -- <file>` eats uncommitted work, and mutation testing is when you reach for it

The #1119 journal says "commit before mutating". I read it in §0, then did the
opposite within the hour: I appended a new function to
`packages/shared/src/notifications.ts`, mutated it, and restored with
`git checkout -- packages/shared/src/notifications.ts`. The file was
**untracked-as-modified but the function was uncommitted**, so the restore
took it back to HEAD and deleted the function entirely. `grep -c` caught it
immediately; had I trusted a green test run it would not have.

The rule as I would now write it: **`git checkout HEAD -- <file>` is only a
restore if the thing you want back is in HEAD.** Commit first, then mutate —
not as hygiene, but because the restore command is a no-op-to-destructive
depending on state you have to remember to check.

## READ THIS FIRST: a hung mobile jest can be a stale watchman watch, not RAM

I lost roughly 40 minutes to jest runs that hung indefinitely on a suite that
takes 2.5 seconds. `free -g` showed 15 GB available, so the host-RAM
starvation note (#809) did not apply, and the process sat in `ep_poll` with
**no worker children** — stuck before spawning them.

The cause was in the warning I had already scrolled past:

```
watchman warning: Recrawled this watch 1 time, most recently because:
dir missing from internal state
```

The fix, and it was instant:

```bash
watchman watch-del '/home/faros/orca/workspaces/loggd/ralph-loop'
npx jest --watchman=false --runInBand <pattern>
```

Back to 2.5s. **Diagnostic that separates the two causes:** jest with zero
worker children is watchman/haste-map; jest with workers running slowly is RAM
contention. Check `pgrep -P <pid>` before reaching for `free`.

Separately, I found and killed a jest process from *a previous iteration's
executor in this worktree*, started 23:04 the night before and still resident
12 hours later — its tests had finished, it just never exited ("Jest did not
exit one second after the test run has completed"). **A timed-out
`delegate.sh` can leave a jest behind that outlives the iteration.** Worth a
`pgrep -fa jest` in §0 orientation; it is one line and it found real garbage.

## Measure the reviewer, too: a "vacuous assertion" finding that was wrong

The spec axis reported that `expect(mockPush).not.toHaveBeenCalled()` after
pressing a nested control "passes no matter what", because RNTL's
`fireEvent.press` stops at the first ancestor with an `onPress` and never
bubbles.

I probed it instead of accepting it — two throwaway nested-`Pressable` cases:

```
PROBE with-handler   outer: 0  inner: 1
PROBE no-handler     outer: 1
```

So the assertion is **real coverage**: remove the inner control's `onPress`
and RNTL walks up and fires the row's handler, and the assertion fails. The
finding was wrong. (The probe needs `await render(...)` — this project's RNTL
setup is async, and a sync `render` fails with the misleading "`render`
function has not been called" at the *next* line.)

Both axes are worth running and both were valuable this iteration — the
stale-prop defect was real and found twice. But **a review finding is a
hypothesis about behaviour, and the ones that assert what a *framework* does
are the cheapest to check and the easiest for a reviewer to get wrong.**
