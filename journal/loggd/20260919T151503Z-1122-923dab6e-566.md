## READ THIS FIRST: `git checkout -- <file>` ate the executor's only copy

The journal already warns about this and I did it anyway. I had edited
`mobile/lib/notification-routing.ts` with a python patch based on a
*mid-run* file-change notification, then ran `git checkout` on it to undo my
patch — which reverted the file to `origin/main`, deleting the whole delegated
implementation, because the executor's work was never committed.

What saved it: the harness's "changed on disk" notifications had printed the
file's new content nearly in full, so I reconstructed it from my own context
plus the unchanged original. That is luck, not a recovery procedure.

Two rules that would have avoided it outright:

1. **Commit the executor's diff the moment you have reviewed it**, before any
   edit of your own. A commit turns every later mistake into `git restore
   --source=HEAD~1`.
2. **Never patch a file from a notification's rendering of it.** Those
   renderings elide unchanged regions (`...` in the middle). Read the file.

## What #1122 actually needed (most of it already existed)

#1117 had landed the shared resolver, the per-type push payload and
`registerNotificationResponseRouting`, and its test file already covered ten of
the fourteen `NOTIFICATION_TYPES`. So the ticket reduced to three things:

- **The gated hold.** `NotificationRouting` was mounted inside
  `OnboardingGate`'s children, so on the onboarding branch no navigator existed
  and the tap vanished; on the signed-out branch it pushed a destination the
  member could not act on. Moved it to the gate's `open()` and added
  `PendingIntentPushCapture` to `closed()`. The gate is now the only thing that
  decides which of the two runs, which is the same shape the link capture
  already had.
- **Double navigation.** The gate opening remounts routing, which replays
  `getLastNotificationResponseAsync` — the same response the capture just held.
  A module-level `capturedResponseIds` set makes the routing side skip `push`
  for a claimed identifier while still running `opened`, so the resume owns the
  navigation and mark-read still happens on the gated path.
- **Mark-read on open.** Matched by notification *link*, not id. That is forced
  by the server: `notify.ts` groups one push payload across every recipient
  (`JSON.stringify(payload)` is the group key), so a per-member notification row
  id in the payload would turn one dispatch into hundreds. Anyone tempted to
  "just add `notificationId` to the payload" should read that loop first.

## Two review findings that were real defects, not style

The local two-axis review (both Opus) earned its keep:

1. **The capture claimed responses it had not held.** `rememberPendingIntent`
   silently writes nothing when `parseIntentDestination` refuses the href, but
   the claim was added unconditionally — so the routing side then skipped a tap
   *nobody* was holding. Today the only such href is the import target
   `/settings/data?job=…` (unreachable: imports are bell-only), but it was a
   trap armed for the next target outside `routeFromSegments`. Fixed by making
   `capture` return whether it held the destination and claiming only on true.
2. **The per-type test was exhaustive by hand.** A fifteenth enum member fails
   the shared resolver's `switch` at build time but would have slipped past the
   test silently. Replaced the fourteen hand-written happy-path cases with one
   `it.each(NOTIFICATION_TYPES)` over a `Record<NotificationType, …>` table, so
   the exhaustiveness is now the compiler's problem.

Also renamed `markNotificationsReadForDestination` → `…ForLink` and
`PushIntentCapture` → `PendingIntentPushCapture`: `CONTEXT.md`'s
**Notification Target** entry lists "Notification Destination" under `_Avoid_`
and names *notification link* as the per-client path, and "Push Intent" was a
coined synonym for a glossary term that already exists. Worth doing in the same
PR — the standards axis will find it every time otherwise.

**Mutation-tested both claim guards** before trusting them: deleting the
routing-side skip fails 2 tests, deleting the capture-side dedupe fails 1.
