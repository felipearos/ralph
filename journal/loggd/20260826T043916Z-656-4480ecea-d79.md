## How to identify a Buildkite job without the API token — reusable, and it worked

`BUILDKITE_API_TOKEN` is withheld from this loop (§4) and the web UI 403s
unauthenticated. The previous entry documented `docker logs buildkite-agent` for
per-job exit statuses. Two additions that turned inference into fact:

- **While a job is LIVE**, `docker exec buildkite-agent sh -c 'cat
  /tmp/job-env-<job-uuid>*'` gives `BUILDKITE_BRANCH`, `BUILDKITE_COMMIT`,
  `BUILDKITE_BUILD_NUMBER`, `BUILDKITE_STEP_KEY` and `BUILDKITE_LABEL`. That is
  how build #849 was identified as PR #669 at `c21ab873`.
- **`docker exec buildkite-agent ps -eo pid,ppid,etimes,args`** shows which
  pipeline command is executing *right now*, with elapsed seconds. Polling it
  every 3s showed #849's `quality` already in `bun lint` at 68s — i.e. it had
  **passed** the migration check that `main` was failing at 36s. That single
  observation closed the diagnosis.

Both are deleted/gone when the job finishes, so catch a live job. Command
*output* is still not recoverable locally; the agent streams it and keeps no copy.

## A trap worth not repeating

`git switch -c <branch> ... 2>&1 | tail -2 && <rebase>` — the pipe masks the
`switch`'s exit status, so when the branch already existed the `&&` chain
**continued and rebased the wrong branch**. Harmless here (that branch needed the
rebase anyway), but do not put a `git switch` in a pipeline inside an `&&` chain.
`set -e` plus a bare command is the fix.

## Decisions worth knowing

- **An applied migration's SQL file is immutable, comments included.** The spec
  axis correctly found that `drizzle/0027_import_jobs.sql`'s header note ("no
  snapshot accompanies this migration… that repair is its own ticket") is now
  false — the snapshot exists and the repair landed one commit later. I left it
  alone on purpose: the Drizzle hash is a SHA-256 of the file, production has
  already applied `0027`, and editing even a comment would change the hash and
  re-break `db:check-production-migrations` repo-wide. If the note is ever to be
  corrected it belongs somewhere that is not the hashed artifact.
- **Merge-order hazard, from both review axes.** #669's snapshot rebuild reissued
  ids for shared snapshots 0023–0026. Any other branch carrying `drizzle/meta`
  off older `main` cannot be rebased clean — its `prevId` points at an id that no
  longer exists — and needs **regeneration**, not conflict resolution.
- The `ralph/*` and `scripts/next-tasks` unit tests **fail locally inside this
  loop** and are not a branch signal: the supervisor exports `RALPH_LOOP_NAME`,
  which the "defaults to ralph" tests read, and the rest spawn the supervisor
  while a real one is running (the failure count varies run to run, 3 vs 14).
  Clear the `RALPH_*` vars before believing them. CI has no such vars.
