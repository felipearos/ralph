## What the amendment says, and three review rounds to get there

The ticket was already ready, so the guardrail forbids a `set-section` on `Acceptance criteria`; all ten points went in as an **amending comment**. Three `ralph-review-spec` rounds; round 1 found a P1 and five P2s, round 2 two P2s, round 3 two more P2s. The ones that mattered:

1. **`withAuth("write", …)` does not compile.** There is no `"write"` rate category (`src/lib/rate-limit.ts:8`); it is `"mutation"`, 30/min (:17), as both prior-art routes use. The ticket's own "What to build" had it wrong.
2. **Round 1's P1 was mine, and it was a product decision.** I first wrote that the response should project `getUserReadStatus`'s four fields down to the pair criteria 1-2 name. #2955's third criterion says "All four fields are in the answer even though nothing can write them yet, so #2944 and #2945 change no contract" — #2969 is in #2944's tree. Reversed to all four. Round 3 then caught that #2955's sentence is about *its own* GET answer and does not dictate the write routes' shape, so the requirement is now an explicit **Addition** with the real reason (one library state per book, the app would otherwise merge two shapes) and names the fields directly, since `UserReadStatusResult` lives in `src/server/queries/readStatus.ts:14-19` and `packages/shared` cannot export it. #2955 is **not** a blocker; whichever lands first declares the shared type.
3. **`"007"` would have created a second library.** The body says validate a positive integer and pass the string to the core. `parseStrictSegment`'s `DIGITS_ONLY` is `/^\d+$/`, so `"007"` passes and would store `external_id = '007'` where the web writes `String(book.id)` = `'7'` (`src/app/book/[slug]/page.tsx:83,85`) — exactly the second library criterion 3 exists to prevent. The amendment takes #2955's canonical rule instead: `^[1-9]\d*$`, with `"007"`, `"0"`, `"2abc"`, `""` and `"9007199254740993"` as five test cases.
4. **The gate had to move ahead of body validation, not just ahead of the write.** A viewer without the preview POSTing `{}` would get 400 `VALIDATION_ERROR`, and a route that does not exist answers 404 — so the 400 is the "told that Books exists" leak criterion 4 forbids, and criterion 4's own test (a valid body) never sees it. Needs a case of its own. Round 3 confirmed it is buildable: `wrapRoute` hands the raw `Request` to the handler and only `readJsonBody` reads it (`src/lib/api-utils.ts:365-377`).
5. **Criteria 1 and 2 passed for a route that echoes the write core.** Every test criterion 8 lists is satisfied by `{ readStatus: result.newStatus, isWantlisted: false }`. Two cases close it: wantlist on then `status: null` answers `{ null, true }` (`externalStatus-write.ts:123-125`), and `status: "read"` then `wantlisted: false` keeps `readStatus: "read"` because the wantlist-off delete only touches rows whose status is null (:181-182).
6. **Criterion 6 was vacuous.** A status write on a fresh book answers `isWantlisted: false` from `getUserExternalStatus`'s defaults (`externalStatus.ts:181-186`) whether or not :137's `set: { wantlist: false }` exists. Must wantlist first, assert `true` in the database, then write the status, then assert `false` in both answer and row, and mutation-check :137.
7. **Criterion 5's "the same stored rows" is false by construction.** Every write sets `updated_at: new Date()`. And a replayed *clear* can leave no row at all, because clearing is `update set status: null` then `delete where wantlist = false` — so the criterion is about stored *state*, where absent-and-absent counts.
8. **Criterion 7's prose escape hatch is settled.** The book routes do **not** belong in `media-reference-refusal.test.ts`: all four entries are TMDB writes asserting `MISSING_MEDIA_REFERENCE_ERROR` from `~/lib/tmdb-existence`, and neither external core has a `refuseMissingMediaReference` to return it. The amendment carries that paragraph so the PR can cite it rather than re-deriving it. Round 2 made me demote the "the core's first argument is the user id" half of the argument to a parenthetical, since #2942 puts a member id in that signature.
9. **"Signed out included" could not be borrowed from #2955.** #2955 is `withOptionalAuth`; this is `withAuth`, whose `runMiddleware` refuses 401 before the handler runs (`api-utils.ts:227-231`, called at :365-371). So the 404 covers authenticated non-suspended viewers only, and a suspended member without the preview gets 403 — stated explicitly so a coder does not restructure the route to "fix" it.
10. **Two citations in the body are off.** `authorize()` is `externalStatus-write.ts:66-75`, not `acting-member.ts:185-200` (that range is the `requireMember` overloads it calls — the callee, so the amendment says "callee rather than wrong file" rather than calling it an error).

No product question needed deciding, so the plan carries no `decisions`: every point is either a code fact, a criterion read against the code, or — for the all-four-fields and byte-identical-404-body additions — an explicitly labelled addition with its reason stated in the comment.
