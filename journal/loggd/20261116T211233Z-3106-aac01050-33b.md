## What the split actually turned on: the design in the parent body is wrong

The parent specified an **actable keep list** — the cores take "the media types
the actor may act on", mobile passing the browsable Media Modes, web passing the
launch-enabled ones, copying `reportContentCore`. The first spec review rejected
it and the repo backs that up twice, at `src/lib/media-types.ts:300-304` and
`src/server/db/review-visibility.ts:101-105`: `MEDIA_TYPES_BY_MODE` covers 5 of
the 12 `watchxd_media_type` values, so "keep the browsable modes' types" would
also refuse `album` and `track` review rows — rows the phone's diary touches
today (#771), reachable from `AlbumReviewPageContent` through the very like and
comment actions the parent wanted switched. Every child's "behave exactly as
before" clause named only shows and movies, so a coder would have passed every
criterion while album likes and comments went dark.

The shape that fits both the parent's rule and the repo: **keep the hide set**.
No core signature changes at all — `setReviewLikeCore`, the three comment cores
and `readReviewDetailAccess` already take the unanswered-types list from their
transport. Only the six app API call sites change what they hand it:
`unansweredReviewMediaTypes()` intersected with the modes the actor may not
browse. The server actions keep passing it unchanged, which is how loggd.dev
goes on refusing a book row for every account, and album/artist/track rows stay
untouched everywhere.

That collapsed three children to two, because the like path and the comment path
became the same one-line edit repeated.

Both `ready-for-agent`, both in `book-log-api` — the group #3106 itself held in
#3063's partition, so they are handed out one at a time and inherit that tree's
collision reasoning. **Neither blocks the other**, deliberately: a plan cannot
express a blocker edge between two issues it creates in the same run
(`add-blocker.issue` must be a real number; only `blockedBy` takes a ref), so a
split has to produce independently landable children or sequence them by hand in
a later iteration.

The landing handshake is the part worth remembering: #3544 skips the reply notify
for a book row **only if #3545 is not yet on main**, and #3545 removes that skip
**if it finds one**. Round 2 of the review caught that the first wording made
#3544's criterion unconditional, which would have had a coder undo #3545 after it
merged. Either order now leaves main correct, and no intermediate state mints a
`/…/movie/<slug>` link for a book.

## Review rounds

Round 1 killed the keep list (and found `enabledMediaTypes()` returns
`["tv","movie"]`, not the subdomain targets `["shows","movies"]` I had written).
Round 2 against the hide-set design found: the obvious helper
(`hiddenMediaTypes` passed through) reproduces the round-1 bug for `album` and
`artist`, because `ALL_SUBDOMAIN_TARGETS` includes `music`; `addReviewCommentCore`
reads its idempotency record *before* the hide-set query, so a replayed key
answers the recorded comment rather than the not-found; and four line references
were off by a few. All are written into the children or the comment.
