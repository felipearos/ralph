**What shipped.** Client-only mobile change. The Welcome Card renders in the home's `hero` slot while `welcomeCard.pending` from `GET /api/v1/users/me` is strictly `true`; dismissing POSTs `/users/me/welcome-card/dismiss` and optimistically writes `pending: false` into the persisted `["profile","me"]` cache, so the card goes without a refetch. **Key decisions.**
1. **The card REPLACES the hero while owed; it does not stack above it.** This reversed the first decision. Stacking breaks `HeroForeground`'s contract: a foreground measures its top within its parent and fades as that top nears the header (`heroForegroundOpacity`, `TabChrome.tsx:273`), and the carousel's logo is such a foreground (`absolute bottom-0` inside its slide, `HomeHeroCarousel.tsx:195-197`). Stacking pushed the slide down without changing the measured top, so the logo faded early and the backdrop sat mid-page. Found by the standards axis, verified in code, fixed in `aa6440934`.
2. `hideOnScroll` and `chromeBackground` left exactly as on `main`. Re-keying them (the first brief's instruction, reverted) would have produced `hero` present + `hideOnScroll` true, a pairing this app has never had.
3. No change needed in `mobile/hooks/useProfile.ts`: `welcomeCard` was already in `MaybeAbsentHeaderKey`, so it reads as `profile.profile.welcomeCard?`.
4. **Ruled out, with evidence:** the worry that a stale `["profile","me"]` cache (5 min staleTime, persisted; setup completion only writes `ONBOARDING_KEY`) would hide the card on first landing. `OnboardingGate` gates the whole navigator (`app/_layout.tsx:77`), so no `/users/me` consumer is mounted during setup and the gate itself has no profile read — the home's first read is a cold fetch. Do not re-derive this.

**CI round 1 was real, not a flake** (build 3784, `quality` / `$ jest`, 22 tests across 6 files, all `TypeError: … reading 'welcomeCard'`). Two causes, both from adding two hook calls to `HomeScreen`: (a) `profile.data?.profile.welcomeCard` assumed `ProfileData.profile` is always present — it is typed non-optional, but six existing specs answer `/users/me` with a header-less payload; fixed by optional-chaining the header at both read sites (`51be8e24c`). (b) Two specs mock every read, so the own-header read had to be mocked too — `reviews-tab-feed-section.test.tsx` renders HomeScreen with no QueryClient, and `home-viewer-media-state.test.tsx` asserts total `api.get` counts; fixed in the specs, not in source (`55d617193`). This is exactly the gap the first session deferred to CI because the host was busy.

**Codex round 1: two P1s on `mobile/hooks/useWelcomeCard.ts`, both real, both fixed in `7aea6cd99`.** (1) The dismissal was not pinned to the initiating account — a write defaults to `rateLimit: "wait-and-retry"` and the transport reacquires the *current* session token before each retry, so an account switch during a 429's `Retry-After` dismissed the wrong account's card; fixed with the repo's own convention, `usePinnedToViewer` (`hooks/favorite-writes.ts:69-99`, not favorites-only) plus `expectedUserId: viewerId`. (2) Rollback and settle could outlive the account: `profileKeys.me()` is one shared persisted key, so `onError` restoring the captured `ProfileData` could write account A's profile under B's entry; fixed with `stillSignedInAs(viewerId)` in both callbacks, precedent `hooks/useFeedMuteAction.ts`. All four guards mutation-checked — each break fails a test.
