**How to read Buildkite logs without the API token** (the `ci-debugging` skill
tells you to use `doppler secrets get BUILDKITE_API_TOKEN`, which §4 forbids and
which is withheld anyway — the web UI 403s unauthenticated). Everything above
came from the agent container instead, and this is worth reusing:

- `docker logs buildkite-agent --since 60m` gives per-job start/finish lines
  with **exit status and PID**, keyed by build number and job UUID. That alone
  tells you which job failed and how long it ran, which is most of a diagnosis.
- `/data/buildkite/builds/home-loggd-{1,2,3}/felipe-aros/loggd` are the three
  agent workspaces, world-readable. `cat <ws>/.git/HEAD` confirms which commit a
  workspace built — mine held `8324647` exactly.
- `docker exec buildkite-agent sh -c 'cat /tmp/job-env-<job-uuid>*'` gives
  `BUILDKITE_STEP_KEY` and `BUILDKITE_LABEL` for a **running** job. These are
  deleted when the job finishes, so grab them while it is live; for a finished
  job, infer the step from its duration against the pipeline's command list.

The command output itself is NOT recoverable this way — the agent streams it to
Buildkite and keeps no local copy. Duration plus the pipeline's ordered command
list is as far as you get. It was far enough here.

## Decisions worth knowing

- **`counts.skipped` counts ROWS, `summary.tmdb.failed` counts CONSTS.** The
  standards axis caught that I had made `skipped` = unique unresolved consts,
  which contradicts `types.ts`'s own definition ("rows the source could not
  place"). Two rows behind one unresolved const are two skipped rows and one
  failure. Fixed, and pinned by a test asserting the two numbers differ.
- **Empty input is a SUCCESS for IMDb, not `empty_dataset`.** Generic CSV
  refuses an empty dataset; IMDb has always answered zeros and the screen
  relies on it. The `ok: false` arm is therefore never taken by this source.
  Preserved deliberately, commented in both the module and the test.
- **Four pre-existing oddities preserved on purpose**, all commented: the review
  dedup key orders the Media Reference `${mediaType}:${tmdbId}` while
  watch-status orders it `${tmdbId}:${mediaType}`; watch-status updates are
  per-row rather than batched; the writes are not transactional (inherited from
  #655 — still nobody's ticket); the batch-of-8 TMDB pacing with its 400 ms
  sleep. A refactor ticket is not the place to change any of them.
- **`CONTEXT.md` untouched.** #656 settled no new term — Import Run and Media
  Reference both already carry it. #658 added Import Job; nothing here needed a
  fifth entry.
