## READ THIS FIRST: `append_to_response` is part of an E2E fixture's identity

Buildkite #1821 failed after 28 minutes and **nothing in the failure named
TMDB**. The cause: `e2e/tmdb-fixtures.ts` keys each recorded fixture on the
request's path *plus its whole sorted query*, and the stub **fails closed** on
a miss. I had appended `external_ids` to `getMovieDetails`, which renamed the
request — so all five `movie.*~append_to_response=credits,release_dates.json`
fixtures were orphaned at once and every movie page in the suite lost its
data. The symptom was `movie-detail … should render movie title`.

Three things made this expensive, and each is avoidable next time:

1. **The whole local gate passes.** Vitest, both typechecks, both lints and
   the build never touch the fixtures. Only Playwright does, and this loop is
   forbidden from running it. So a one-character change to an
   `append_to_response` string is, today, only checkable in CI.
2. **I had no Buildkite token** (withheld by `.ralph/config.json`) and the
   host-visible agent workspaces under `/data/buildkite` were stale from
   06:43 — build #1821 left nothing there. The memory note about live
   fail-dirs did not apply. What actually diagnosed it was **comparing
   against the other loops**: PRs #1179/#1177/#1175 and `main` itself were all
   green, including a build running concurrently with mine, which ruled out
   the environment and pointed straight back at my diff.
3. **The append was never needed.** TMDB carries `imdb_id` on the movie
   payload itself — all five fixtures already had a real one. Only a *show's*
   payload lacks it, so `external_ids` belongs on the TV fetch alone, and no
   fixture exists for that request because only the mobile-facing v1 route
   calls it.

**Generalisable: before changing any TMDB request's query string, grep
`e2e/fixtures/tmdb/` for a fixture recorded under the old one.** And check
whether the field you are appending is already on the payload; I appended for
symmetry between the two media types and paid 28 minutes for the symmetry.

I left a guard rather than a note: `e2e/tmdb-fixture-append-conformance.test.ts`
asserts no fixture is recorded under an `append_to_response` the app no longer
sends. I verified it by re-introducing the bug — it fails in one second and
names all five orphaned files. It is deliberately one-directional (the
reverse, "every app append is recorded", is false for call sites E2E never
reaches).

## The design decision worth arguing with: I did not fold in the cast screens

`mobile/lib/crew-departments.ts` buckets crew by department, and so do
`show/[id]/cast.tsx`, `movie/[id]/cast.tsx` and
`show/[id]/season/[s]/cast.tsx` (the standards axis found the third one, which
I had missed). I kept mine separate because the *requirements* differ: a full
listing wants one row per person (first-wins), the tab wants a person's jobs
merged — TMDB lists a movie's writer twice, as "Screenplay" and as "Story",
and two rows read as two people. Same bucketing skeleton, different dedupe.

That is a judgement call and a reviewer may reasonably overturn it. What I am
confident about is the alternative I rejected: parameterising one function
with a merge strategy, which would have made a 40-line function serve two
callers worse than two functions serve one each.

## Fans was a deletion, not an addition

Both title screens hand-rolled a three-button `StatButton` row; the shared
`MediaCommunityCounts` — already on the season, episode and movie-stats
screens — renders exactly those three plus Fans. So the Fans card was
*removing* two copies, and that is also what makes the acceptance criterion
("Fans count matches the Fans subpage") provable rather than asserted: same
`stats.fansCount`, same `mediaPeopleHref(scope, "fans")` destination.

Its two visible side effects are real and I said so on the PR rather than
hiding them: the Members/Lists icons change (`Users`→`Eye`,
`BookOpen`→`List`) and every accessibility label gains the title
(`Members: 10` → `Members of Breaking Bad: 10`).

## What the reviews found that I would have shipped

- **Standards**: the movies-route docstring claimed `homepage` needs
  `include=credits`. It is on the basic payload too. A comment that overstates
  a coupling is how the next person designs around a constraint that is not
  there.
- **Spec**: the Crew tab showed five rows of a department with nothing saying
  it was a preview, so a 30-person Camera department read as five people. Now
  the heading carries the department's **full** count (the cast screen already
  did this) and is an `accessibilityRole="header"`.
- **Spec**, flagged not fixed: the Fans *count* is unbounded while the Fans
  *directory* is capped at 50 rows, so a title with 128 followers renders
  "128" over a 50-row subpage. Pre-existing and true on web too, but it is the
  literal wording of this ticket's criterion, so it went on the PR.
- **Spec**, flagged not fixed: a show whose `aggregate_credits.crew` is empty
  gets a populated Crew tab whose "All Cast & Crew" lands on an empty screen —
  the cast screen has no `credits` fallback. That asymmetry already exists for
  *cast* on the same screens; I mirrored the neighbouring memo rather than
  fixing one half of it. Worth a follow-up.
