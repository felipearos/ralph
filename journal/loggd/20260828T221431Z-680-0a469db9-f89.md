## You can run real SQL without touching the shared stack

The single most useful thing this iteration did, and the reason the migration
shipped with measurements instead of reasoning. The local Supabase stack
(`supabase_db_loggd`) is Felipe's and CI's; **CI's own stack lives inside the
dind container and is reaped after each build**, so the host stack is not what
CI resets — but it is still not yours to reset. You do not need to:

```bash
docker exec supabase_db_loggd bash -c '
  psql -U postgres -c "CREATE DATABASE rls_probe;"
  pg_dump -U postgres -d postgres --schema-only -n public -n auth > /tmp/d.sql
  psql -U postgres -d rls_probe -f /tmp/d.sql'
```

That is a faithful clone of the checked-in schema — 0 errors, real `anon` /
`authenticated` roles, the real `auth.uid()`, the real `handle_new_user`
trigger — in a database nothing else uses. Apply your migration to it, then
`SET ROLE anon` / `SET ROLE authenticated` with
`SET request.jwt.claim.sub = '<uuid>'` and read as each actor. Drop the database
afterwards. Replaying `supabase/migrations/` from scratch does NOT work
(the baseline wants an `extensions` schema that only `supabase start` creates);
cloning the running database does.

Two gotchas building fixtures in the clone: `postgres` is not a superuser here,
so `SET ROLE` on a role you created needs `GRANT <role> TO postgres` first; and
inserting into `auth.users` fires `handle_new_user`, so do not also insert the
`profiles` row.

## The fact that changed the migration, established by execution

**A column-level `REVOKE` against a table-level `GRANT` is silently a no-op.**
After `REVOKE UPDATE (is_hidden) ON review FROM authenticated`,
`has_column_privilege('authenticated','review','is_hidden','UPDATE')` still
answers `true` — no error, no warning. The only thing that takes the column
away is `REVOKE UPDATE ON TABLE ... ` followed by `GRANT UPDATE (<allowlist>)`.
The first spelling is the one you would write, and it would have shipped a
moderation bypass wearing a REVOKE.

That mattered because `review_update_own` carries no `WITH CHECK`, so PostgreSQL
reuses its `USING` clause for the new row: without the grant change a member
could clear `is_hidden` on their own moderated Review with one PostgREST call,
and the read rule this ticket adds would have been undoable by its own subject.

## What the two review axes were worth

Both found the same thing independently, and it was the one real design error:
the first draft's `review_comment` policy carved out the comment's own author
(`OR user_id = auth.uid()`), by symmetry with `review`. Wrong symmetry.
`reviewCommentVisibility` (`src/server/queries/comment-visibility.ts`) replaces
a suppressed comment's text with the empty string for **every** reader
including its writer, so the carve-out would have opened a read at the PostgREST
boundary that no Loggd surface offers. It is gone, and the mutation is visible:
on the clone, the comment's author saw their hidden and deleted comments before
the change and does not after.

The `review` author carve-out is the opposite case and stays — three client
components (`UserActionBar`, `MusicActionBar`, `BookActionBar`) read the
caller's own Review over PostgREST, and `review-visibility.ts` documents
write-path finders as the one read that must see a moderator-hidden row.

Standards also caught the migration repeating `hideReportedContent`, a function
name the repo lost some time ago (it is `hideContent`) and which
`review-visibility.ts` still carries — copying a stale comment is how a stale
comment becomes two.

## Decisions worth knowing

- **Staff get nothing at this boundary.** Moderation reads through Drizzle
  (table owner, RLS-exempt); Supabase is used in `moderation.ts` only for
  `auth.getUser()`. The suite therefore asserts a moderator *cannot* read a
  draft or hidden Review, with a comment saying why so nobody "fixes" it. Both
  axes agreed this is a defensible reading of the AC's "moderator cases".
- **No dependency on #675.** This migration defines its own predicate rather
  than using #675's `current_member_is_staff` / `current_member_is_admin`
  SECURITY DEFINER helpers, so the four drafts can be applied in any order.
- **The `is_hidden` grant change is scope creep and is flagged as such** in the
  PR body and the `needs-migration` comment, with an offer to split it. Both
  axes called it necessary but unauthorized by the ticket's read-side ACs.
