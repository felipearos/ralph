## The lens, and the cuts

Pure file-overlap closure put this whole tree in ONE component — every ticket
reaches #3338 or #3348 through some shared file — which would serialise 36
tickets and is useless. The cut I used: **a shared file does not force one group
when one ticket blocks the other**, because the frontier never offers the second
until the first has closed, so they cannot be in flight together. The children
carry a dense `## Blocked by` graph (read from the bodies, recorded in the
comment), which makes that lens cheap and checkable.

Five overlaps were cut on that basis, each named in the issue comment:

- **#3338 edits `mobile/components/books/BookShelves.tsx`** (forced: widening
  `BookShelf` breaks `SHELF_COPY: Record<BookShelf, …>`), which
  `book-dnf-mobile-book-write` owns. #3357 ← #3342 ← #3338, so #3338 merges first.
- **#3385 / #3387** on `book-browse-catalog.ts` — #3387 is blocked by #3385.
- **#3341 / #3382** on `profile-write.ts` / `users/me/route.ts` — #3382 is blocked
  by #3341.
- **#3348's predicate** applied by #3344, #3349, #3350, #3351, #3352, #3382, #3383
  in their own reads — all seven are blocked by #3348.
- **#3362's possible `RatingRow.tsx` edit** against #3355/#3356. The mapper flagged
  this one as a judgement call rather than a fact: `RatingRow` already carries
  `unavailable` + `caption`, so #3362 likely consumes it; and #3362 is blocked by
  #3347 and #3072, landing well after the two write tickets. This is the only cut
  that is not backed by a blocker edge, and it is the one to revisit if a coder
  hits a rebase there.

Two merges in the other direction, under "when in doubt, share the group":
#3344+#3360 and #3352+#3366 are wire pairs with no file overlap at all, grouped
because they are one surface answered twice (server read, mobile consumer), and
#3354 joined #3386/#3387 on the weakest concrete edge in the mapper's report
(both touch `BookViewerState*` for the fade rule).

## Findings for whoever works the tree

- **#3338 cannot ship as a server-only change.** Widening `BookShelf` also makes
  `isBookShelf` accept `did_not_finish`, so `/api/v1/users/books?shelf=did_not_finish`
  answers the shelf before #3342 adds the privacy check. Latent until #3341 lets
  anyone turn the switch off, but the ordering matters.
- **#3348 meets the review-visibility conformance test.**
  `src/server/db/review-visibility-conformance.test.ts` recognises only the name
  `publishedReviewPredicate` (`const PREDICATE`); a composed predicate under a new
  name fails it unless the test learns the name. This matches the existing memory
  that the conformance check is lexical.
- The mapper also flagged four book-review reads that **no child of this spec
  covers** and that could leak a hidden Not Finished log:
  `reviews/[id]/story-card/route.ts`, `reviews/[id]/unwatch-offer`,
  `src/server/queries/app-link-resolve.ts` (possibly covered by #3384's change to
  `review-detail-access.ts`), and `members-directory-ranking.ts` /
  `popularReviewers.ts`, which count Book Logs. That is a gap in the spec, not in
  the staffing; I did not file anything for it, since adding children to a spec is
  the oversize bucket's job and this unit was staffing.
