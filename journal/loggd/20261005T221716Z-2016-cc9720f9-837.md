**What landed.** The server-side Feed Section registry (`src/server/feed-sections/`):
`readFeedSection(section, ctx)` and `readFeedSectionBatch(requests, shared)`, with one
entry registered — Popular Reviews with Friends, falling back to community-wide Popular
Reviews. The registry owns the shared rules: fall back only on an empty *first-page*
read and never on a continued page, withhold the fallback for a switched-off category,
flag `isFallback`. The v1 Feed Sections endpoint answers that section through the
registry in both its single and batch forms and its own Reviews branch is gone; the
other four sections stay on the endpoint's read, fenced at the type level by
`EndpointFeedSection = Exclude<FeedSection, RegisteredFeedSection>`. The endpoint's
contract is unchanged — its 81 tests pass untouched.

**Key decisions.**

- **The entry shape deviates from spec #2009 deliberately.** `read`/`fallback` answer
  *rows*, and a third member `hydrate(rows, ctx)` turns them into items. #2009's user
  story 21 also requires that a first page emptied *by hydration* not fall back, which
  is unexpressible if `read` answers hydrated items. The spec-axis review agreed the
  deviation should stay.
- **The registry is partial, not total,** over the shared section list
  (`Partial<Record<…>>` plus `isRegisteredFeedSection`), because #2016 requires the
  other four sections keep using the endpoint's path during the transition.
- **The entry is keyed by its section,** so both its kind and its category are
  compile-checked against the shared maps rather than merely asserted.

**Dead ends, so nobody walks into them again.**

- I first wrote a comment claiming a shared cached community ranking *cannot* express a
  per-viewer feed mute. That is wrong: the ranking is already keyed per viewer by
  `rankingBlockKey(blockedUserIds)`, so blocks ∪ mutes is cache-safe, and the exclusion
  happens in SQL so the page is not short. The spec axis caught it and the fallback now
  honours feed mutes — a real behaviour change for members who have them, in scope per
  #2016's AC.
- The kind/category table test was **tautological** as first written: the entry read its
  category out of the same function the test compared it against. Declaring the category
  literally on the entry, then keying the entry type by the section, made it both a real
  test and a compile error if they diverge.
- Declined with reasons during review (see `.ralph/logs/phase-2016-review.md`): collapsing
  the route's batch try/catch into `readFeedSectionBatch` (transitional code, due to go
  with the other four sections), removing `REGISTERED_FEED_SECTIONS` as "test-only" (AC1
  needs it), flattening the three-branch `envelope` cascades (no `as` assertions allowed),
  and renaming `getGlobalPopularReviews`'s `blockedUserIds` parameter (other callers).
- No `CONTEXT.md` change: the glossary's **Feed Section** entry already states every rule
  the registry implements and the diff coins no term. `hydrateReviewRow` became
  `hydrateReviews` because the glossary reserves *Row* for a client's rendering.
