## The design decision the next import ticket (#660) inherits

`processImportJob` finishes a job with `preparedOutcome ?? outcome`, so **the
outcome handed to `beforeWrite` is the one the member ends up reading.** Generic
CSV never noticed because its prepared outcome *is* its final one. IMDb's was
not: its summary was filled by three `count(*)` queries run AFTER the account
writes, so wiring it up naively would have published placeholders.

The fix was to restructure the run's tail plan-then-write and derive the
post-import totals arithmetically from the pre-write snapshot plus the plan
(extend the `existingWs` select with `status`/`watchlist`; a touched row ends in
exactly the state `wsData` holds, an untouched one keeps the snapshot's).
Three queries deleted, and the numbers are now one consistent read instead of a
post-write count racing the member's other writes.

**Letterboxd (#660) has the same shape** — `runLetterboxdImport` also returns a
richer `summary` alongside the shared result. Check where its summary numbers
come from before wiring `beforeWrite`, or it will publish the same placeholders.

## The two things the local review caught, and both axes found the same one

**The row cap died with the deleted route.** It refused `> MAX_IMPORT_ROWS` with
an immediate message; nothing on the job path replaced it, so a 10 MB
`ratings.csv` passed the size gate and then could not finish TMDB resolution
inside `maxDuration` — three doomed attempts instead of one instant refusal.
`too_many_rows` joins `ImportRunFailureCode` and the run answers it.
**Generalise: when a ticket deletes a transport, diff its gates, not just its
body.** The Import Run inherits validation only where someone moves it.

Second: `useImportJob` treated a 404 as terminal, so a member reloading mid-POST
could out-run their own job's creation and destroy the durable handle. First
three polls now ride out a 404.

## Reusable: reading a Playwright failure with no Buildkite token

Two builds failed on e2e with the log unreadable (the API token is withheld and
the build page 403s). What worked, and it is now the fastest path here:

1. Identify the live job: `docker exec buildkite-agent sh -c 'grep -h
   BUILDKITE_STEP_KEY /tmp/job-env-*'` — filter by `BUILDKITE_COMMIT`, because
   **stale env files from old builds linger** (one for build 804 was still there).
2. The agent's checkout is on the host at
   `/data/buildkite/builds/<agent>/felipe-aros/loggd` (`BUILDKITE_BUILD_PATH`
   is `/data/buildkite/builds`, bind-mounted).
3. Poll every 3s for the job-env file to disappear, then immediately
   `cp -r` `playwright-report/` and `test-results/` out. **The agent takes its
   next job within ~15s and the checkout is cleaned** — I lost build 889's
   report to exactly that.
4. The failure text is in `playwright-report/data/*.zip` → `test.trace`, one
   JSON object per line; the `{"type":"error"}` line carries message and stack.

The bug it found: **`request.postDataBuffer()` returns the multipart envelope
with the file part's contents elided.** `expect(body).toContain("tt0111161")`
could never pass. Assert on `filename="…"` and the `source` field instead.

Also worth knowing: `expect`'s timeout is **5s on this desktop** (only the
hosted profile raises it to 15s), while these screens poll every 2s. Any
assertion that waits on the *next* poll needs an explicit budget — the CSV spec
dodges it by reloading, which is why it was passing where mine was not.

## Do not repeat

- **`bun run test:coverage` fails locally in a ralph worktree** —
  `ralph/ralph.test.ts` and `scripts/next-tasks.test.ts` read `ralph/.loop-name`
  (gitignored, contains `rafa` here) and `$RALPH_LOOP_NAME`. It reproduces on
  `origin/main`, is not a repo break, and CI does not see it. Do not chase it.
- **`main` was red for its own reasons** while this PR was green: builds 885/886/
  887 failed `quality` at 23s–3m. My branch's `quality` passed at ~5m throughout.
  A red `main` did not mean a red branch this time.
- `ralph/inspect.sh mapper` and all three `delegate.sh` rounds hit the 900s
  timeout. Budget for it: run them backgrounded and poll, never in a foreground
  Bash call (the tool caps at 10 minutes).
