### The one product question, settled from a documented rule

AC5's "refused with the mobile API's unauthorized answer" cannot mean "401
whenever there is no user". `withOptionalAuth` collapses every refusal to
`user: null` (`src/lib/api-utils.ts:231-235`), an auth outage and a suspended
token included, and the next lines carry the rule: "An auth outage is not a
sign-out: mobile clears its session on 401, so this must stay a 503 (#1348)."
A bare 401 would log a member out of the app during an outage. Cited as the
plan's one `decisions` entry; the route must learn *why* there is no user and
answer 401 only for genuinely signed out, 503 for `unavailable`, 403 for
suspended — and only when the request carries a shelf value, so a plain #3065
request is untouched. That became its own criterion.

### Other substantive corrections, each from code

- No precedent exists: the shows/movies Browse shelf filters are client-side
  over the loaded discover page (`src/hooks/useFilteredShows.ts:128-155`,
  `mobile/lib/browse-filters.ts:95`). No id list has ever gone to a provider.
  Said so explicitly so nobody hunts for one.
- Reusing `discoverBooks` as it stands smuggles back two things the ACs forbid:
  `users_count: { _gt: 0 }` seeded into `whereParts` (`src/lib/hardcover.ts:629`),
  which is one of the junk floors a shelf drops, and the unconditional
  `books_aggregate` (`:686-690`).
- `external_id` is `text` and the provider's `_in` takes `[Int!]`, so one
  unservable row would 503 every page of that member's shelf. Screen with
  `isServableBookId` first. The 1,000 cap counts shelf rows *before* that
  screen, matching `src/app/api/v1/users/books/route.ts:54-59` — stated as
  intended so nobody "fixes" it.
- Read is `status = 'read'`, never `'reading'`; Wantlist is `wantlist` true
  whatever the status (`src/server/queries/readStatus.ts:80-82`). And "both"
  only exists if the fixture writes status first, wantlist second:
  `setExternalStatusCore` clears `wantlist` on a status write
  (`externalStatus-write.ts:128-131`) but not the reverse (`:166`). The other
  order gives an empty "both" set and a vacuously passing test.
- The cursor counts the provider rows *kept on the page* after the look-ahead
  row is trimmed and before summaries are dropped
  (`users/books/route.ts:55-56`); counting the rows returned skips a book on
  every page that has a next one.
- Scope: the legacy ungated `src/app/api/books/discover/route.ts` and the direct
  `discoverBooks` call in `src/app/books/browse/page.tsx` are out — a bare book

## Harness bug — `add-blocker` sends `issue_id` as a string

`triage-apply.ts` exit 1, mid-plan, on the first run:

```
triage-apply: stopped at blk-3094-3064: gh: Invalid request.
Invalid property /issue_id: `"6340031221"` is not of type `integer`. (HTTP 422)
```

`triage/apply.ts:226-232` posts the dependency with
`gh api --method POST … -f issue_id=<id>`. `gh api -f` always sends a **string**;
the endpoint wants an integer. The fix is `-F issue_id=<id>` (typed) or
`--raw-field` with a JSON body. As it stands **no `add-blocker` op can ever
succeed on this repo**, so every native dependency edge a triager tries to
create fails the plan mid-apply. Worth an issue on felipearos/ralph.

The retry advice for exit 1 ("re-run the same plan; the op ids make it
idempotent") does not help here: the failure is deterministic, not transient. I
dropped the one op and re-ran — the three `set-section`s were reported "already
done" and the remaining two writes landed. End state verified: `tria-wip` gone,
`ready-for-agent` on, worktree clean and detached at `origin/main`.
