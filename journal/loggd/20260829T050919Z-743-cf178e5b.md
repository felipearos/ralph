# 2026-08-29 — #743: the frontier handed me a ticket that already had a PR (PR #744)

**Outcome: merged.** Loop: **rafa**. Ticket #743, branch
`rafa/743-frontier-pr-fence`, PR **#744**, Buildkite **#1061 green**
(unit + E2E: 698 passed, 8 flaky-retries, 0 failures). `rafa-wip` cleared on PR open —
and the ticket stayed fenced anyway, as `PR #744`, which is the whole fix

## Read this first if you are the next iteration

**The frontier had a hole where an open pull request should have been, and it
fired on me.** `bun run next --take-one` handed me **#685** and wrote
`rafa-wip` on it while ralph's **#742** — open, non-draft, `closes #685` —
already carried the finished work. I backed the claim out. Without that, two
loops would have implemented one ticket end to end.

The cause: `classify()` decided "somebody has this" from a `<loop>-wip` label
or an assignee, and nothing else. §5 has a loop **clear its `<loop>-wip` label
when it opens the PR**, so between "PR opened" and "PR merged" the ticket wore
no claim at all. That window is not an edge case — it is *every* shepherdable
PR, and it is widest for the ones that sit longest, which right now is most of
this backlog.

If you are reading this before #744 merges, the hole is still open on
`origin/main`. **Check `gh pr list` against whatever the frontier offers you**
before you start, exactly as the old §1 told you to.

## The trap that made it invisible

Drafts were safe *by accident*, which is why nobody caught this earlier. A
migration-blocked draft also gets a `<loop>-blocked` label, and `stuckLabelOf`
drops stuck tickets out of `queued`. So the four blocked drafts never
reappeared — the fence that was actually holding them was the stuck label, not
anything about the PR. #742 was the first non-draft PR whose issue carried
neither label, and it went straight through.

**A guard that works only because a second, unrelated guard happens to cover
the same cases is not a guard.** Ask what is actually holding, not whether the
outcome currently looks right.

## The empty frontier was the real signal

`--take-one` returning #685 came *after* the frontier had otherwise emptied:
every other ticket is migration-blocked or in flight. An almost-empty queue is
exactly when this bug bites, because a PR-held ticket is the only thing left
to hand out. If a future iteration sees the frontier offer something that
feels too convenient, that is the shape to be suspicious of.

## Leases outlive the claim you backed out

Removing the `rafa-wip` label from #685 did **not** release its lease, and my
supervisor's heartbeat kept renewing it — so `--take-one` then reported #685
`obstructed` by "lease active", wedging it for *both* loops on a claim I had
already abandoned. There is **no release command**; `ralph/claim-lease.ts` has
only `heartbeat`. I deleted the entry directly, guarded on `loop === "rafa"`
and my own `RALPH_RUN_ID`:

```
bun -e 'import {leasePathFromGit, readLeaseStore, writeLeaseStore} from "./ralph/claim-lease"; …'
```

**If you back out a claim, release the lease too.** A release subcommand is
worth writing; I did not, to keep the diff on the ticket.

## Two review axes, four findings, one shape

Both axes ran (`ralph/inspect.sh`, exit 0 each, ~15 min) and independently
found the *same four things*, which is a strong signal they were real:

1. **The census bound was silent.** `gh pr list --limit 200` — and `gh pr
   list` returns **newest first**, so what falls out past the bound is the
   *oldest* PRs, precisely the long-lived ones the fence exists for. Now a
   named constant, documented, and printed to stderr when a read hits it.
2. **Three branches no test could reach**, each surviving deletion: the
   maintainer path's PR wiring in `claimObstruction` — *the path that actually
   fired* — the tree renderer's `PR #N` detail, and `takeOne`'s `io.isOpenPr`
   argument. The delegate had mutation-checked its own tests honestly and
   still left these, because it checked the tests it *wrote*, not the branches
   it *added*.
3. `ralph/prompt.md` §1 went stale (below).

**The lesson: mutation-check per production branch, not per test.** "Every
test I wrote fails when mutated" and "every branch I added is covered" are
different claims, and the delegate proved the first while believing the
second.

## Gotchas

- **`bun run test -- ralph/ scripts/` takes >10 min and timed out mid-run
  while my work was stashed.** Do not stash across a long suite. Use a WIP
  commit, or scope the run.
- Three `ralph/*` test failures here are **worktree identity, not your diff**:
  `loop identity > defaults to ralph` and two in `frontier-gate.test.ts` whose
  assertion diff is literally `ralph-wip` vs `rafa-wip`. They read
  `ralph/.loop-name`, which says `rafa` in this worktree, and they fail on
  clean `origin/main` here too. Verified by stashing. They pass where CI runs.
- After #695 merged, `bun run typecheck` failed on
  `.next/types/validator.ts` referencing a deleted letterboxd route. Stale
  generated output — `rm -rf .next`, not a code problem.
- The pre-PR hook's marker `touch` did not take inside a `&&` chain with
  `$(git rev-parse HEAD)`; running the literal path alone worked.
