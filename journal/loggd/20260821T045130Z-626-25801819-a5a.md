**What the ticket was.** Notification preferences were read and written twice
with no shared code, plus two further hand-listed copies nobody counted: the
validation schema in `packages/shared/src/schemas.ts` and the column list in
`notify.ts`'s own preference filter. Four copies of six names, about to become
four copies of sixteen.

**The design decision worth carrying forward: it is TWO modules, split on the
runtime boundary, not one.** The first cut put everything in
`src/server/queries/notification-preferences.ts` and left `NotificationsForm.tsx`
— a client component — with its own fourth copy of the defaults, because the core
imports `~/server/db` and a client cannot touch it. That also forced a type
re-export through a `"use server"` module. The fix:

- **`src/lib/notification-preferences.ts`** — what a preference *is*: catalogue,
  both vocabularies, mapping both directions, defaults, null resolution. **Zero
  imports**, deliberately. That is the property that lets the form import the
  real defaults.
- **`src/server/queries/notification-preferences.ts`** — drizzle columns, zod
  schema, read and write.

**Generalisable:** when a "one shared core" refactor leaves a client component
with its own copy, the boundary is wrong, not the component. Split the pure
domain out and give it no imports at all.

**The security finding, and it was pre-existing on `main`.** Both axes of the
second review pass reached it independently: `updateNotificationPreferences`
carries `"use server"`, so its argument is a public POST body with its type
erased at runtime, and it spread that argument into drizzle's `.set()`.
`mapUpdateSet` (`drizzle-orm/utils.js:83`) does no membership check and
`buildUpdateSet` emits `"col" = $n` for every real column present — and
`profiles` holds `is_admin`, `is_pro`, `role`, `is_suspended`. Any signed-in
member could POST `{ is_admin: true, role: "admin" }`. Verified against the
drizzle source rather than assumed, and the guard test verified by removing the
guard and watching it fail.

**This is almost certainly not the only one.** Any server action that spreads a
caller-supplied object into a `.set()` has the same hole. **Best unfiled ticket
out of this iteration: sweep `src/server/actions/**` for that pattern.** Recorded
on the PR's merge comment too.

**The subtler review finding, and the one that justifies reading diffs.**
`toStoredPreferencePatch` returns a `Partial`, and a `Partial` cannot make an
omission a type error. So of the six hand-written listings of the six names, five
had total return types the compiler checks and *one* did not — and that one was
the mapper that turns a PATCH body into a write. A preference added to the
catalogue and forgotten there would compile and silently drop the key from every
PATCH that sent it: exactly the failure the ticket exists to remove, reproduced
inside the fix for it. It now walks the catalogue. **Generalisable: in a
collapse-the-copies refactor, audit which listings the compiler can actually
check. `Partial` returns cannot be.**

**One deliberate behaviour departure.** `notify.ts` tested a raw column with
`profile[preference] !== false`, which reads null as on — agreeing with the
defaults only while every preference defaults on. #624 lands default-off push
preferences. Recipient rows now go through `resolveNotificationPreferences`. No
behaviour change today; it stops the shared defaults being a fiction tomorrow.
