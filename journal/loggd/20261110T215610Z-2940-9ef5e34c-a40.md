## The decision that shaped it: the server read does not need #2939

#2940 was blocked by #2939 (book search in the app), which sits behind spec #2938 and its five children. The **server read needs none of that** — only #2936's "may this viewer browse Books". ## Three things the code does not support as #2940 describes them

Written into the children rather than left for a coder to discover.

1. **"The envelope an unknown route gives" cannot be taken literally.** No catch-all exists under `src/app/api/v1`, so an unknown v1 path falls through to Next's not-found with a 404 and no JSON body, and the proxy's matcher does not cover `/api/v1/books` (`src/proxy.ts:444`; `API_ROUTE_OWNER` marks `v1: "shared"` at `src/lib/media-types.ts:217`). #2955 states the effect instead: a 404 naming neither books nor the provider, **decided before any provider request** (a stub that throws if called), mutation-checked. A viewer who *may* browse Books and asks for a missing id is a different case and may be told plainly.
2. **A missing book and a provider outage are the same `Error` today.** `getBook` throws `new Error("Book not found: …")` (`src/lib/hardcover.ts:156-158`); `fetchHardcover` throws the same class on a non-ok response (44-48), on GraphQL errors (52-54) and on an absent key (30-32). #2940's criterion 7 is impossible until those are two codes on the wire, so #2955 owns the split and #2956 consumes it. The absent key counts as retryable, per #2934's "book reads answer a provider-unavailable error to preview accounts".
3. **`MediaPoster` cannot draw a book.** It needs a `MediaScope` with a numeric `tmdbId`, reads Viewer Media State, schedules the long-press action-state read and pushes a title destination (`mobile/components/MediaPoster.tsx:159-240`); the frame itself is 242-263. #2956 factors it out or copies it, and factoring out is named as the kinder choice because #2939, #2946 and #2947 all draw covers.

Also: `media-reference-refusal.test.ts` is a table of **write** surfaces only (101-146) and both v1 conformance tests walk the directory, so #2940's "registered with the conformance and contract checks" needs no table edit. #2955's criterion names what it actually binds — the `withOptionalAuth` wrapper imported from `~/lib/api-utils`, no `username` read, and the response type exported from `packages/shared`.

## Judgement calls a later pass should not re-derive

1. **#2956 is blocked by #2955 alone, not by #2938 — and is therefore forbidden from editing `mobile/lib/media.ts`.** It does not need to: `RowMediaType` is `"tv" | "movie"` (`mobile/lib/media.ts:60`), `mediaDetailHref` takes a numeric `tmdbId` (84-85), `QUERY_KEY_PREFIX` is keyed by `RowMediaType` (88-91) — none could hold a book, and the spec asks for the book's plumbing "beside the existing TV and movie ones". `mobile/lib/media.ts` belongs to the `mobile-mode-shell` group, so a book edit there would be two groups in one file. The residual overlap is one `Stack.Screen` line in `mobile/app/_layout.tsx`, named in #2956's body. The reviewer twice preferred blocking #2956 on #2938 instead; that costs the heavy child the whole shell's wait for a rebase it will probably not need.
2. **All three share `hardcover-reads`.** #2955 edits `src/lib/hardcover.ts`, which #2943 also edits; #2956 shares `card-snapshot.ts` and `usePressInPreparation.ts` with #2946/#2947 and the poster frame with #2939; #2957 shares `discover.tsx` with #2939/#2946. The chain already serialises the three, so the group costs nothing between them. What it buys is that #2955 never runs beside #2943.
3. **The id's string-ness cannot be witnessed by a value on the server.** Inside the range the route serves (a GraphQL `Int` is signed 32-bit), a round trip through `Number` leaves the string identical, so #2955 holds it by type and by review and asserts the out-of-range and non-canonical ids (`^[1-9]\d*$`) as not-found. The value witnesses (`"9007199254740993"`) live on #2956 and #2957, where the pushed route and the issued request are observable. The single `Number()` at the `getBook` call is stated as the deliberate exception to criterion 11.
4. **No child for the Hardcover retry or the summaries filter.** Neither is in #2940's eleven; the retry is #2943 and the filter belongs to the list reads.

## HARNESS GAP — a native dependency cannot be removed, and a prose repoint does not replace one

I repointed #2944, #2946 and #2947 from #2940 to #2957 with `set-section` on `## Blocked by`, to spare them the wait on this spec's closure. **It does not work, and the first comment I posted overstated it.** All three carry a **native** GitHub dependency on #2940 as well (`gh api repos/felipearos/loggd/issues/<n>/dependencies/blocked_by` → `2940,2941,2942`, `2940`, `2940`), and the triage write path has **no op that removes one** — only `add-blocker`, which adds. So the rewrite added #2957 beside an edge it cannot take away and the three stay gated on the spec closing, exactly as before. A correction comment is on #2940 (attempt 3). Worth a `remove-blocker` op on felipearos/ralph; until then, do not plan a native-edge repoint and do not promise one.

`add-blocker` is still broken the way the #2938 entry describes (`-f issue_id` sends a string, GitHub's endpoint answers 422, `-F` is the fix), so #2955/#2956/#2957's own edges went in as prose. The census reads them and warns `prose-only edges, backfill as native dependencies: #2957 #2956 #2955 #2954 #2950 #2947 #2946 #2944`.

**The placeholder trick that made two plans safe.** A child has no number until it exists, so sibling edges cannot be written at creation time. Each child was created carrying `- #2940` under `## Blocked by` — wrong, but pointing at a still-open spec, so never offerable. The second plan replaced those lines. That is the fail-safe ordering: if the second plan had failed, the children would have been stuck behind the spec, which is the status quo, rather than loose and claimable.
