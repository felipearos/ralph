## What the mapper found

Neither scan is fixed at HEAD. `network.ts`'s `memberCounts` is a module-level
`sql` const (aliases `r` and `rc`) interpolated into `getNetworkMembers` and
`getBlockedMembers`, with no visibility condition; the `watched` CTE in
`topCollections.ts#getUserTopCollections` has no `is_draft`/`is_hidden`
condition. No schema change and no migration — `review.is_draft` and
`review.is_hidden` already exist. So: real work, not a closure.

**The ticket's premise was half wrong.** At `main` there is no
`UNGUARDED_SQL_SCANS`; the baseline is `UNGUARDED_SCANS` and it cannot name
either query, because the conformance walker matches only `.from(review)`-style
calls in files that import `review` and is blind to a raw `FROM review r` inside
a `sql` template. The blocker #2687 is what teaches the test to read raw `sql`,
and on #2687's branch `UNGUARDED_SQL_SCANS` does exist and already lists both
queries as "fixed by #2791". So the blocker is correct and the criterion is
satisfiable once #2687 lands — but only if the AC says so rather than assuming a
constant that is not on `main`. That is now written into both sections.

## The product question, and the rule that settled it

The ticket left the `topCollections` predicate open: `loggedReviewPredicate`
(drafts out, moderator-hidden logs in) "or the published predicate if the stats
surface is meant to be public-only". **Decided: `publishedReviewPredicate` for
both scans.** Cited in the plan's `decisions` and in the issue comment:

- `src/server/db/review-visibility.ts`, `loggedReviewPredicate` doc comment —
  "The batched Viewer Media State read is the one surface that answers `logged`",
  and it is "never a substitute for `publishedReviewPredicate` on a display read".
- `src/server/db/review-visibility-conformance.test.ts`, `UNGUARDED_SCANS` doc
  comment — "a display read filters hidden reviews even on the author's own
  profile, because the write-path exception above does not apply to reads."

Collection progress is a display read of a subject's profile
(`read-stats-section.ts` calls `collections(subjectId, …, viewer)`), so the
published predicate applies. Two independent confirmations: every sibling query
on that stats page already uses `publishedReviewPredicate`, and #2687's new
scanner rule recognises **only** the identifier `publishedReviewPredicate` as a
guard, so the logged variant would have left both scans recorded as unguarded
and made the baseline criterion unsatisfiable.

**My first draft had this backwards** — I was about to cite `CONTEXT.md`'s
*Viewer Media State* entry ("a draft does not count and a moderator-hidden log
does") to pick `loggedReviewPredicate`. Round 1 of the spec review showed that
entry is scoped to the acting member's own library and that the repo's
display-read rule points the other way. Worth remembering: **CONTEXT.md's
`logged` sentence is about one batched viewer read, not a licence to use
`loggedReviewPredicate` on any surface that asks "has this member logged it".**

  cannot call `memberCounts` or `getBlockedMembers`, both private.

`topCollections` test pass against the pre-fix query: the CTE is

new tests are required to be `*.integration.test.ts` files, because
`network.test.ts` and `topCollections.test.ts` each `vi.mock("~/server/db")` for
the whole file and can never observe a predicate.
