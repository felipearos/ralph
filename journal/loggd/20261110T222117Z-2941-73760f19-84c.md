## The decision that shaped it: #2961 owns a kind-free resolver, and it must NOT live in `parseFilter`

"All media means the viewer's modes" has to be answered once, but the routes that need it do not agree on how they ask. Three profile reads declare `{ media: "filter" }` and get `"all"`; `/users/profile` and `/users/likes` declare **no** kind and `withOptionalAuth("read", handler)` gives such a route no `scope` key at all (`src/lib/api-utils.ts:338-341`); the Activity read declares `{ media: "memberList" }`, whose missing value is `null`, not `"all"`. So the resolver is a function of the viewer, callable without a kind — and #2962/#2963/#2964 are blocked on #2961 rather than on #2936 alone.

The second review then killed the obvious shortcut. Teaching `parseFilter`/`parseMemberList` to answer the viewer's set would change **eleven** `filter` routes and **four** `memberList` ones: among them `GET /api/v1/users/watchlist`, which #2941's criterion 9 explicitly leaves alone, the two diary routes #2962 owns, and `lists`, `lists/trending`, `users/member-lists`, which no child of #2934 owns. `"all"` therefore keeps meaning `"all"` on the scope, and #2961 carries a criterion naming all fifteen routes as unchanged. **Do not re-derive this as a simplification.**

## What the code does not support as #2941 describes it

1. **The diary and heatmap are not leaking — they are over-hiding.** `diaryMediaCondition` maps `"all"` to `enabledMediaTypes()` (`src/server/queries/diary.ts:80-92`), so books are hidden from the preview account too. #2962's job is the viewer's set; and because that condition is shared with the **web** diary page and `DiaryHeatmapMini` (via `cached-stats.ts`), #2962 must give the viewer's set its own path and leave the web on the launch constant.
2. **The Activity read has four book-carrying sources, not one.** `fetchBookKeys` (the `readStatus` shelf, gated by the request's own `exclude` at `activity.ts:1352`) is the leak criterion 3 names; `fetchReviewKeys` hardcodes `["tv","movie"]` (`:520`) and has to **widen** for a preview viewer; `fetchLikeKeys` (`:737-760`) has no media restriction; `fetchIncomingLikeKeys`/`fetchIncomingCommentKeys` have none either but run only on the signed-in member's own tabs (`shouldShowIncoming`, `:1325-1327`). #2963 names a tab in every criterion and requires a mutation check **per source**.
3. **`getProfileStats` feeds two routes**, `/users/profile` and `/users/me` (`src/app/api/v1/users/me/route.ts:92`), so #2961's count criterion names both.
4. **Three web book pages nobody was gating.** `isDisabledPath` matches path bases at the root (`src/lib/media-types.ts:384-391`) and the proxy matcher covers only root `/book` and `/books` (`src/proxy.ts:440`), so `/<username>/books`, `/<username>/book/<slug>` and `/<username>/likes/books` fall outside both. All three are #2966's. The web liked-**Lists** page uses the same `family: "liked"` intent #2964 changes, so it is #2964's.
5. **`media_preference=books` is not a testable shape for the web pages.** `getServerMediaMode` reads the host and the `x-media-mode` cookie (`src/lib/media-mode-server.ts:16-21`); `media_preference` only arrives through `src/proxy.ts`, which writes `x-media-mode` on the **response**, so it lands on the following request. #2966 tests a `books.` host and an `x-media-mode=books` cookie.
6. **The watchlist refusal needs nothing from the preview.** `POST /api/v1/watchlist` accepts `book` through the shared `toggleWatchlistSchema` (`packages/shared/src/schemas.ts:118-122`) and `refuseMissingMediaReference` checks only tv and movie (`src/lib/tmdb-existence.ts:141-148`). #2965 refuses **at the route**, not by narrowing the shared schema, because the web's server action parses the same schema and this spec does not change the web. That is why #2965 is offerable now, and why round 1's "including a viewer who holds the preview" clause had to go — it could not be set up on a ticket that is unblocked before #2936.
