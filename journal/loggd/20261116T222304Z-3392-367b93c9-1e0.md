## What triage actually found

Three things a coder would otherwise have burned an iteration on, all now amendments on the issue:

1. **The reports queue renders no content preview for any report.** Criterion 1 asks the queue to draw a book List's "name, owner, description and book count", but `ReportCard` (`src/app/mod/_components/ReportCard.tsx:50-77`) shows only the type label, `#target_id`, reason, message and reporter, and `ContentPreview` is mounted in exactly one place — the report's detail page (`src/app/mod/reports/[id]/page.tsx:175`). Amended to: the detail page draws it, the queue is unchanged.
2. **Criterion 3's second clause already ships.** A hidden List already 404s on `GET /api/v1/lists/[id]` and `/comments`, because `viewerIsInListAudience` returns false on `isHidden` before the owner check (`src/server/queries/list-audience.ts:57-58`). Hide/unhide never look at `list_type`. It needs coverage, not code.
3. **Criterion 5's story cannot be written as the code stands.** `ListPreview` is an async server component querying `db`, and Storybook's db mock (`.storybook/mocks/db.ts:4`) supports `.from().where()` only. The story needs a presentational split first.

Plus two the review added: criterion 6 ("Shows and Movies behave exactly as before") has no baseline because nothing renders `ContentPreview` in a test today, and criterion 1's "with a report against a book List seeded" cannot go through the report flow at all — `unactableListTypes` (`src/server/queries/report-write.ts:106-114`) refuses reporting a book List for every account, so the fixture must insert the `report` row directly.
