## The thing to know before touching this area again

**Another agent shares this worktree and it committed onto my branch.** The
browse/MobileHeader work that the last two journals describe as "uncommitted in
the shared tree" was committed at 01:17 as `e23ed97b feat(browse): move
quick-add into the navbar on sm/md` — onto `ralph/630-dead-push-targets`, the
branch I had created ten minutes earlier. Not malice, just a shared checkout.

The fix, which is the cheapest reversible one and is worth copying:

1. `git branch quickfix/browse-navbar-portal e23ed97b` — the commit is now
   reachable by name and nothing is lost.
2. `git reset --mixed origin/main` — their six files go back to being
   working-tree edits, exactly the state they had been in for two iterations,
   and my own untracked/modified files are untouched.
3. Stage by explicit path, commit.

`reset --hard` would have destroyed my own modified `schema.ts`; `--mixed` is
the whole trick. Do **not** try to dodge this with a second worktree: it has no
`node_modules`, so lint-staged in the pre-commit hook has nothing to run.

**So: check `git log --oneline -1` before you commit, not just `git status`.**
A shared worktree can grow a commit under you as easily as a modified file.

## The `as`-assertion trap, confirmed and now avoidable

The pre-commit `eslint --fix` really does strip `{} as Record<string, unknown>`
and really does break the typecheck that follows (`TS7053: expression of type
'"ticket-ok"' can't be used to index type '{}'`). **Test it before you commit**:
run `bunx eslint --fix <file>` yourself, then `bun run typecheck`. The fix is
not to re-add the assertion — it is to pick a value that carries its own type,
here `new Map<string, unknown>()`. Return-type annotations are the same idea for
functions.

## The migration numbering, and what the second lander owes

`drizzle/0024_polite_pete_wisdom.sql`, not 0023, because #642 holds 0023 on
another unmerged branch. Renaming the `.sql` + snapshot + `_journal.json` entry
by hand is safe and takes a minute.

What renaming does **not** fix, and cannot: `0024_snapshot.json` records `0022`
as its parent, because that is what `main` had. When both land, two snapshots
claim 0022 and the chain forks. `drizzle-kit migrate` does not care (it runs
files in journal order), but the next `db:generate` after the merge reads the
chain and produces a wrong diff. **Whichever branch merges second must delete
its `.sql`, its snapshot and its journal entry and re-run `bun run db:generate`
against the new `main`.** Both PR bodies say so.
