**Key decisions.**

- **The deleted guard's comment was false, which is why the guard could go.**
  `updateListContentCore` (`src/server/queries/list-content-write.ts:313`) refuses only
  `input.items?.length === 0` — an *explicit* empty array — and `updateListContentSchema`
  has `items` optional. `toSave` omits the `items` key entirely when staged is empty, so an
  emptied session never sends it. Nothing downstream changed.
- **The seam worth carrying forward: `applyImmediate` moves baseline and staged together**
  (`list-edit-session.ts:456-461`). Emptying an edit session *alone* therefore leaves
  `isDirty()` false and `toSave()` null. Criterion 3's "still saveable" only means anything
  alongside a buffered edit. My first brief got this wrong by placing the new case beside
  the creation-only one; it now lives in `describe("immediate actions")` and asserts
  `isDirty()` false *before* the rename.
- **Both guards mutation-tested on a committed tree**, so neither criterion is nominal.
  Restoring `LAST_ITEM` + the web guard fails exactly the two inverted cases; restoring
  `rows.length > 0` fails exactly the new mobile case.
- **One finding declined on purpose.** `list-content-write.ts:312`'s comment ("every list
  keeps at least one item") now contradicts the product rule, but criterion 5 forbids
  editing outside `packages/shared/`, `src/app/list/` and `mobile/`. Flagged in the PR body
  as a follow-up; a later iteration should not treat it as a bug it discovered.

  is a `registerRows` no-op skip and `ThumbnailEditor.tsx:373` is an existing empty state.
