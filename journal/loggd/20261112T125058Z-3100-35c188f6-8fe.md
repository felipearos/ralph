**What shipped.** The v1 Book detail read's viewer state gains `readingSince`:
the ISO-8601 instant the signed-in viewer's `read_status` row last changed, when
their read status is `reading`, and `null` otherwise — Read, Wantlist-only, no
row, or a Reading row with no recorded change time. The four book library writes
(status, wantlist, rating, like) answer it too, since they share
`getUserReadStatus`. Nothing new is stored: no schema change, no migration.

**Key decisions.**
- The field lives on a new `BookDetailViewerLibrary extends BookViewerLibrary`,
  not on `BookViewerLibrary` itself. The latter is `BookViewerStateEntry`'s
  base, so widening it would put the field on every per-cover batch entry and
  rewrite ~70 fixtures. The batch reader keeps its own
  `BatchExternalStatusResult`, so it cannot invent a timestamp it never read.
- A same-status Reading write moves the field. Documented, not guarded:
  guarding the conflict update would change a write path music shares, for a
  field the ticket accepts as an approximation.
- Mobile's optimistic guess can leave `readingSince` beside a non-Reading
  status — transient and currently unrendered. Not widened, because
  `BookViewerPatch` is also spread over Book Viewer State entries. Written up
  in the PR body as the follow-up for whoever first draws the field. This was
  the one correctness P3 dropped.
- Log-sheet prefill, which the ticket's prose gestures at, is out of scope:
  no sheet exists yet.
- `CONTEXT.md` gains `**Reading Since**` in Title Case, matching every other
  glossary entry, though the issue's prose writes "Reading since".
