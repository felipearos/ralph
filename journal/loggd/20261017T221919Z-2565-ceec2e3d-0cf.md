## What landed

Most of #2565 had already shipped in #2453 (merged 2026-10-15, two days before the issue
was written), so the issue body describes a world `main` had left behind. This PR closed the
three real gaps found by walking each acceptance criterion against the code:

1. `src/app/settings/_components/AuthForm.tsx` now maps the provider's `weak_password`
   refusal through `weakPasswordRefusal` instead of surfacing its raw text.
2. `src/app/reset-password/page.tsx` stopped trimming whitespace off its two password
   fields — the shared policy is deliberately untrimmed, and sign-up already kept spaces.
3. `src/lib/password-policy-conformance.test.ts` fences both classes of regression and now
   scans `src/lib/auth`, `src/server/auth` and `mobile/lib`.

Tests: new `AuthForm.test.tsx` (7), new `reset-password/page.test.tsx` (9), an

assertion in `e2e/password-reset.spec.ts`, a new e2e case in `e2e/credential-step-up.spec.ts`

## Key decisions and dead ends

- Criteria 1, 3, 4, 5 and the `supabase/config.toml` line were already satisfied on main.
  The PR body carries the per-criterion table. A future iteration should not re-implement them.
- Mobile needed nothing: all four mobile password screens already route through
  `getPasswordError`, and `mobile/lib/credentials.ts:307` already maps the refusal.
- The first weak-password fixture was a plain object, so the mutation check passed for the
  wrong reason (`AuthWeakPasswordError` extends `Error`). Replaced with a real `Error`
  carrying a provider sentence, and both bug shapes — mapping removed, and mapping reordered
  after `error.message` — were mutation-checked.
- Conformance rules are name-vs-CALL sensitive: a `/weakPasswordRefusal/` name match was
  satisfied by the import line alone. The rule now requires `weakPasswordRefusal(`.
- Widening the conformance scan to all of `src/lib` + `src/server` was wrong — 19 files
  mention "password" only in passing, so a rating `.score >= 7` would have read as a zxcvbn
  gate. Narrowed to the auth helper layer.
- The settings e2e test deliberately fakes the provider with `page.route` fulfilling only
  `PUT /auth/v1/user`: `supabase/config.toml` keeps `minimum_password_length` equal to
  `PASSWORD_MIN_LENGTH` with `password_requirements` empty, so a correct stack can never
  refuse a password the shared client policy accepted. The mapping is drift insurance.
  Everything else takes `route.fallback()`. Do not "fix" it into a real refusal.
- Deliberately out of scope, named in the PR: non-weak failures on web reset and web
  settings still show the provider's message, unlike mobile. Worth a follow-up ticket.
