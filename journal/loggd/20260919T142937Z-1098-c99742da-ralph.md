## READ THIS FIRST: a value assigned inside a React state updater is not readable after the await

This was the sharpest bug of the iteration and the *verification* pass caught
it, not the two first-round axes. The bulk remove needed to remember the Cover
Pin each title left behind, and the generated code did it the obvious way:

```ts
let pin: MediaRef | null = null;
await changeMembership(item, false, (state) => {
  const found = state.coverPins.find(...);
  if (found) pin = toMediaRef(found);   // written inside the updater
  return { ...state, coverPins: state.coverPins.filter(...) };
}, ...);
removed.push({ item, pin });            // read right after
```

Two things make that wrong, and both are invisible in review unless you are
looking for them:

1. **The updater runs when React processes the update, not when `setStaged` is
   called.** `changeMembership` calls `setPendingItems` first, which marks the
   fiber dirty and kills the eager-evaluation path — so the updater is deferred
   to a render. With a mocked API resolving in microtasks, *no render flushes*
   between the write and the read, so `pin` was `null` for every entry. In
   production the network await usually lets a render through, which is worse:
   it works until a fast response on a busy thread loses the race.
2. **The updater runs twice** — `applyNow` calls it for `staged` and again for
   `baseline`. A side effect in there happens twice by construction.

The fix is to read what you need *before* the write, from the ref:
`const pinsBefore = stagedRef.current?.coverPins ?? []`. Deterministic, once,
no scheduling assumption.

**The general rule: a state updater is not a place to compute a value you
intend to read. It is a pure function of previous state.** If you catch this
shape in a diff, it is a bug even when the tests pass.

## The test for it did not exist, and passing tests proved nothing

The whole pin path had zero coverage — the fix-round tests covered the note
restore and not the pin. So the bug shipped through a green suite. I wrote the
missing test and then **mutation-tested it** (stub `pinsBefore` to `[]`): it
failed, so the test is real. That took two minutes and is the only reason I
believe the fix.

Worth repeating from the standing lesson: a green suite is evidence about the
tests you have, not about the code.

## The screen's own doctrine settled the design, and it was in the file header

`mobile/app/list/[id]/manage.tsx` opens with a comment saying name, description,
order and notes are *staged* and published by Save, while membership is
*immediate*. That one paragraph answered three design questions I would
otherwise have had to guess at:

- bulk remove is immediate, not staged, so it loops `changeMembership` and
  inherits the in-flight guard, the revision advance and the pin cleanup;
- undo *appends*, because `handleAdd` appends and the server appends — the
  screen must not claim an order the server does not have;
- the note and the pin, which the membership write cannot carry, go back onto
  `staged` **alone**, which makes the screen dirty so Save publishes them.

That last one is the fix for a silent data-loss bug the spec axis found: the
first pass restored the note into staged *and* baseline, so `dirty` was false,
Save was greyed out, and the note the member could see vanished on next reload.
**Read the file header before designing against a screen like this.**

## The shared mutation observer is a live hazard on this screen

`changeMembership` routes every write through one `useMutation`. React Query
drops an in-flight call's callbacks when `mutate` is called again, so a second
write mid-loop means the first promise **never resolves**. The spec axis traced
it end to end: bulk-remove two titles, type in the header search and add one
mid-loop → `bulkBusy` stuck `true` forever, bar disabled for the session, and a
write that *succeeded on the server* never applied, leaving `baseline` holding a
title the server no longer had.

The hazard is pre-existing (two fast single-row removes collide the same way),
but bulk made it easy to hit. Mitigation: hide the Content block during
selection mode, clear the busy flag in a `finally`, and guard re-entry with a
ref. **If a screen funnels every write through one observer, any new loop over
that function is a correctness question, not a performance one.**
