## Reusable: localising a Buildkite failure by DURATION

`gh pr checks` says `fail` while a build is still running, so it cannot say
which step died. What worked, with no API token:

1. `docker logs buildkite-agent | grep 'builds/<n>#'` → Starting/Finished job
   pairs. Subtract timestamps for each job's duration. Build #870 reported
   failing with only THREE jobs logged — upload (18s), sentinel (15s), and one
   4m29s job. e2e had not started (queued behind another build's e2e), so the
   4m29s job was necessarily `quality`.
2. **The duration then localises the failure inside `quality`'s command chain.**
   4m29s is just past `bun lint` (~4m on that box) → `test:coverage`. That is
   what prompted running `bun x vitest run --coverage` locally with
   `ACTION_RESULT_BASE_REF=origin/main CONFORMANCE_BASE_REF=origin/main`, which
   surfaced both ledger failures immediately.

A ~35s `quality` death still means the prologue (migration check). A 3–5 minute
one means lint finished and a test failed. Read the duration first.

(`git diff --stat origin/main -- ralph/ scripts/` empty), which is the cheap
proof that neither is yours. Ignore both.
