## Two decisions the parent left open, both settled from the cores rather than from taste

1. **What a write answers.** The parent said each write "answers the confirmed state", and at `origin/main` nothing can produce that: `setExternalStatusCore` returns `{ success, newStatus }` (`src/server/queries/externalStatus-write.ts:142`) and `setExternalWantlistCore` returns `{ success, isWantlisted }` (:188) — each **echoes its own input** and is silent about the other field. Clearing a status leaves a wantlisted row wantlisted (:123-125), so the app cannot derive the pair from what it sent, and the parent's "setting a status takes the book off the Wantlist … on screen" would be unbuildable. #2969 therefore answers the pair read back through the existing read core `getUserReadStatus` (`src/server/queries/readStatus.ts:24-36`): one write core, then one read core, no SQL in the route, still a Thin Transport. #2970's prose says it reads that pair rather than inferring it.
2. **Which rows.** The web's book actions write `mediaType: "book"` (`src/app/book/[slug]/_components/BookActionBar.tsx:48`), but the shared Media Mode table maps the Books mode to `mediaType: "tv"` (`packages/shared/src/media-filter.ts:36`) — and that table is also where the path segment comes from, so a coder sent there for one thing can take the other. A route that did would write valid rows into a **second** library. #2969 asserts `media_type = 'book'` and the web's `external_id` against a real database.

Neither is a product decision: both are the only readings under which the parent's own criteria 1, 5 and 9 can pass. No `decisions` block was needed, so no rule citation was made.
