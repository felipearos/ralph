**What shipped.** `/api/v1/lists/[id]` GET ran ~12 independent reads serially

no prefetch.

**Key decisions.**
- The enabler was making `movieMetadataById` a `Map<number, Promise<Movie>>`
  via `movieMetadataOnce`. A value map would have fetched every page movie
  twice once the prefetch and the hydration overlapped.
- The route file itself was orchestrator-written, not delegated, because the
  change moves the Audience, blocks and adult gates (the visibility carve-out).
  Tests were delegated.
- Codex P2 #1: `Promise.all` → `Promise.allSettled` on the two gates. A
  fulfilled Audience denial answers 404 before either rejection is read; with
  neither gate hiding the List, a rejection is re-thrown so the response is
  500, exactly as the serial reads behaved.
- Codex P2 #2: `buildPage`'s uncontrolled branch put the whole page slice (up
  to 100) in flight. Bounded at 10 per read pass. The diagnosis worth keeping:
  the accidental bound the prefetch used to provide only ever covered a
  signed-in viewer who had opted out of adult content, on page 0 — so the
  unbounded fan-out was reachable on `main` already by every signed-out reader.
  This PR widened the hole rather than creating it, which is why the bound went
  on the reads instead of on restoring the prefetch ordering.
- The honest ceiling is **10 per read pass, not 10 overall**: the prefetch and
  the hydration are two independent `fetchInBatches` fronts over one reuse map
  and can drift apart. Said so in the code comment, both tests and the Codex
  reply. A later edit must not quietly upgrade that to a global semaphore.
