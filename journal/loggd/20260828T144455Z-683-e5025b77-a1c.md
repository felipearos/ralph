## The real finding: no GoTrue rate limit can be enforced on the local stack

`security/suites/auth-abuse.security.test.ts` tried to prove throttling by
exhausting `token_verifications` against `POST /auth/v1/verify`. It cannot. From
the GoTrue v2.186.0 source, `performRateLimiting` in `internal/api/middleware.go`:

```go
limitHeader := a.config.RateLimitHeader
// If no rate limit header was set, ignore rate limiting
if limitHeader == "" {
    return nil
}
```

Every IP-keyed limiter funnels through that one function. `GOTRUE_RATE_LIMIT_HEADER`
is in **neither** the Supabase CLI binary nor the running `supabase_auth_loggd`
container's environment, and `supabase/config.toml` has no key for it. The hosted
platform sets it; `supabase start` does not.

Confirmed by execution before any code changed — 40 POSTs to `/auth/v1/verify`
against a configured limit of 30, no 429; 35 POSTs to the web3 grant, same.

Two techniques worth reusing:

- **List what the CLI can actually emit**:
  `strings <cli-binary> | grep -oE 'GOTRUE_RATE_LIMIT_[A-Z_]*' | sort -u`.
  That is how "the CLI has no knob for it" stopped being a guess.
- **Probe the idle local stack directly** with `curl` before touching code.
  Check `ps -eo etimes,args | grep -E 'playwright|vitest'` first so you are not
  spending another loop's budget.

`email_sent` is the exception and it matters: `mail.go` calls a bare
`a.limiterOpts.Email.Allow()` — one global bucket, no key, never reaching the
header check. So "nothing binds locally" is true of it only because the CLI
ships `GOTRUE_RATE_LIMIT_EMAIL_SENT=360000` when SMTP is off, **over the `2` in
config.toml**. The local TOML value is not what the container starts with, and
the conformance test compares declaration↔TOML, never TOML↔container.
