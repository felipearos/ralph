## What the two review passes bought: two criteria that fail on correct code

This is the second iteration running where the spec stage earned its cost on a
label-free ticket, and both defects were of the same species — **a criterion that goes
red against a correct implementation**, which costs a coder an afternoon and ends in a
wrong "fixed" diff.

1. **Criterion 5's first grep, in the body as written by iteration 16.** It claimed
   `rg -n 'viewerId' src/app/\[username\]/ -g '*.tsx'` shows `viewerId` only in
   `ActivityContent.tsx` and `MediaActivityContent.tsx`. It really returns **62 lines
   across 28 files** — `viewerId` is an ordinary local and prop name across the whole
   profile tree. A coder could only have "passed" it by deleting unrelated production
   code. Narrowed to `-g '*Activity*.tsx'`, which returns exactly the two lines (in
   either order; `rg` promises none). My first draft said "more than 40 files"; review
   pass 1 corrected it to 28 and also caught that my illustrative brace expansion named
   two files that do not exist.
2. **My own replacement for criterion 4, caught by review pass 2.** I specified
   `Extract<keyof LoadActivityPageInput, "viewerId" | …> is never`. That **passes
   against broken code**: widen the schema with `z.looseObject`/`.catchall` and the
   input type gains an index signature, `keyof` becomes `string | number`, and
   `Extract<string | number, "viewerId" | …>` is *still* `never` while the type now
   admits any `viewerId`. The arguments have to go the other way —
   `Extract<"viewerId" | …, keyof LoadActivityPageInput>` — so each forbidden name is
   tested against the key set. **Generalisable:** when asserting a key is absent,
   `Extract<forbidden, keyof T>`, never `Extract<keyof T, forbidden>`. I had also asked
   for a demonstration of the assertion failing "when widened to admit a viewerId",
   which under the wrong order would itself have stayed green.

Review pass 1 found a third of the same species in Amendment 5, mine: the mutation
check's failure count. I said five; running the whole `src/app/api/v1/activity`
directory gives **six**, because `route.exclusions.integration.test.ts:236` ("answers
an empty page to a member the Profile Subject has blocked") runs the real reader and a
null viewer skips `blockExistsBetween` (`src/server/queries/activity.ts:1350`), so the
page returns items. Scoped the check to `route.test.ts`, where five is exact, and
explained the sixth so a coder who runs the directory is not derailed.
