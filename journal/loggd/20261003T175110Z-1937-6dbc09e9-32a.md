**What shipped.** Three new `/api/v1` trending reads — `people/trending` (TMDB
`trending/person`, behind the adult gate), `members/trending` (followers gained in 7
days, over a new cached directory ranking) and `lists/trending` (likes in 7 days, via a
new `TrendingDiscoveryIntent` in the List Summary read boundary) — with shared response
types in `packages/shared/src/trending-types.ts`, three mobile hooks, and
`SearchResultsList` rendering each tab's own trending through the row components that tab
already uses, so an empty query still records a Recent search. `CONTEXT.md` gained a
**Trending** entry, defining it as a per-kind discovery read and distinguishing it from
Popular by metric rather than by window.

**Key decisions.**
- Members trending barely differs per Media Mode: the Mode scopes the counts, not who is
  listed. Switching the `review` join to INNER is the one-line alternative; it was
  offered in the PR body rather than chosen, so a human decides.
- Blocked accounts' follows and likes still count toward rank, following List
  Popularity's documented rule; blocks decide who is *listed*, not what ranks.
- Signed-in Lists trending is uncached, because `readListSummaries` caches only for
  `viewer === null` — the module's existing design, not a new exception.
- Title tabs gained the trending error state too: AC4 asks for one and one shared path
  was cheaper than two.
- No `browse-adult-gate.test.ts` row for people — that table is keyed `shows`/`movies`
  over raw TMDB payloads. The route's own test covers all four gate cases.
- Declined on review: `time_window=day` (the sibling routes use the same window), a
  `window: "all"` branch, a `followerGain`/`followersGained` rename (the internal/wire
  split `toMembersDirectoryMember` already makes), a `gainById` re-attach, extracting
  the three hooks' shared boilerplate, and de-duplicating three lines of
  `UNSCOPED_LIST_TYPES`.
