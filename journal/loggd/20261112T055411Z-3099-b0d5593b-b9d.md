## The two review rounds were the whole value of this iteration

Three blocking findings, every one of them a *plausible implementation of the body that breaks AC6*:

1. **Round 1: my read filter was a keep-list, and `track` belongs to no mode.** I had said to keep rows whose `metadata ->> 'list_type'` is in `viewerListTypes(browsableTargets)`. `viewerListTypes` says in its own doc comment that "`track` is in no mode's List types, so no viewer gets it" (`media-mode-scope.ts:187`), and a track List can take collaborators (`listTypeEnum` has it, `createListSchema` accepts it, `getListIfOwned` restricts no type). So a keep-list hides every track List's invitation and acceptance from everyone, permanently. The body's rule is the other direction — hide a row "whose List type belongs to a Media Mode the viewer may not browse" — so the filter has to be a **hide set built by walking `LIST_TYPES_BY_MODE` and taking the non-browsable modes' types**, which excludes `track` by construction. *Lesson: `inArray(list.list_type, viewerListTypes(...))` is right where it is used today (#2964's liked-Lists read, `list-summary/index.ts:834`) because it filters a real column over Lists that exist; it is wrong as a row-hiding predicate, and the asymmetry is entirely about `track`.*
2. **Round 2: the write half had the same hole**, because I had written "`isMediaModeBrowsable` for the mode of `listData.listType`" and **there is no ListType-to-MediaMode map at `main`** — only `LIST_TYPES_BY_MODE` running the other way. Every obvious way to write that lookup gives `track` no mode and suppresses its acceptance notification. The comment now says both halves use one shared hide set, keyed on the owner's targets for the write side, and names where the helper should live.
3. **Round 1: type-scoping is not a substitute for the SQL NULL exemption.** `metadata ->> 'list_type'` is NULL on every non-collaboration row, and `NULL IN (…)` is NULL, which `WHERE` drops — so a naive predicate empties the entire bell for every account. I had offered `notification.type IN (collab types)` as an *alternative* to `OR … IS NULL`. It is not: collaboration rows written before `list_type` entered the metadata carry no `list_type` either (`notification-links.ts:52`, "Legacy notifications (created before owner_username/list_type were added)"), so type-scoping alone vanishes legacy *show*-List rows for everyone.

Round 2 also confirmed the Drizzle shape (`or(isNull(x), notInArray(x, hidden))` is correct, including for a wholly NULL `metadata`, and `notInArray(x, [])` emits `true` since Drizzle 0.30 — the repo pins `^0.45.2`), and corrected four citations.

## What the mapper found that the body does not say

- **The two halves key on two different accounts.** The acceptance core's `userId` is the *acceptor*; AC1 is about the **owner**, reached only as `accepted.addedBy` (`list-collaborator-write.ts:551`). The auth wrapper's `browsableTargets` is therefore the wrong answer on the write side and the owner's previews need their own `readAccountAccess` inside the core. Passing the route's value down makes AC1 pass its happy path and answer the wrong question in every case the ticket exists for.
- **The notification row has no `list_id` column and these deliveries set no `media_type`.** That is why **#3102 does not cover this ticket**: #3102 keys its list/count/web filters on the row's `media_type`, which is null here, and writing #3099's filter as a `media_type` predicate would filter nothing. Complementary, not duplicates — worth knowing before someone closes one as covered by the other.
- **The unread count is a separate COUNT query** (`notifications/route.ts:22-39`), not derived from the answered rows, and `hasMore` over-fetches `limit + 1`. AC3 needs the predicate in both `where` clauses, and the filter must be in SQL or paging goes short.
- **The web is untouched for free**: the page and the bell use `getUserNotifications`, which shares no query with the v1 GET. The *write* half does change web behaviour, through the shared core — the body's "the web's notifications page is not changed" is about the read.
- **`userBlock-write.ts:123-133` is an existing `metadata ->> …` predicate on this same table**, scoped by `eq(notification.type, …)`. My draft claimed no such predicate existed under `src/server`; the round-1 reviewer found it. It is the pattern to copy.
- **The tests as they stand cannot see either guard.** `notifications/route.test.ts` mocks `db.select`, so a mock cannot fail on the NULL trap (AC6's mutation requirement would be satisfied vacuously) — the read half needs a DB-backed test. And `list-collaborator-write.integration.test.ts` mocks `notifyAfterResponse` as a bare `vi.fn()`, so the callback never runs; the comment says to read the owner's access *before* the callback, which is what makes the skip visible there.
