## What I decided and why
#795 (child of spec #329, filed from #765) asks the operator to choose between keeping
#520 — a signal is an ending, so a shutdown's SIGTERM leaves the loop stopped — and
restarting a self-recorded SIGTERM `interrupted` whose stop predates the current boot.

Verdict `ready-for-human`. The decisive finding is that the two written statements point
opposite ways, so this is exactly the "design decision that neither the ticket's parent
spec nor the README settles" case:

- For option 2: spec #329's criterion 2 ("After a reboot, the same is true without anyone
  acting") and its list of what stays stopped, which does not include a shutdown; plus
  `README.md:2163-2164` "A reboot is covered by the dashboard's reconciler, which
  restarts every loop that died without choosing to stop."
- For option 1: `dashboard/README.md:1988-1994` "**A signal is an ending, not a death.**
  … so the loop stays stopped and Start or Resume work picks it up. Before it, on
  2026-10-28, a shutdown came back at boot as every loop restarted." Same reason in
  `signal-stop.sh:8-9` and `ralph.sh:672-674`.

Two further reasons it is not a coder's: `## Acceptance criteria` reads "To be written
once the choice is made" (nothing to finish against), and the criterion that would prove
either option is measured across a host reboot, which no iteration can observe.

Either way `README.md:2163-2164` is stale — it predates #520 and now holds only for
SIGKILL, an OOM kill or a power cut. The comment says so, and sketches the criteria for
both options so the choice comes back to intake ready to write up.
