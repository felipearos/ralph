## What the ticket is

A `learning-fix` ticket off learning `github-graphql-throttled-at-merge`: on 2026-11-03 ralph's merge step on PR #656 saw `gh pr view` and `review-threads.ts` both fail with `GraphQL: API rate limit already exceeded for user ID 21047325`, twice, while `gh api rate_limit` still showed ~3.4k graphql points. GitHub's secondary limit, on a token every loop on the host shares.

## What I decided, and the evidence

Ready for a coder, not for a person. The mapper found the whole chain at `origin/main`:

- `frontier/github-rate-limit.ts:38-39` — `RATE_LIMIT_TEXT` matches `rate limit exceeded`; GitHub's wording puts "already" in the middle, so `classifyRateLimit` returns `null` and **no** caller retries or reports `rateLimited`. The test fixtures (`:30,57`) only cover the wording without "already". This single regex is why the whole harness is blind to this throttle.
- `review-threads.ts` never imports the classifier. Its one catch at `:249-252` maps every `gh` failure to exit 5, so `RATE_LIMITED_EXIT` (75) is unreachable there, and `prompt.md:905-908` has to call a throttle "unreadable".

So: widen the pattern (must classify as `{ kind: "unspecified", retryAfterSeconds: null }`, like the no-"already" form does today), classify and retry both `gh` calls in `review-threads.ts`'s `main` through the existing `withRateLimitRetry` sharing one `RetryBudget`, exit 75 when the budget is spent, document 75 in the header table and in §6.

Two things the review caught that I would have shipped wrong:

1. **`fake-gh.ts` cannot fail a call with chosen stderr.** `apiGraphql` (`:1604-1606`) answers the review-threads query or refuses with `unsupported: …`, which is not throttle text, and the settings are fixed at `:23-26`. Without a new knob there, neither half of the fix is testable. It became change 3 and AC2.
2. **A zero retry budget never retries.** My first AC set `RALPH_FRONTIER_RATE_LIMIT_BUDGET_SECONDS=0` to keep the test fast, and `withRateLimitRetry` (`:196-205`) then throws on the first classify — so an implementation that maps "throttled" straight to `return 75` with no wait would have passed every criterion, making the change a relabel of exit 5. AC3 now uses base 1 with a budget of 3 (base is clamped to ≥1 at `:148`, so the first wait is 1-2s and fits) and requires the run to **succeed**. AC4 keeps the zero budget for the persisting-throttle case.

Also from review: `gh repo view` at `:244` was missing from my scope — the prompt invokes the tool with no `--repo` (`prompt.md:876`), so that lookup runs every time and takes the same limit; AC1 pins the exact signal instead of "non-null" and names its near-miss negative; AC5 names the exit-64 case; AC6 asks for a `prompt-render.test.ts` assertion on the rendered §6 so the prompt wording is mechanical, not just "the suite passes".

**Deliberately out of scope, stated in the body:** the ~40 other `gh pr …` call sites (`claim-race.ts`, `merge-wait.ts`, `pr-wait.ts`, `pr-medic/*`, `ci-doctor/*`, `sentinel/*`), the `gh pr view` the model runs by hand in the merge step, and any host-wide pacing or serialisation of the shared token. Nothing in the repo serialises GitHub access across loops today — `RALPH_FRONTIER_CONCURRENCY` is per process and only inside one frontier fan-out — so that is a design, not a ticket, and I did not invent one here.

Not `ready-for-human`: no secret, no host state, no product decision, no migration. Three source files plus a test helper, and the prompt edit is this repository's own.
