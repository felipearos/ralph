# 2026-10-20 — #353 Two of the three "subprocess timing flakes" were real defects

**Outcome: merged.** PR #356, squash-merged as `d5a1284`, issue #353 auto-closed.

**Key decisions.** The ticket read as three load-induced flakes; only one was.

- `codex-executor.sh` copied the real git index with a plain `cp`, which stamps the copy
  with a newer mtime and so destroys the signal git uses to re-read a racily clean entry
  (one whose cached mtime is not older than the index file's own). `git status --short`
  inside the sandbox then reported a clean tree over a real edit — the CI reds' exact
  message. Fixed with `cp --preserve=timestamps` (codex-executor.sh:225) and pinned by a
  deterministic regression case that reds on `origin/main` on an idle host. The cause was
  proven before any code changed: plain `cp` → empty `git status --short`, `cp -p` →
  `M app.ts`, and the same split through the script's `update-index --skip-worktree` path.
- `cp -p` was narrowed to `cp --preserve=timestamps` on review: `-p` also attempts mode
  and ownership, which under `set -euo pipefail` would kill the executor on a mount that
  refuses them.
- `runCommand`'s timeout path resolved over a still-live process group (4 of 25 timed-out
  runs under load). It now waits for the group, bounded at 2 s, degrading to resolve — a
  supervisor wait never throws. The review's most serious finding was not in the ticket:
  an earlier version made `close` an `async` listener, which could leave `runCommand`
  unsettled forever if its last log write threw. Reverted to a synchronous listener with
  the wait in `reapGroup`.
- The `experiments.test.ts` case's own fixed-time assumptions (a 1000 ms literal, one
  unwaited `/proc` read) are gone: the kill is driven through `runCommand`'s abort signal
  once `child.pid` parses as a positive integer, and liveness is a bounded predicate poll.

**Dead end worth skipping.** The first regression case asserted the host's `git status`
BEFORE the sandbox run, and passed on `origin/main`. Any read of the repository's own index
— `core.optionalLocks=false` included — re-reads the racily clean entry and writes the index
back with that entry's stat invalidated, after which every copy reports `M`. The host
assertion has to come last.
