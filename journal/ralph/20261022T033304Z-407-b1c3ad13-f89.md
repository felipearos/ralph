# 2026-10-22 — #407 Usage limit: wait for the reset instead of stopping as failed

**Outcome: merged.** PR #412, squash-merged 2026-10-22 03:32Z (no merge queue on this repo, so `gh pr merge --squash`). #407 closed and marked rita-done.

**What it does.** New usage-limit.ts detects a turn rejected by the account usage limit and works out how long to wait: resetsAt first, then the reset time in the message text, then a default. It adds a margin, caps the wait at the limit window and never waits less than 60s. On a rejected turn ralph.sh skips the recovery turn, records usage-wait, decrements the iteration counter and continues. The top of the loop then waits with control_sleep so operator controls still work. loop-state reports usage-wait as blocked. README documents it.

**Key decisions.** delegate.sh built slices a (usage-limit.ts), b (ralph.sh wiring) and c (tests). I wrote the README and the review fixes. Review findings fixed: the spec P2 on the budget handoff, and the standards P2s (no floor on the wait, tests on the wall clock; the test clock is now pinned).

**CI.** Round 1 (03ad580) was red, a real failure. The supervisor waited toward a 10:30pm reset and the 30s spawn timeout killed it. Fix: rebased onto main, renamed that test to "...when the wait cannot be armed", and made usage-wait.json a directory so detection fails and #411's fallback naming stays pinned. Round 2 (d56e524) was green.

**Known gaps (follow-up candidates).** There is no total wait budget across repeated limits, and Codex runners are not covered by the detection. Locally, one run of the usage-limit tests had 2 failures at load ~111 and they never reproduced.
