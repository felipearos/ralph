**What landed.** `triage-apply.ts`: a CLI that validates a triage plan, simulates
it, and applies it — an ordered, paced, idempotent write engine whose body edits
are reversible, plus the lease release and the marker's apply fields. Built over

re-run had already been spent (`run_attempt: 2`) before the pattern was clear.

`queued`, which the billing refusal never produced — handed the wait back, and
this session got green: run 36781191171, 3m39s on head `85526045`.

**Key decisions.**

- **No enqueue — this project has no merge queue.** No `mergeQueue` key in
  `.ralph/config.json`, no `.mergify.yml`, and `ralph.sh` renders §5.6's enqueue
  block empty. §5.6's prose forbidding `gh pr merge` describes loggd's hook, not
  this repo, which has only a `pre-push` hook; the delegate's rails deny `gh` but
  explicitly reserve "history, remote and queue control" for the orchestrator.
  Journal `20260930T114750Z-140-90679867-c9a.md` reached the same conclusion on
  PR #200. Merged directly with `gh pr merge --squash`.
- **The §7 release-marker format deviates from the issue deliberately.** Spelled
  as the issue writes it (`<!-- ralph-triage v1 loop=… -->`) it does not parse in
  `triage-marker.ts`, so `hasCurrentTriage` would never see the decision and every
  triaged issue would sit in the intake bucket forever. The fields ride as extra
  percent-encoded keys on the format that module already reads. Both review axes
  judged the deviation defensible.
- **`unblock` deliberately not implemented** — the issue assigns it to a later ticket.
- **Known gap, stated in the PR rather than papered over.** The
  `frontier/next.ts --dry-run --json` subprocess is not driven in a test: it
  materialises its payload from the harness's `origin/main`, so testing it would be
  a network test. `frontierVerdict` and `release` are exported and directly tested.
- **`delegate.sh` was used** for the implementation slices (brief per slice); the
  orchestrator owned the briefs, the diff review, the review-finding fixes and
  every gate.
