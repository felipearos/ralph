## What landed

The ci-doctor's gate — no model turn — may now re-run one candidate flake's
failed job, using a dedicated `write_builds`-only token
(`RALPH_BUILDKITE_RETRY_TOKEN`) the supervisor exports to that gate alone.
Four fences: candidate flakes only; never a merge-queue branch, an unfinished
build, or a PR branch that has moved on; one per candidate per 72h and six per
UTC day, claimed under the store lock; and only while both the host-lease store
and `readCi` report idle, re-checked immediately before the write.

Files: new `ci-doctor/retry.ts`; `bk-log.ts` (`--check-retry-token`,
`Buildkite.put`); `host-lease.ts` (`leaseInUse`, `requiredChecksFrom`,
`holderLapsed`); `store.ts` (`FINISHED_BUILD_STATES`); the gate's
`PollDeps.retry` + `retryDep` + `retryLine`; `preflight.ts`; README and
`adding-an-agent.md`.

## Key decisions

1. **`perCandidate` is a 72-hour window, not per candidate ever.** The durable
   guard is the row the scan marks `retried: true`, and `scan.ts` prunes rows
   at 72h; `retries.byCase` is day-scoped by the store's shape. Flagged in the
   PR as the spec owner's call, and the README says the window out loud. Making
   it per-candidate-ever needs a record on the `Case` — a store change.
2. **The retry needs the READ token as well**, which the issue never says.
   Free in practice (the gate already needs it to find a case), but an unstated
   condition; raised in the PR.
3. **`preflight.ts`: WITHHELD now outranks AVAILABLE and the environment.** No
   AC asked for it, but giving the token a checker forced it — otherwise a
   hand-run preflight reports `ok` on a token the supervisor had refused.
4. No `CI_HEALTH_VERSION` bump: `retries` already existed in the store.
5. The slot is claimed under the lock BEFORE the PUT; a non-2xx leaves it
   spent, because it does not say whether the job started.

## Reported, not fixed

- `expired` sits in the shared finished-state set because `scan.ts` records it.
  Neither review could establish whether Buildkite retries such a job; inert
  either way, since `expired` is a job state, not a build state.
- No cooldown after a `busy` retry: the issue puts these reads on the gate's
  budget and says nothing about backoff. Out of scope.
