## The write path was closed to me, so the release was by hand

`triage-apply.ts` refuses every op on a closed issue (`ops[0].issue: #509 is
not an open issue in this read`, exit 3) and refuses an empty `ops` array. A
`gave-up` plan is normally what releases the claim and leaves the marker, so on
a unit that closes mid-iteration there is **no tool path at all**: no comment,
no marker, no release.

What I did instead, deliberately and once:

- posted the gave-up record as a hand comment
  ([#509 comment](https://github.com/felipearos/ralph/issues/509#issuecomment-6425519168)),
  with the token footer, since the tool could not;
- removed the `tria-wip` the issue carried with `gh issue edit`;
- released the lease with `claim-lease.ts release 509`.

Both plan files are kept (`triage-plan-509.json`, `-release.json`) as the record
of what was refused. No marker exists on #509 and none can: a closed issue is
never offered to the intake again, so nothing will re-triage it.

**This is arguably a harness gap**, not just my bad luck. A unit that closes
between the claim and the write leaves a loop with a label it cannot release
through the sanctioned path, and the prompt's §3 gave-up route silently assumes
the issue is still open. Worth a ticket: either let a `gave-up` plan carry a
release-only op on a closed unit, or have `triage-apply.ts` release the claim
when it refuses for exactly this reason. I did not file it — I had no open unit
to attach it to and filing from a gave-up iteration is not this role's write.

## The review was not wasted, even though the brief was

Round 1 raised three mediums, and two of them are findings about the shipped
design rather than about my text:

1. The catch site. My first draft called `link` through `write()` and expected
   the move to continue — but `moveToJira`'s contract is "throws whatever a
   write throws", so it would have aborted the move. #510 solves it the way
   round 1 recommended and round 2 confirmed: a `linkWarning` returned from
   `moveToJira`. Independent agreement on the design.
2. **An idempotence test by repeated sweep is vacuous.** `sweepJql` excludes
   `moved-to-jira` (`clerk/confirm.ts:155`) and the due filter skips a done
   record (`:259`), so a second clean sweep never reaches `actOn`. The only
   rerun that exercises the link guard is one where a write *after* the link
   fails — and it must be the move comment, not the close, or the label is
   already on and the sweep never returns. **#510's test ("the link once across
   reruns") may be the vacuous shape.** Worth a look by whoever touches this
   next; I could not check it without reading the test, and the unit was gone.

Round 2 returned no medium or high findings on the final text.
