## The one thing worth remembering: the ticket named the wrong file, and the
## boundary test makes that a hard error

`## What to build` said to build the retry state in `dashboard/adapter.ts`.
`DashboardLoop` is not built there at all — it is built in
`aggregateDashboard()`'s roster map (`dashboard/aggregate.ts:484-524`), with two
other sites constructing the same shape (`absentLoop()` at `:242`, `basePanel()`
at `dashboard/preview.ts:304`). And `dashboard/read-only.test.ts`'s `ALLOWED`
table (`:66`) gives every dashboard module ONE import set: `aggregate.ts` may
import only `./contracts` (`:68`), and `adapter.ts` has no `./records` (`:72`).
So neither file can reach the feed or the schedule, and a coder following the
ticket would have had to edit that table — which the ticket's own last criterion
forbade. The two halves contradicted each other, and the reviewer found it as a
P1 by reading `ALLOWED` rather than the prose.

**For any future dashboard ticket: check `ALLOWED` in
`dashboard/read-only.test.ts` before naming a file in `What to build`.** It is a
layout constraint, not a convention. The layout this ticket now pins, which is
reusable:

- `records.ts` (imports `./contracts` only) — the row parser. `raisedAt()`
  (`:154-168`) returns `string[]` and drops the payload, so a sibling returning
  `{ id, at, retry }` deduped by `id` is needed; "read it the way the reconcile
  does" was not possible.
- `reconcile.ts` (already has `./records`, `./records-adapter`,
  `read-only.test.ts:204-213`) — the pure computation, taking the feed,
  `lastIterationEndAt` and the effective schedule as plain data. Taking the
  schedule as DATA is what makes the `RALPH_DASHBOARD_RETRY_SCHEDULE` override
  testable: `aggregateDashboard(runtime, clock)` takes no environment and must
  not read `process.env`.
- `contracts.ts` + `server.ts` — carried on the snapshot as an optional field
  beside `claims`/`ciHealth`/`learnings` (`contracts.ts:519-546`); `server.ts`
  is the only module importing both `./reconcile` and `./aggregate`.
- `aggregate.ts` — a projection, copying the value onto `DashboardLoop`.
- `dashboard/ui/retry-model.ts` + its test — the formatting. This repo tests UI
  logic through `*-model.ts` / `*-model.test.ts` (`feed-model.ts`), so
  "renders nothing extra" is otherwise unverifiable; the model returns an ISO
  time for the component to localise, because CI runs on the live loop host and
  a `toLocaleString()` assertion would be host-dependent.

## Other rules pinned (each was a review finding)

- The attempt number is the newest in-bound record's `retry.attempt`/`retry.of`,
  not a count of rows: a row may be written twice (`records.ts:162-164`).
- The `lastIterationEndAt` bound decides WHETHER there is retry state, not what
  it says; an absent bound drops nothing, matching #420 (a loop that errored
  before its first ever iteration).
- The gap index was ambiguous by one: `at + schedule[attempt]`, 1-based attempt
  over a 0-indexed schedule, with a worked example.
- "Spent" is a flag, not a sentinel time; a schedule shorter than the record's
  attempt also reads as spent.
- The retry state renders as a SIBLING of the `StopReason` lines (`app.tsx:887`,
  `:2758`), not inside their `entry.stopReason &&` guard — a loop mid-retry that
  is alive has no fresh stop.
