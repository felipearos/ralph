## Why one group and not several

The mapper resolved the real edit set per ticket at `origin/main` rather than trusting the spec's "each step is an independent PR". The four form one connected component through three files:

- `dashboard/read-only.test.ts` — three tickets, overlapping hunks. #609 drops `node:child_process` from the `adapter.ts` allow-list entry (`:80`) and adjusts the "exactly one `execFile(`" count (`:488-492`); #610 changes the `jav-adapter.ts` and `intake-adapter.ts` entries (`:199`, `:203`) and the intake `spawn(` regex (`:452`); #611 rewrites the file whole.
- the four PATH-fake adapter suites — `adapter.test.ts`, `adapter-claims.test.ts`, `adapter-performance.test.ts`, `adapter-timeline-failure.test.ts`. #613 moves exactly these onto the recording Executor, and #609 has to touch the same four because they assert the `COMMAND_SURFACE` shape (`adapter.test.ts:276-310`, `adapter-claims.test.ts:82-85`, `adapter-timeline-failure.test.ts:242-243`) and a spawn count (`adapter-performance.test.ts:59`) that #609 changes.
- `dashboard/README.md` — the read-only section is #611's by its own AC; #610 edits the intake cache paragraph (`:277`); #609 and #613 likely touch the architecture and tests sections.

So #609-#610-#611 collide in `read-only.test.ts`, #609-#613 in the suites, #610-#611 in the README. No pair is safely parallel, and the remaining likelihoods go the same way under "when in doubt, share the group".

The group costs almost no parallelism anyway: the blockers already serialise this tree (#611 blocked by #609 and #610, #613 by #609), so the only pair the dependency graph would have let run together is #610 and #613 — and those two meet in the README, and possibly in `dashboard/recording-executor.ts` if #610's Executor-driven tests extend the shared fixture instead of only importing it.

Useful facts the mapper established, for the next pass: there is no aggregating surfaces module — `COMMAND_SURFACE` lives in `adapter.ts:118-171`, `JAV_SURFACE` in `jav-adapter.ts:17`, `INTAKE_SURFACE` in `intake-adapter.ts:30`, and `read-only.test.ts` imports eight such constants one by one. A shared recording Executor already exists at `dashboard/recording-executor.ts:72` and is already used by six suites, so #613's "one shared fixture" is an extension, not a new file. `ALLOWED` lists shipped modules only, so a new test fixture needs no allow-list entry.
