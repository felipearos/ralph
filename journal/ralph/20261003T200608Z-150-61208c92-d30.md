## What landed

The triager may now lift a coder's `<loop>-blocked` — resetting that coder's two-rescue count,
until now an operator-only act — but only by changing what the ticket asks for. Two surfaces: a
fifth `rescue` triage bucket (last in the intake order) and an `unblock` op with five
preconditions, a two-per-ticket lifetime cap, and a `RALPH_TRIAGE_UNBLOCK_DAYS` (7) window.
`remove-label` of a `*-blocked` stays refused: every guard hangs off the one op allowed to touch
another loop's label.

## Key decisions

- **No new `TriageOutcome`.** The issue's `rescued (…)` is the journal's `**Outcome:**` line, not
  the marker's; `prompts/triager.md`'s journal vocabulary carries it. Marker outcome stays
  `specced` or `routed`.
- **The `op=unblock` marker is stamped by `triage/apply.ts`**, not written into the plan — its
  `body=` is a truncated sha256 no model can produce. As the issue specified it, every real plan
  would have been refused.
- **The bucket reads the census's 20-comment tail; the op re-reads the thread in full**, so the
  bucket can offer what the op refuses. A full read per candidate inside the claim path is the
  per-issue fan-out GitHub throttled on 2026-09-28. Costs one iteration, never a wrong write;
  documented rather than papered over.
- **`sections.ts` is a leaf.** Putting the `## heading` anchor in `triage/body.ts` made the
  frontier import the triage write engine, and `runner-failure.ts` imports the frontier — which
  broke the supervisor's stderr redaction in `ralph.test.ts`. Layering, not tidiness.
- **One spec question left open on the issue** (comment 5972936297): the `"amends": true` comment
  route cannot be mechanically verified to change anything. Implemented as the issue names it,
  fenced as far as is checkable; dropping it is a four-line follow-up.
