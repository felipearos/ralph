## Why three criteria became eight

Three rounds of `ralph-review-spec` against the fetched issue
(`.ralph/logs/spec-328.md`), with the proposed section text pasted into the
brief as the change under review (`brief-328-ready.md`, `-r2.md`, `-r3.md`).
Round 1: 6 findings. Round 2: 6 against the rewrite. Round 3: "no blockers",
3 worth a one-line edit, all applied. What the rounds bought:

1. **"a live lease" was undefined**, and the real claim blocks on more than
   `active`: `leaseBlocksClaim` lets only `expired` through, so `slow`,
   `reconnecting` and `dead` block too (`claim-lease.ts:146-161`). A coder
   reading "live" as `status === "active"` leaves the dry run disagreeing with
   the claim in three cases of four. The criterion now names the rule, and asks
   for a test over `active` plus `reconnecting` — not `slow`, whose
   `holderRunsHere` check is host-dependent.
2. **The issue's "matching the `expiredLease` branch" pointed the wrong way for
   its own incident.** That branch needs `canReclaimExpired`, which also
   requires the lease's `claim` label to be on the issue (`:3808-3811`) — and a
   leaked lease has no label. Routed through it, an expired labelless lease
   would be obstructed while the real claim takes it: the same disagreement,
   inverted. The criteria state the rule outright (obstruct exactly when
   `claimLease` would return `held`) and say not to use that helper. Flagged on
   the ticket as a deliberate reading of the issue rather than its text.
3. **The original gate criterion was satisfiable by a test that already passes
   on `main`**: `decide` only reads `obstructed.length`
   (`frontier-gate.ts:424-426`), so a hand-built `pick` proves nothing. It now
   requires the real chain (`takeOne` → `renderTakeOne` → `frontierOutcome` →
   `decide`, or the CLI under a fake `gh`, which means `subprocessSuite`), and
   that the test flip when the new check is removed.
4. **Two traps in that test, both named on the ticket.** The lease store must be
   a temp one: `leasePathFromGit()` resolves to the git common dir every loop
   worktree on this host shares (`claim-lease.ts:163`), so a test writing a
   "foreign lease" there would fence the live loops off that issue number — and
   `test-ralph-logs.global.ts` does not guard that file. And the fixture
   frontier must hold exactly one unit, since a dry run that obstructs one
   candidate moves on and offers the next (`:3095-3131`).
5. **"writes nothing" was not checkable.** `withClaimLock` and
   `withLeaseStoreLock` use the same `next-tasks-claim.lock`
   (`claim-lease.ts:203-208`, `next-tasks.ts:3277-3289`) and both delete it on
   exit, so asserting its absence afterwards proves nothing. A spy is required
   instead, plus `io.claim` / `io.releaseExpired` never called.
6. **The lease read needs a seam at all.** The lease `io` is an inline literal
   inside `main()` (`:3801-3818`) and is not exported, and neither is
   `probeFrontier`. Without an exported, path-injected factory a coder's only
   honest route is spawning the CLI. The first criterion now asks for that
   factory, taking the store path and **both** halves of the identity.

## Decisions

One product question the issue left open, decided under a cited rule and
recorded in the plan's `decisions`:

- *What does a dry run do when the lease store cannot be read?* It falls back —
  a candidate with no label or PR obstruction is still offered, and nothing is
  recorded against it. Rule: `CLAUDE.md`, "a missing or malformed signal falls
  back to existing behaviour, never to a stuck loop." This diverges from the
  real claim, which throws there (`readLeaseStore`, `claim-lease.ts:182-186`),
  and the criterion says so in as many words.

The loop's **own** lease must not obstruct either (`run` *and* `loop` matching,
`next-tasks.ts:2730-2733`, since `claimLease` compares both). That is not a
product decision — the issue already says "owned by another loop" — only the
testable form of it, and it is the one error that would be worse than the bug.
