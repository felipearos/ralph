## What was built
- `eval-proposals.ts`: a proposal's status (proposed → subset-run → full-run → passed/failed) comes from its runs. A promising subset run (guardrail conditions without the noise floor) puts exactly one full-set recommended run in the inbox. The promising check runs outside the long lock and re-reads under the lock. An unpromising or stopped run fails its proposal and records the reason.
- `evals-proposals.ts list` CLI; dashboard `GET /api/evals/proposals`, relayed as `evals-proposals`; a Proposals tab in Evals; README section.

## Key decisions
- Proposals advance when they are read (the GET writes; the collect.ts header says so).
- Rationale is hidden on summary-only projects locally as well as remotely, following the evals-set convention.
- No verdict until the full-set run exists.
- correctness: 0 P1, 1 P2, 5 P3 — 4 fixed, 2 dropped (the failing-advance re-check on every poll is acceptable; a no-op quality proposal counts as promising per the spec wording). Spec: all ACs met. Standards: P3s only.
