## What the three review rounds found, and what the merged code does about it

Worth recording, because the work is not wasted — the same questions will come
back on the next picker-shaped ticket, and two of them are still open in
`cf46771b`.

Round 1 (6 findings), round 2 (1 blocker + 7), round 3 (no blockers + 6). The
blockers were both about the same thing: **on Linux an exit code cannot tell a
cancel from a failure.** `zenity` exits 1 when the operator cancels AND when it
cannot open a display, and stderr is no proxy either — a GTK build prints
`Gtk-Message: GtkDialog mapped without a transient parent…` on an ordinary run,
so "exit 1 with anything on stderr is unavailable", which my round-1 draft said,
would have turned every cancel on such a host into an error. Round 3 settled on:
cancel is the default, unavailable only on a stderr line matching
case-insensitive `/open display/` (GTK3 says `cannot open display:`, GTK4 says
`Failed to open display`; this host is Fedora 44).

`cf46771b` resolves it the simpler way — `if (picked.status === 1) return { path:
null }` in `dashboard/onboarding.ts`, with the 502 path tested at exit **255**
(`dashboard/folder-picker.test.ts:69`). Same default, no display check. So where a
build exits 1 on a display failure, the operator clicks Browse and nothing
happens, with no message.

The second blocker, also still open: **the deployed dashboard may have no display
at all.** `dashboard/remote/systemd/ralph-dashboard.service` sets only
`RALPH_HOME` and `PATH` and is `WantedBy=default.target`, so it can start before
any graphical session, and `createOnboardingAdapter`'s env is `{ ...process.env,
...config.env }` (`:154`). There is no `DISPLAY`/`WAYLAND_DISPLAY` precheck in the
merged code and nothing in `dashboard/README.md` about
`systemctl --user import-environment DISPLAY WAYLAND_DISPLAY XAUTHORITY` — which
also has to be run from a terminal inside the graphical session (over SSH it
imports nothing) and lasts one boot.

Both are in the comment on #370 as evidence. **A triager cannot file the
follow-up**: `create-issue` lives in a plan, and a plan needs an open unit.
