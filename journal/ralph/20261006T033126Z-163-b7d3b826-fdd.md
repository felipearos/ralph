**What shipped.** The ci-doctor's own success measure, written and surfaced:

`store.metrics` already existed in the schema and was already pruned to 30 days

derivation and the panel.

**Key decisions.**
1. **Both counters keep `Math.max(stored, recomputed)` per day.** `prune` drops
   builds at 72 h while metrics live 30 days, so assigning would undercount a
   half-pruned day and zero whole days on a rebuild. The consequence is that
   the counters are monotonic: a reclassification cannot lower a past day, and
   a doctor down more than 72 h loses a day silently. Accepted, documented at
   the site.
2. **"Parked on a flake" is NOT `block-reason.ts`'s kind.** That classifies
   from the record's first line only, so the canonical CI block (`blocked: PR
   #1681 red twice in CI` with a quoted FAIL beneath) lands in `other` — yet it
   is exactly what the gate's priority 4 acts on. A new optional
   `Case.parkedOn` records the doctor's own reading: the lead line OR a quoted
   `FAIL <file> > <test>`. A record that merely mentions a `*.test.ts` path is
   not counted.
3. **`merge-wait.ts` keys on `RALPH_RUN_ID` + `RALPH_ITERATION`**, not the
   session: `ralph.sh` mints a fresh session inside one iteration on a phase
   retry, which would split that iteration's queue waits in two.
4. **Wait windows come from file mtime** — a `WaitResult` carries no clock and
   the filename's stamp is local time. The `.jsonl` history is deliberately
   never read (same records; reading it would double every wait). The worktree
   is part of the iteration key.
5. **`CI_HEALTH_VERSION` not bumped**; `Case.parkedOn` is optional with a
   reader fallback.
6. `utcDay`, `KNOWN_FLAKE_STATES` and `METRICS_DAYS` moved to `store.ts` (the
   leaf): three writers need the day grammar, and the parity test otherwise
   imported the whole Buildkite scanner graph to read one integer.

**Ruled out.**
- `parkedOnFlake` keyed on `block-reason.ts`'s kind alone — measures almost
  none of the tickets the doctor acts on. Tried; failed its own test at 1 of 2.
- `testId !== null` as the flake signal — over-counts, because `testIdOf`'s
  fallback matches any test-file token.
- Reading `build.state` for "red" — kept the module's own `isRed` notion, so a
  build green only because its flaky job was retried still counts. Tested.
- Filtering the adapter's roots to coder roots — only coders run `AWAIT_PR`, so
  the numbers come out identical, and `dashboard/README.md` already says "every
  configured root", so code and docs agree as they stand.
