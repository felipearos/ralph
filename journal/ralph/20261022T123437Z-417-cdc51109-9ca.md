## What I decided and why

#417 ("a PR whose migration was applied by hand is the project's top priority
until it merges") arrived unlabelled with 4 ACs, so the frontier gave it to
intake. The mapper confirmed nothing of it is on `main`: `migration-applied`
matches nowhere in the repo, there is no operator "applied" signal at all, no
ordering among the PRs a loop could shepherd (`shepherdable()` is a plain
`prs.find(...)`, `frontier-gate.ts:203-211`), and no PR-age watchdog anywhere
(`pr-wait.ts` pushes nothing). But the work crosses the role prompts, the
frontier and the dashboard — three of `CLAUDE.md`'s areas, plus notifications —
so it is oversize and the verdict is a split.

Three children, each ready on its own terms and in no dependency order, because
the one thing they share is a label name I pinned in the parent:

- **#432 `ready-for-agent`, group `migration-applied`** — the applied signal: a
  `migration-applied.ts` CLI modelled on `ci-doctor/unpark.ts:14-33` (comment
  with a marker, drop the `<loop>-blocked`, label the issue and the PR
  `migration-applied`, `gh pr ready` last), plus the `prompt.md` §6 line that
  makes the handoff comment name it. Criterion 1.
- **#433 `ready-for-agent`, group `migration-applied`** — the frontier
  ordering: when more than one of a loop's PRs is shepherdable, the
  `migration-applied` one comes first, in `shepherdable()` and in `prompt.md`
  §1 priority 1. Criterion 2, for the loop that owns the PR.
- **#434 `ready-for-agent`, group `migration-watchdog`** — the stall alert: one
  notification from the dashboard's reconcile pass when a `migration-applied`
  PR is still open past a one-hour threshold. Criterion 3.

Criterion 4 (`prompt-render.test.ts`) belongs to #432 and #433, the two that
touch a prompt — which is also why they share a staffing group: they both edit
`prompt.md` and that test. #434 touches neither, so it is its own group and can
run in parallel.

**All three went out `ready-for-agent`, with `## Blocked by: None`.** That is
the first split in this run that did not leave children un-promoted, and the
trick was to pin the contract — the label is exactly `migration-applied`,
lower-case, on both the issue and the PR — in the parent's `What to build`.
#432 writes it; #433 and #434 only read it, so neither needs #432's code to be
built or tested, and the staffing group (not a blocker edge) carries the
file-level conflict between #432 and #433. Worth reusing: it sidesteps the
`add-blocker.issue`-cannot-take-a-ref problem that left #420, #421, #425, #430
and #431 waiting for a later triage pass.

## The decisions, with evidence

- **A command, not a dashboard button.** #417 offers either. A dashboard action
  needs a new adapter with its own closed surface (`dashboard/read-only.test.ts`)
  and verbs no surface has — `adapter-pulls.test.ts:68` asserts the PR-read
  surface contains no `ready`, `edit` or `merge`.
- **`gh pr ready` goes last**, as unpark does: a stamped draft is never
  shepherded (`frontier-gate.ts:198-211`), so that step is what exposes the PR,
  and nothing should become shepherdable before the ticket is unblocked.
- **The marker suppresses a second comment and nothing else.** My first draft
  made it short-circuit the command; a run that died after commenting would
  then leave the ticket blocked and the PR a draft — this incident over again.
- **Nothing in `block-reason.ts` changes.** I had specced an "applied" state
  there; dropping the `<loop>-blocked` already removes the ticket from the
  stuck list and the rescue path, which key off the stuck label
  (`frontier/next-tasks.ts:1657-1661`).
- **The label must be ensured on the GitHub repo, not only in the tracker.**
  `checkTrackerLabels` (`preflight.ts:688,782-800`) calls
  `tracker.ensureLabels`, which on Linear or Jira creates it there — and
  `gh pr edit --add-label` refuses a label the GitHub repo lacks. On the
  backoffice project (live on Linear) the PR half would have failed and
  `gh pr ready` would never have run. #432 ensures it on the repo itself.
- **Criterion 2 needs no change to the shepherd's position.** `decide()`
  already returns the shepherd verdict ahead of the resumable claim and local
  recovery (`frontier-gate.ts:297-311`) and `prompt.md:254` is priority 2. The
  gap is only *which* PR. The rails stay: `prompt.md:244-245` — a shepherdable
  PR is never permission to overwrite a different dirty checkout.
- **"Before any other work on the project" = the owning loop's own work.**
  Another loop's PR "remains that loop's work" (`prompt.md:229-233`), so idling
  other loops buys nothing. The uncovered case is the incident's: the owner
  crashed. That is #425's, and the plan commented there asking the adopter to
  take a `migration-applied` PR before any other orphan.
- **The alert cannot live in an iteration**, for the same reason. The only
  pass scheduled without one is `dashboard/reconcile.ts`
  (`dashboard/server.ts:939-953`).
- **The watchdog's dedupe is the delicate part, twice over.** `claimState` keys
  `${run}:${occurrence}` per worktree (`push-notification.ts:43,453-459`) and a
  restart under a new run id re-raises it (`:63-68`) — so the pass carries a
  fixed run id and an occurrence derived from the PR and the apply time. And
  the state root is not just where the dedupe file lives: `claimState` resolves
  the project's plugins from it (`:458`, `plugins.ts:119-133`), so a scratch
  directory would pass every criterion and page nobody. #434 names one of the
  project's own loop worktrees, in roster order.

No `decisions` block in the plan: every call above is forced by code the mapper
cited or by #417's own text (which offers "a dashboard action **or** a command"
and "for example 1 h"). No difficulty labels: Jav is off here and its block
lists none.
