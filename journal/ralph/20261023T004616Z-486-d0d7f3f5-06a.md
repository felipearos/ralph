## What I decided and why

#486 is the `learning-fix` ticket for `learning-fix-tickets-filed-twice`: one learning
gets two fix tickets, and the frontier then hands the duplicate to a second loop. It
arrived `needs-triage` with the template body, whose first criterion is "specify a
reproducible verification criterion before marking this ticket ready-for-agent" —
i.e. the spec work was the unit. Verdict: **ready**, after writing `What to build`,
8 acceptance criteria and a `## Blocked by: None` the body did not have.

First I ran the ticket's own workaround: `gh issue list --search
"6bb455cb84…" --state all` returns only #486, so this one has no duplicate sibling.
(#481/#482 and #483/#484 are the duplicate pairs the learning is about; they are open
and claimed, and I left them alone.)

A mapper pass over `origin/main` (bd8d552) found **two** causes, each sufficient:

1. `reconcileFindings` (`findings.ts:138-166`) writes its `--revise` draft from
   `git show origin/main:<file>` (`:144-157`) **before** spawning the publisher
   (`:158`), which is where the lock is taken. Under the lock `publishLearning`
   re-reads a fresh `origin/main` (`publish-journal.ts:404-418`) and calls
   `reviseEntry` (`:428`), which keeps only the `Seen again` ledger lines and takes
   the draft's prose — so a stale `- **Fix:** no issue yet` lands back over a link
   another process wrote seconds earlier, and `pendingFinding` reads the entry as
   pending again.
2. `promoteFinding` (`findings.ts:95-134`) then decides the finding is unfiled from a
   single REST read of the `learning-fix` registry (`:78-79`, exact-line match at
   `:103`). The comment at `:93-94` asserts a just-created ticket is visible there.
   The history says otherwise: `cc1f839` rewrote "no issue yet" → `#481` at 21:22:21,
   `4644c72` rewrote `#481` → `#482` eight seconds later, and `7990ee7`/`dc3c200` did
   the same for #483/#484. Had the read thrown, the diff would show a revert to "no
   issue yet", not a second number — so the read succeeded without #481 in it.

So the spec asks for two guards: carry an existing `Fix` link through a `--revise`
whose replacement says `no issue yet`, and keep a per-host `{ marker: url }` record
(`$RALPH_FINDINGS_RECORD`, else `~/.ralph/findings.json`, a `promoteFinding`
parameter like `gh`) written immediately after a successful create, consulted
alongside the registry read.

**#485 is not the cause, and I did not touch it.** Its `--slurp`/`--jq` fix already
landed as `43faafc` ("#478"); before it the lookup always threw and nothing was filed
at all, so the duplicates are downstream of that fix, not of the bug. Worth a later
look by someone: #485 is still open and `ready-for-agent` even though its fix appears
to be on main — a closure candidate for whichever loop draws it, not mine this pass.

Out of scope in the body, with reasons: frontier-side dedupe (neither
`frontier/next-tasks.ts` nor `frontier/next.ts` mentions `learning-fix` or
`ralph-finding`), cross-host duplicates (the record is per host, as the lock is), and
cleaning up the existing pairs.

Not oversize: 8 checkboxes, one area (`findings.ts` plus its publisher). Not
`ready-for-human`: no secrets, no host configuration, no human decision, no
migration; `~/.ralph/findings.json` is runtime state of the same kind as the journal
lock, not operator configuration. Jav is off here and lists no labels, so no
difficulty label.

## Review — three rounds, and what each caught

`ralph-review-spec` ran three times. Every round found something that mattered, which
is the argument for not stopping at one:

- **Round 1, P1:** the first draft's "two successive promote passes file exactly one
  issue" **passes on origin/main**, because the second pass gets the text the first
  returned, `pendingFinding` is false and it returns at `findings.ts:96` without
  reaching the create. A criterion that passes unchanged is worthless. Fixed by
  giving both calls the *original pending* text.
- **Round 1, P1:** "unreadable record throws" would have swallowed a **missing**
  record, so a fresh host would never file anything — against CLAUDE.md's rule that a
  missing signal falls back to existing behaviour. Fixed: missing = empty, corrupt =
  throw before any create.
- **Round 2, P1:** the revise criterion could still pass via guard 2 if the fake's
  registry listed the existing ticket. Fixed by pinning the fake's registry read
  empty and the record path fresh, so only guard 1 can prevent the create.
- **Round 2, P2s:** the control case "with no record in play" is unbuildable once the
  record path has a default, and the retry criterion miscited
  `publish-learning.test.ts:443` (which uses `maxAttempts: 1` and a second
  `publishLearning` call, not a re-run inside one run).
- **Round 3:** confirmed each criterion now fails on `origin/main` today, and that the
  citations are right at bd8d552. One P3 applied: the failed-record-write half is
  skipped as root, the way `lineup-editor.test.ts:398-406` already skips a chmod case.

The reusable lesson for this role: **ask the reviewer whether each criterion fails on
today's main.** Two of the three P1s were criteria that a correct implementation and
today's code would both satisfy.
