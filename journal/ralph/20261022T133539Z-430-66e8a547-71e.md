## What I decided and why

#430 ("a blocker two loops are waiting on escalates once, early") is child C of
spec #416. It arrived with no state label on purpose: the split that created it
could not write an edge to an issue it was itself creating, so its `## Blocked
by` was prose asking the next triage pass to record the edges and promote it.
Both blockers have merged — **#428** (child A, 32b3b20) and **#429** (child B,
6222d14) — so the promotion was due. Verdict: **ready**.

A mapper pass over `origin/main` confirmed none of it is built: `backoff.ts`
imports only `node:fs`, `node:path`, `./control-inbox` and `./pr-wait`
(`backoff.ts:49-53`), `blocker-store.ts` has no importer but its own test,
nothing outside it calls `markNotified`, `shared-blocker` is absent from
`NOTIFICATION_KINDS`, and `--base-sha`/`--base-failing` exist only as
`blocker-store.ts`'s own CLI flags. Not oversize: 8 criteria over one area. Not
`ready-for-human`: no secrets, no host state, nothing measured on a live loop,
no migration. Jav is off here and lists no labels, so no difficulty label.

## The interesting part: a split's text ages against its own siblings

#430 was specced before #428 and #429 existed as code, and they did not land
the shape it assumed. So `## What to build` gained a **Pinned by triage** block
and the original seven items were left verbatim, with the pins saying where
they win. The ones that would each have cost a coder a round:

- **`settle()` stays pure** (`backoff.ts:266-267`) and `SettleInput` has
  nowhere to put a dependency. The store work is a new async `shareBlocker`
  called from the CLI's settle branch; `main` is already async (`:439`), so it
  takes an optional fourth `deps` and nothing below it changes shape.
- **The default base lookup must read the commit-STATUS endpoint too**, not
  only check-runs, classified by `parseCheck`'s rules (`pr-wait.ts:103-125`) as
  `readCi` does (`host-lease.ts:500-501`). The key #416 exists for is
  `ci:buildkite/loggd:production-migrations` (`backoff.test.ts:370`) and
  `buildkite/loggd` is a legacy StatusContext: a check-runs-only lookup would
  report `baseFailing: null` forever and child D's base probe would never arm.
  This was the single most valuable finding of the three review rounds.
- **A corrupt store is not a degrade case.** `readStore` reads an unparseable
  file as empty and the next write repairs it (`blocker-store.ts:226-245`), so
  #430's item 7 was wrong about the store it was written against, and a coder
  satisfying it would have added corruption detection against #429's design.
  What degrades is a throw: `withStore` out of lock attempts (`:269`),
  `identity()` (`host-lease.ts:439`), or the push.
- **The push's argv is pinned in full.** `inputFrom` returns null without
  `--subject` and `--body` and `main` swallows the null
  (`push-notification.ts:346-359`); the kind must be in `NOTIFICATION_KINDS`
  (`:354`). Every criterion counts invocations of a fake, so a push missing
  either would pass all of them and escalate nobody.
- **`prune` is not a step to add** (`withStore` already does it, `:274-275`),
  and **`clearedBy`/`baseSha`/`baseFailing`/`first`/`notified` are on the
  blocker, not the waiter** (`:55-68`) — item 4 had it the other way round.
- **`shareBlocker` returns at once when nothing is shared**, and `identity`
  takes `main`'s `env` and never `process.env`. Both exist because
  `backoff.test.ts:385-392` pins a settle's output lines with `toEqual`, and
  because `process.env` HAS `RALPH_LOOP_NAME` when a loop's own gate runs
  `bun run test` — so the existing `ci:`-key cases would have joined a store
  and called the real `git`/`gh` lookup from CI.
- **A `storePath` trap worth remembering.** `blocker-store.ts:309` resolves its
  path from `process.cwd()`. Copied into `backoff.ts`, an in-process test would
  resolve to THIS checkout's git common dir — the live loops' real store — and
  the `.ralph` logs guard would not catch it, because it only watches
  `.ralph/`. Pinned to `blockerStorePath(cwd)`, using `main`'s own argument,
  which is also what makes the two end-to-end worktrees share one store.
- Stale citations in the ticket corrected: settle is `ralph.sh:2474-2477`, and
  the "must never hold or stop a loop" rule is `ralph.sh:2094-2097`.

The criteria were replaced, not amended — the ticket was unlabelled, so they
were mine — and there are still 8, inside this project's size fence, each
naming its seam and the dependency a test injects.

## The frontier read my prose as an edge — and that is the lesson

The first plan's `## Blocked by` carried the two numbers and a sentence saying
which child of the spec each was: "#428 is child A of #416 … and #429 is child
B". The frontier reads **every** issue reference under that heading as an edge,
so #430 came out of the apply as `#430 ← #416` under BLOCKED in the census —
blocked by its own open parent spec, the exact opposite of a promotion. The
apply did not refuse it: the plan was valid and the census still read, it just
read something I did not mean.

**Under the five managed headings, write references and nothing else.** A
number inside an aside is still an edge. A second plan replaced the section
with bare numbers; #430 then showed as READY NOW, 1 independent staffing group,
and the "prose-only edges" warning stopped naming it.

## A harness bug, filed nowhere yet

`add-blocker` cannot write a native dependency on this project:

```
triage-apply: stopped at edge-430-428: gh: Invalid request.
Invalid property /issue_id: `"5979105789"` is not of type `integer`. (HTTP 422)
```

The dependency API wants `issue_id` as an integer and it is being sent as a
string. Exit 1, so the plan was re-runnable, but re-running would hit the same
bug — it is not transient. I dropped the two `add-blocker` ops, said so in a
comment on the ticket, and the promotion stands without them: the frontier
reads the bare list, both blockers are closed, and the ticket gates as ready.
**This is worth a ticket of its own.** Every split in this run has left its
children's edges as prose for the next pass to backfill, and this is the op
that backfill needs — #431 and #421 are still waiting on it (the census names
them under "prose-only edges"). I could not file it: a triager creates issues
only as children of its own unit's split.

## Spec review — three rounds, all three of which changed the ticket

1. The corrupt-store criterion could not be met; "one line on stdout" collided
   with the settle's own line; the push argv was unpinned; lock exhaustion cost
   10 s in-process, so it became an injectable `withStore`; and the `storePath`
   pin had the right conclusion for the wrong reason.
2. The check-runs-only lookup; the unpinned check-name comparison
   (`normaliseBlockerKey` lowercases the key, GitHub does not lowercase names)
   and the repo to ask about; `identity()` reading `process.env`; and the
   in-process criteria not requiring an injected lookup.
3. Nothing blocking. Folded in: the early return, "null in every other case",
   and `main`'s env throughout.

I verified every load-bearing claim against the code myself before taking it —
`readStore` swallowing corruption, `inputFrom` requiring subject and body,
`push-notification.ts` being mode 644 while `usage.py` is 755,
`commonStatePath` falling back rather than failing, and `readCi`'s two
endpoints.
